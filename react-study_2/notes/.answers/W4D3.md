## 复习 1（0.5 分｜useActionState 与 useFormStatus）

### 参考答案

1. **返回顺序错了。** `useActionState` 返回 `[state, formAction, isPending]`；代码写成了 `[state, isPending, formAction]`，于是 `formAction` 实际拿到的是布尔值，`<form action={formAction}>` 不会正常工作。`saveCard` 的声明是 `(formData: FormData)`，但 `useActionState` 调用 action 时第一个参数是 `prevState`（初始为 `{ error: null }`），所以 `saveCard` 收到的“formData”其实是上一次 state，真正的 `FormData` 在第二个参数。正确签名是：
   ```ts
   async function saveCard(prevState: State, formData: FormData): Promise<State>
   ```
2. **`SaveButton` 里的 `pending` 可靠。** 它渲染在 `<form>` 内部，`useFormStatus` 读取的是祖先 form 的提交状态。**`CardForm` 里的 `pending` 不可靠，永远是 `false`**：`useFormStatus` 只读取祖先 `<form>`，不会读取同一个组件自己返回的、尚未成为祖先的 form；即使外面还有一层 form，它跟踪的也是外面那层。因此提交期间「外层按钮」不会因为 `CardForm` 的 `pending` 而禁用；`SaveButton` 会正常显示“保存中…”并禁用。

### 评分点（共 0.5 分）

- 0.25 分：指出返回顺序应为 `[state, formAction, isPending]`，并说明 `saveCard` 第一个参数是 `prevState`、`FormData` 在第二位，给出正确签名。
- 0.25 分：指出 `SaveButton` 的 pending 可靠、`CardForm` 的 pending 不可靠（同组件渲染的 form 不是祖先），外层按钮不会禁用。

### 简短解释

`useActionState` 把 action 当成“带副作用的 reducer”，所以第一个参数永远是上一次 state；`useFormStatus` 是“父级 form 的上下文”，必须从 form 的子树里读。两者都不是“组件自己的状态”。

## 复习 2（0.5 分｜路由 action 的校验与 redirect）

### 参考答案

1. **`data(errors, { status: 400 })` 同时表达“请求有误”和“这是校验结果”。** React Router 只对 2xx 的 action 结果触发 loader revalidate；400 避免无意义地重新跑 loader，也能让 `useActionData()` 读回结构化错误。组件里用 `const errors = useActionData<typeof createTaskAction>()?.errors`，再渲染 `errors?.title`。如果返回普通对象，缺少状态码语义，容易被当成成功响应并触发 revalidate。
2. **成功路径 `return redirect(...)` 是让路由导航到新页面，而不是把 task 当作普通数据返回。** `redirect` 是控制流：React Router 会据此导航并重新跑目标路由的 loader；返回 `task` 不会改变 URL，也不会触发目标页的数据加载。Server Action 里的 `next/navigation` `redirect` 同样是**抛出**控制流异常（`NEXT_REDIRECT`），不是普通返回值；它必须放在 `try/catch` 外，且后面的代码不会执行。

### 评分点（共 0.5 分）

- 0.25 分：说明 400 的语义（校验失败、避免成功 revalidate）以及 `useActionData` 读取错误。
- 0.25 分：说明 `redirect` 用于导航/控制流、不是普通返回值；Server Action 中它抛 `NEXT_REDIRECT`，不能在 try/catch 里吞掉。

### 简短解释

路由 action 的返回值决定“成功还是失败、要不要 revalidate”；`redirect` 决定“去哪里”。Server Action 把同样的思路搬到了 POST + RSC payload 的世界，`redirect` 仍然是控制流异常。

## 第 1 题（3 分｜一个“看起来能跑”的 Server Action）

### 参考答案

#### 1. 至少 4 个问题（1.5 分）

- **没有认证/授权。** action 里没有 `auth()`/session 检查；任何人都能直接 POST 这个 action，改任意 `cardId`。即使页面只对登录用户渲染，也不影响直接调用。
- **没有所有权/项目成员检查（IDOR）。** `cardId` 完全由客户端提供，代码直接 `db.card.update({ where: { id: cardId } })`；攻击者可以把 ID 换成别人的卡。必须用 session 的用户去查“这张卡是否属于我/我的项目”，而不是只按 ID 更新。
- **信任隐藏字段 `assignee`。** 隐藏字段会出现在 HTML/请求里，攻击者可以改成任意人；代码又把它直接写进 `data`。`status` 同样只做了类型断言，没有运行时校验。服务端应只接受白名单字段；`assignee` 要么由有权限的用户显式选择并在服务端校验角色，要么从数据库/服务端逻辑派生。
- **没有输入校验/类型转换。** `title` 用 `as string` 断言，File/null 也会被当成字符串；`status` 的 `as 'todo' | 'doing' | 'done'` 只是编译期断言，运行时可以传 `"admin"`；没有 trim、长度、必填、枚举检查。`String(formData.get('cardId'))` 对 null 会得到 `"null"`。
- **返回整个数据库行 `card`。** 可能包含内部字段、token、软删除标记、关联数据；返回值会序列化到客户端。应返回最小 DTO（如 `{ id, title, status, assignee }`）。
- **没有缓存失效。** 写库后没有 `revalidatePath` / `revalidateTag` / `updateTag`，看板/详情可能继续显示旧缓存。
- **没有错误处理/限流。** 数据库异常会原样抛出或泄露；也没有 rate limit，攻击者可以高频写库。
- **前端 `pending`/`disabled` 不是安全措施。** 它们只影响正常用户的交互，不阻止直接 POST。

#### 2. 正确的服务端核心流程（1 分）

```ts
'use server'

import { auth } from '@/lib/auth'
import { revalidatePath, updateTag } from 'next/cache'
import { redirect } from 'next/navigation'
import { updateCardForUser } from '@/data/cards'
import { parseCardForm } from '@/lib/validation'

export async function updateCard(prevState: State, formData: FormData): Promise<State> {
  // 1. 认证：session 从 cookie/header 读，不从 FormData 读
  const session = await auth()
  if (!session?.user) return { ok: false, error: 'UNAUTHENTICATED' }

  // 2. 解析 + 校验 + 类型转换，一次收集 fieldErrors
  const parsed = parseCardForm(formData)
  if (!parsed.ok) return { ok: false, fieldErrors: parsed.fieldErrors }

  // 3. 授权/所有权：只更新当前用户有权限的卡；owner/member 从 DB 查
  const result = await updateCardForUser(session.user.id, parsed.data)
  if (!result.ok) return { ok: false, error: result.error }

  // 4. 成功后才失效缓存；需要立即看到自己的写入用 updateTag/revalidatePath
  updateTag('cards')
  revalidatePath('/board')
  redirect(`/cards/${result.cardId}`) // 放在 try/catch 外
}
```

关键点：session 在 action 内读；`cardId` 只是“操作哪条资源”的引用，不能当权限；只更新允许的字段；校验失败返回 `{ ok:false, fieldErrors }`，不写库、不失效、不跳转；成功后再 revalidate，最后 redirect。

#### 3. 序列化边界（0.25 分）

`FormData`、原始类型、数组、普通对象、`Date`、`Map`/`Set`、Server Function 等可以跨边界；类实例、普通函数、JSX、未注册的 Symbol 不行。`card` 不应原样返回：数据库行可能含内部字段或类实例，既可能泄露也可能序列化失败。返回最小 DTO，例如 `{ id, title, status, assignee }`，并且只返回 UI 需要的字段。

#### 4. pending/disabled 能否作为安全边界（0.25 分）

不能。`disabled`/`pending` 只是浏览器端的 UX，攻击者可以直接构造 POST，绕过按钮、隐藏字段和任何客户端校验。真正的边界是服务端的 session、授权、所有权、输入校验和限流。

### 评分点（共 3 分）

- 1.5 分：至少指出 4 个有效问题（无认证/无授权/IDOR/信任隐藏字段/无校验/返回整行/无缓存失效/无限流/错误泄露），并说明利用方式。
- 1 分：给出正确流程：action 内 `auth()`、解析校验、按资源授权/所有权、只写允许字段、成功后 revalidate、校验失败返回结构化 state；失败不写库。
- 0.25 分：正确说明序列化边界，指出应返回最小 DTO 而不是整行。
- 0.25 分：明确 pending/disabled 不是安全边界。

### 简短解释

这段代码的“能跑”来自把客户端当成了可信调用方：隐藏字段直接写库、只按 ID 更新、返回值不裁剪。Server Action 是公开 POST 端点，必须把页面渲染时的所有假设在 action 内重新验证一遍。

## 第 2 题（2.5 分｜公开端点与越权）

### 参考答案

#### 1. 为什么是公开端点、缺什么（1 分）

Server Action 编译后，客户端拿到的是 action ID + dispatcher；调用就是向当前页面发 POST。这个端点不经过页面渲染，也不要求请求来自你的 UI，所以任何能发 POST 的人都能调用。页面只给成员渲染按钮、viewer 的按钮 disabled，都只影响正常用户；攻击者可以直接构造请求。

这段代码缺少：

- **项目成员/角色/所有权检查。** 只验证了“登录”，没有验证“当前用户是否属于 `projectId` 这个项目、是否有移动/分配权限”。
- **卡片与项目的一致性检查。** `cardId` 和隐藏的 `projectId` 是分开传的；攻击者可以传自己有权限的 `projectId`，再传别人项目里的 `cardId`。必须用 `cardId` 查出卡片真实的 `projectId`，再基于真实归属授权，而不是相信客户端传的 `projectId`。
- **字段白名单。** `assignee`/`status` 都来自隐藏字段，直接写库；应只允许客户端提交允许的变更，或者由服务端根据角色决定。
- **失败时的原子性。** 当前代码在检查项目存在后就更新；如果后续发现无权限，必须保证没有写库。授权检查必须先于任何写入。

这是典型的 **IDOR（Insecure Direct Object Reference）**：客户端能指定对象 ID，服务端却没有验证该对象是否属于当前用户。

#### 2. 授权核心（1 分）

```ts
'use server'

import { auth } from '@/lib/auth'
import { revalidateTag } from 'next/cache'

export async function moveCard(formData: FormData) {
  // 1. 身份来自 session（cookie/header），不来自 FormData
  const session = await auth()
  if (!session?.user) return { ok: false as const, error: 'UNAUTHENTICATED' as const }

  // 2. 只接受白名单字段；assignee 是否允许由服务端角色决定
  const cardId = formData.get('cardId')
  const toStatus = formData.get('toStatus')
  if (typeof cardId !== 'string' || typeof toStatus !== 'string') {
    return { ok: false as const, error: 'INVALID_INPUT' as const }
  }
  if (!['todo', 'doing', 'done'].includes(toStatus)) {
    return { ok: false as const, error: 'INVALID_INPUT' as const }
  }

  // 3. 用 cardId 查真实卡片 + 项目成员关系；不要相信隐藏 projectId
  const card = await db.card.findFirst({
    where: {
      id: cardId,
      project: { members: { some: { userId: session.user.id } } },
    },
    select: { id: true, projectId: true },
  })
  if (!card) return { ok: false as const, error: 'NOT_FOUND' as const }

  // 4. 角色/所有权：例如只有 owner/editor 能移动，viewer 只能读
  const membership = await db.projectMember.findUnique({
    where: { projectId_userId: { projectId: card.projectId, userId: session.user.id } },
    select: { role: true },
  })
  if (membership?.role !== 'owner' && membership?.role !== 'editor') {
    return { ok: false as const, error: 'FORBIDDEN' as const }
  }

  // 5. 只写允许的字段；assignee 不由客户端隐藏字段决定
  await db.card.update({
    where: { id: card.id },
    data: { status: toStatus },
  })

  revalidateTag('cards', 'max')
  return { ok: true as const }
}
```

失败时（未登录/无权限/不存在/非法输入）必须直接 return，不能先写再检查；对“无权限”和“不存在”的响应要一致，避免通过不同错误枚举资源。

#### 3. 框架保护与缺口（0.5 分）

Next.js 内建：

- **只允许 POST**：降低被 GET 触发的风险。
- **CSRF/Origin 校验**：比较 `Origin` 与 `Host`/`X-Forwarded-Host`，不匹配拒绝；代理/CDN 用 `allowedOrigins`。文档说明**没有 `Origin` 头的请求会跳过比较**，所以它是纵深防御，不是认证。
- **body 大小限制**：默认 1MB，可用 `bodySizeLimit` 调整。
- **加密 action ID + dead code elimination**：构建期生成加密、非确定性 ID；未使用的 action 从客户端 bundle 移除；ID 最多缓存 14 天，新构建轮换。
- **closure 加密**：内联 action 捕获的变量加密后发给客户端；自托管多实例需稳定的 `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`；不要只依赖加密。

它们不能替代：认证/授权、输入校验、返回值裁剪、rate limit、幂等/重放防护、错误脱敏、会话安全。这个 action 还应加：按用户/IP 的 rate limit（写库/发通知）、审计日志、幂等键（防重复提交）、安全错误码（不返回 SQL/堆栈）、对高风险操作重新认证。

### 评分点（共 2.5 分）

- 1 分：说明公开 POST 端点、页面/按钮/隐藏字段不是安全边界；指出缺少成员/角色/所有权检查、cardId 与 projectId 不一致、IDOR、失败可能已写入。
- 1 分：给出正确授权核心：session 从 cookie/header 读；用 cardId 查真实卡片和项目；检查成员/角色/所有权；只接受白名单字段；失败不写库；成功后 revalidate。
- 0.5 分：至少说出 2 个框架保护及其局限（Origin 校验不是认证、无 Origin 跳过、body limit 不是业务限流、action ID 加密不是授权），并补充 rate limit/错误脱敏等至少一条。

### 简短解释

`projectId` 是客户端给的，`cardId` 也是客户端给的；两者不一致时，代码却用前者判断权限、用后者写数据。正确做法是“以 cardId 查出的真实归属为准”，再用 session 用户去匹配成员关系。任何“UI 不显示/按钮禁用”的说法都不能替代这条链。

## 第 3 题（2.5 分｜缓存失效、redirect 与三个 Hook）

### 参考答案

#### 1. Next.js 16 的缓存 API（1 分）

`revalidateTag` 的签名是 `revalidateTag(tag: string, profile: string | { expire?: number }): void`。Next.js 16 中单参数 `revalidateTag('cards')` 已弃用（旧行为等价于立即过期），应写两个参数。

- `revalidateTag('cards', 'max')`：把 tag 标记为 stale，采用 stale-while-revalidate；后续请求先拿旧值，后台刷新。**它不会在 action 响应里立即重渲染**，所以不适合“用户必须立刻看到自己的修改”。
- `revalidateTag('cards', { expire: 0 })`：下一次请求阻塞等待新数据；在 Server Action 中会触发类似 `updateTag` 的客户端刷新。
- `updateTag('cards')`：立即过期，下一次读取等待新数据；**只能在 Server Action 里调用**，适合 read-your-own-writes。
- `revalidatePath('/board')`：按路径失效；适合只影响一个页面/布局的场景。动态段用 `/cards/[id]` + `type: 'page' | 'layout'`；rewrites 要传目标路径。
- `refresh()`：只重新执行当前路由的动态工作，不失效服务端缓存；适合视图依赖缓存之外的状态。

本题写库后应选择 `updateTag('cards')` 或 `revalidatePath('/board')`（必要时组合），而不是单参数 `revalidateTag('cards')`。如果用户不需要立即看到，才用 `revalidateTag('cards', 'max')`。

#### 2. redirect 的语义与顺序（0.75 分）

`redirect` 在 Server Action 中**抛出**控制流异常（`NEXT_REDIRECT`），不是普通返回值。它必须放在 `try/catch` 外面，并且用 `return redirect(...)` 或直接调用；如果包在 `try/catch` 里，catch 会把它当普通错误吞掉，跳转不会发生，后面的代码还可能继续执行。

`revalidateTag` / `revalidatePath` / `updateTag` 应该放在 `redirect` **之前**。因为 `redirect` 之后的代码不会执行；如果先 redirect 再失效，目标页面可能读到旧缓存。Server Action 有 JS 时走客户端导航，渐进增强表单提交时用 303，其它情况常用 307；默认在 action 中使用 `push` 历史记录。

#### 3. 三个 Hook 的分工（0.5 分）

- `useActionState`：保存 action 的返回 state（如 fieldErrors）、提供 `formAction` 和 `isPending`；action 签名是 `(prevState, formData)`。预期内错误返回 state，未预期异常 throw 到 Error Boundary。
- `useFormStatus`：读取**祖先** `<form>` 的 `pending`/`data`/`method`/`action`；必须放在 form 的子组件里，不能和 form 写在同一个组件。
- `useOptimistic`：在 action 期间提供临时覆盖层；setter 只能在 action/`startTransition` 里调用；reducer 必须纯（不能生成随机 ID、不能改参数）。action 成功且真实数据更新后，乐观层与真实值对齐；失败或真实值没变时，临时层消失，UI 自动回滚。服务端仍是唯一真相。

#### 4. 2025-12 安全公告（0.25 分）

可核实的例子：

- **CVE-2025-55182**（2025-12-03，CVSS 10.0）：RSC/Flight 反序列化缺陷，未认证 RCE；影响 `react-server-dom-webpack/parcel/turbopack` 19.0、19.1.0、19.1.1、19.2.0，修复 19.0.1/19.1.2/19.2.1；Next.js 下游公告 **CVE-2025-66478**（App Router）。
- **CVE-2025-55184 / CVE-2025-67779**：DoS（CVSS 7.5）；**CVE-2025-55183**：Server Function 源码暴露（CVSS 5.3）；后续修复版本 19.0.4/19.1.5/19.2.4。
- 工程动作：升级 React/Next.js 相关包并重新部署；按公告轮换密钥；不要把秘密硬编码在 Server Function 源码里（运行时 `process.env` 不在源码暴露范围）；把依赖版本和安全公告纳入上线检查。应用层鉴权不能替代运行时补丁。

如果只写“RSC 有 RCE/DoS/源码暴露，应该升级和轮换密钥”，不写具体编号，也给分；编造编号不给分。

### 评分点（共 2.5 分）

- 1 分：正确说出 `revalidateTag(tag, profile)` 签名、单参数已弃用；区分 `'max'`（SWR，不立即重渲染）、`updateTag`（action-only，立即）、`revalidatePath`、`refresh`；指出本题应使用 `updateTag`/`revalidatePath`。
- 0.75 分：说明 `redirect` 抛 `NEXT_REDIRECT`、必须放在 try/catch 外、用 return；revalidate 必须在 redirect 之前，并解释原因。
- 0.5 分：三个 Hook 分工正确；useOptimistic reducer 纯、setter 在 action/transition、失败回滚；useFormStatus 必须在 form 子组件。
- 0.25 分：至少一个可核实的 CVE/影响类型 + 两条工程动作（升级、轮换密钥、不硬编码秘密、上线检查等）。

### 简短解释

Next.js 16 把“标脏等后台刷新”（`revalidateTag(...,'max')`）和“立即过期、用户马上看到”（`updateTag`）分开了；选错会让用户看到旧数据。`redirect` 不是返回值而是异常，顺序和 try/catch 都会影响它是否生效。Hook 负责体验，服务端负责真相。
