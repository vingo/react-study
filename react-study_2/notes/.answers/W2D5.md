# W2D5 课前测验参考答案与评分

总分 **9 分**：复习题 1 分（0.5 + 0.5），新主题题 8 分（2.5 + 3 + 2.5）。

依据本地 `zustand@5.1.0` 的类型定义与运行时源码、React 19.3 的实际行为核对。关键事实：

- TypeScript 中带 middleware 时写 `create<T>()(...)`（柯里化形式），否则 `set` 的类型推断可能不正确。
- v5 的 `useStore` 直接用 `useSyncExternalStore`，默认用 `Object.is` 比较 selector 的返回值；没有默认的 shallow 比较。
- `useShallow` 从 `zustand/react/shallow` 导入（`zustand/shallow` 也会重新导出）。
- v5 把 `createWithEqualityFn` / `useStoreWithEqualityFn` 移到了 `zustand/traditional`。
- `persist` 默认存储是 `createJSONStorage(() => window.localStorage)`，默认 `partialize` 是原样返回整个 state，默认 `merge` 是浅合并 `{ ...currentState, ...persistedState }`，写入形状是 `{ state, version }`（默认 `version: 0`）。

## 复习 1（0.5 分｜interval 的过期闭包与 cleanup）

### 参考答案

1. 页面在 1 秒、2 秒、5 秒时都显示 `1`。每次 tick 的 `console.log('tick', count)` 都打印 `0`。
2. 因为 Effect 的依赖数组是 `[]`，interval 回调闭包住的是首次 render 时的 `count`，也就是 `0`。之后 Effect 不再重新执行，回调里始终是 `count = 0`，所以每次都执行 `setCount(1)`；React 发现新旧值相同会跳过后续更新，页面停在 `1`。
   正确写法是用更新函数读取最新的 pending state，并在 cleanup 中清理：

   ```tsx
   useEffect(() => {
     const id = setInterval(() => {
       setCount((c) => c + 1)
     }, 1000)

     return () => clearInterval(id)
   }, [])
   ```

   依赖数组仍然保持 `[]`。如果把 `count` 加进依赖，每次 `count` 变化都会先 cleanup 旧 interval、再建立新 interval；虽然通常也能“每秒加一”，但计时器会被不断重置，容易漂移，而且每个 tick 都重新订阅，不是推荐写法。
3. 用 `useEffectEvent` 把“读取最新 `count`”从响应式依赖中分离出来：

   ```tsx
   const onTick = useEffectEvent(() => {
     console.log('tick', count)
   })

   useEffect(() => {
     const id = setInterval(() => {
       setCount((c) => c + 1)
       onTick()
     }, 1000)

     return () => clearInterval(id)
   }, [])
   ```

   `onTick` 不进依赖数组，但它总能读到最新的 `count`。状态更新本身仍应使用 `setCount((c) => c + 1)`，不要用 Effect Event 代替更新函数。

### 评分点（共 0.5 分）

- 0.2 分：页面始终显示 `1`，console 每次打印 `0`，并指出是空依赖导致的过期闭包。
- 0.2 分：使用 `setCount((c) => c + 1)`，并保留 `clearInterval` 的 cleanup；能说明把 `count` 加进依赖会重置 interval。
- 0.1 分：能说出用 `useEffectEvent`（或 ref）读取最新值且不重置 interval。

### 简短解释

Effect 的依赖数组决定“什么时候重新执行”，闭包决定“回调能看到哪一轮的值”。空依赖的 interval 只创建一次，所以它永远看到初始值；状态更新用更新函数才能基于最新的 pending state 计算。这个 cleanup 纪律同样适用于 Zustand 的 `store.subscribe`：订阅必须返回取消订阅函数。

## 复习 2（0.5 分｜URL 作为状态）

### 参考答案

1. 点击后：
   - URL 变成 `/tasks?q=react&page=3`；
   - loader 会重新执行，因为 search params 变化会触发导航/重新验证；
   - `TaskList` 不会重新挂载，还是同一个路由组件实例；
   - 列表使用 `q=react`、`page=3` 的数据；
   - 输入框仍显示本地草稿 `vue`。

2. `sort=due` 不在了。`setParams({ q, page: ... })` 传入对象时，会用这个对象**替换整个查询字符串**，不是合并。要保留所有现有参数，应基于当前 params 复制后修改：

   ```tsx
   setParams((prev) => {
     const next = new URLSearchParams(prev)
     next.set('q', q)
     next.set('page', String(page + 1))
     return next
   })
   ```

3. “下一页”使用的是 loader 数据里的 `q`（`react`），不是输入框里的本地草稿 `draft`（`vue`）。这里同一份“搜索词”有两个来源：一个是 URL/loader 中的已提交值 `q`，另一个是组件里的未提交草稿 `draft`。点击“下一页”只读取了前者，于是 URL/列表是 `react`，输入框是 `vue`。又因为 `q` 从 `react` 到 `react` 没变，同步草稿的 `useEffect([q])` 不会执行，草稿不会被重置。
   设计上应让 URL 成为唯一来源（输入框直接读写 URL，必要时防抖），或者在翻页时把草稿一起写进 URL；更符合 HTML 的做法是用 `<Form method="get">` 让浏览器统一生成查询串。若保留草稿，至少要在 `draft !== q` 时禁用翻页或提示先搜索。

### 评分点（共 0.5 分）

- 0.25 分：正确写出 URL `/tasks?q=react&page=3`；说明 loader 会执行、组件不重挂载、输入框仍是 `vue`。
- 0.15 分：指出 `sort` 被对象 setter 整体替换掉；给出基于 `new URLSearchParams(prev)` 的复制式修复。
- 0.1 分：指出 `q` 与 `draft` 两个状态源，以及为什么草稿不会被同步。

### 简短解释

`useSearchParams` 的 setter 本质是一次导航；search 变化会重新执行 loader，但同路由组件不会重新挂载。对象形式替换整个查询串，函数形式才能基于旧值增量修改。本地草稿与 URL 并存时，必须明确谁是唯一真相。

## 第 1 题（2.5 分｜状态归属与服务端数据）

### 参考答案

#### 1. 状态归属

| 项 | 归属 | 理由 / 取舍 |
|---|---|---|
| 1. 尚未提交的搜索文本 | **local** | 只属于当前输入组件，未提交前不分享、不参与取数；提交后才写入 URL。若产品要求“边输入边搜索且可分享”，也可以直接放 URL，但要防抖并接受历史记录/请求频率成本。 |
| 2. 已提交的 `status`、`page` | **URL** | 需要刷新保留、可分享、可前进后退；loader 或 Query key 从 search params 读取。不要同时再存一份到 Zustand。 |
| 3. 任务列表、`isPending`、`error` | **server** | 属于 TanStack Query 的缓存与请求状态，用 `queryKey: ['tasks', status, page]` 管理；不是 Zustand 的全局客户端状态。 |
| 4. `theme` | **global（Zustand）** | 全站共享、跨路由、刷新保留；用 `persist` 的 `partialize` 只持久化这个字段。也可以放 cookie/localStorage，但不必放进 Query 或 URL。 |
| 5. 侧边栏折叠 | **global（Zustand）** | 多个页面/布局共享，但刷新不要求保留，所以只放内存；如果只有一个布局消费，也可以提升到该布局的 local state。 |
| 6. 卡片标题编辑草稿 | **local** | 只在该卡片的编辑态存在，取消即丢弃；提交时才调用 mutation。不要放全局，也不要持久化。 |
| 7. “新建任务”对话框是否打开 | **local（提升到最近公共父级）**，或 **global UI store** | 两个按钮在不同位置，状态应放在它们最近的公共父级；如果触发点非常分散、跨路由，可以用 Zustand 的 UI slice。除非希望对话框可深链，否则不放 URL；它不是服务端数据。 |
| 8. 拖拽中的临时坐标/占位 | **local / ref**（高频时用瞬态订阅） | 高频、短暂、不需要持久化；拖拽结束把最终顺序通过 mutation 提交给服务端。若多个组件要读，用 `store.subscribe` 做瞬态更新，而不是让每次 mousemove 触发全局渲染。 |

#### 2. 双写的问题

`tasks` 有两份来源：TanStack Query 的缓存（`data`）和 Zustand 的 `tasks`。Effect 会在 `data` 变化时执行，包括首次成功、后台 refetch 成功、缓存被手动更新、以及某些重试成功之后。

至少三个问题：

- **两份真相**：UI 读的是 store，Query 里的 `data`、`isPending`、`error` 和 store 可能不同步；刷新、失效或 mutation 后，一边更新了另一边没更新。
- **旧数据覆盖新数据**：翻页或切换筛选时，旧请求/旧 `data` 可能在新结果之后写入 store，造成“URL 是 done，列表还是 all”的竞态或短暂错配。
- **加载/错误状态丢失**：Query 正在 refetch 或失败时，store 仍保留上一次成功的数据，组件可能把旧数据当成当前结果展示；`error` 也无法反映到 store。
- **mutation 失效不同步**：删除/新增任务后通常只 `invalidateQueries`，Query 会重新取数，但 store 要等 Effect 再写一次；这中间读 store 的组件看到旧列表。若组件在 Effect 之外读 store，过期时间更长。
- **持久化污染**：如果 store 还配置了 `persist` 并包含 `tasks`，刷新后会先水合旧任务，删除的任务可能“复活”，甚至把上一个账号的数据带给下一个账号。

如果 `status` 从 `all` 切到 `done`：URL 变成 `?status=done&page=1`（或保留当前 page），Query key 变化并开始取新数据。在 v5 默认没有 `placeholderData` 时，新 key 的 `data` 在成功前是 `undefined`，但 store 里的 `tasks` 仍是 all 的旧数据。这个组件在 `isPending` 时返回 `<Spinner />`，所以当前页面会显示加载态；但其他直接读 store 的组件仍会看到旧列表。如果使用了 `placeholderData: keepPreviousData`，列表还会短暂显示上一筛选的结果，与 URL 不一致。

#### 3. 正确分工

- **TanStack Query 拥有服务端数据**：任务列表、加载态、错误、重试、缓存失效都归 Query。组件直接渲染 `data`，需要派生列表时用 `select` 或 `useMemo`，不要复制进全局 store。
- **Zustand 只放客户端全局状态**：主题、侧边栏、跨路由的 UI 开关、拖拽等。已提交的筛选条件放 URL；输入草稿放 local；服务端数据放 Query。
- **mutation 后更新列表**：用 `useMutation`，在 `onSuccess` 里 `queryClient.invalidateQueries({ queryKey: ['tasks'] })`；需要即时反馈时用 Query 的乐观更新（`onMutate` 取消在途查询、写入缓存、`onError` 回滚），或 React 的 `useOptimistic`。不要手动往 Zustand 再写一份。
- **多个远距离组件共享任务列表**：共享同一个 `QueryClient` 和同一个 query key（或封装一个 `useTasks` hook），而不是把数据复制进 Zustand。若确实需要跨组件的客户端状态，才用 Zustand。

### 评分点（共 2.5 分）

- 1.2 分：8 项归属基本正确，每项 0.15 分；分类正确但理由含糊可给一半。第 1、7 项允许合理的第二种选择，只要说明取舍。
- 0.8 分：指出至少三个双写问题（两份真相、旧数据覆盖/竞态、加载或错误状态丢失、失效不同步、持久化污染）；能说明 `status` 切换时 store 仍保留旧数据。
- 0.5 分：给出正确分工（Query 管服务端数据、Zustand 管客户端全局、URL 管可分享筛选、local 管草稿），并说明 mutation 用失效或乐观更新而不是双写；多组件共享 query key/QueryClient。

### 简短解释

状态归属的核心是“谁拥有这份数据的生命周期”。服务端数据的生命周期由请求和缓存决定，交给 Query；可分享、可后退的筛选条件交给 URL；只影响一个组件交互的交给 local；跨路由且与服务器无关的客户端状态才交给 Zustand。把 Query 数据复制进 store 会制造第二个生命周期，之后所有失效、竞态和持久化问题都要手动补齐。

## 第 2 题（3 分｜selector、useShallow 与不可变 actions）

### 参考答案

#### 1. 挂载时的快照与警告

`TaskList` 首次挂载后，控制台可能立即出现：

```text
The result of getSnapshot should be cached to avoid an infinite loop
```

最坏情况是 React 反复检测到快照变化，继续强制重渲染，最终抛出：

```text
Maximum update depth exceeded
```

原因是三个订阅的返回形状不同：

- `useTaskStore((s) => ({ tasks: s.tasks, filter: s.filter }))`：每次调用 selector 都创建一个**新对象**。v5 默认用 `Object.is` 比较，新旧对象永远不相等，`useSyncExternalStore` 的 `getSnapshot` 不稳定，挂载阶段就可能进入循环。
- `useTaskStore((s) => s.filter === 'all' ? s.tasks : s.tasks.filter(...))`：`filter === 'all'` 时返回 `s.tasks` 原引用，暂时稳定；一旦 `filter` 切成 `'open'` 或 `'done'`，每次调用都 `filter` 出一个**新数组**，同样是不稳定快照，会触发警告/循环。
- `useTaskStore((s) => s.doneCount)`：返回数字，`Object.is` 可稳定比较；只有 `doneCount` 真正变化时才会触发该订阅的更新。

注意：虽然三个 Hook 中只有前两个不稳定，但它们在同一个组件里，任何一个导致的重渲染都会让整个 `TaskList` 重渲染。

#### 2. 切换主题时是否重渲染

只调用 `toggleTheme()` 时，原始代码会重渲染：store 更新后，第一个 selector 又返回一个新对象，`Object.is` 判定变化，组件重渲染。`visible` 在 `filter === 'all'` 时返回同一个 `s.tasks` 引用，`doneCount` 也没变，但第一个订阅已经足够触发重渲染。

修复 selector 后（分开订阅或用 `useShallow`），`theme` 变化不会让 `TaskList` 重渲染：`tasks`、`filter`、`doneCount` 都没有变化，三个快照都与上一次相等。`DoneBadge` 也不会因为主题变化而重渲染。

#### 3. 原地修改与 useShallow

下面讨论点击行为时，假设第一个对象 selector 已经用 `useShallow` 或拆分 selector 修好；否则组件会在挂载阶段就进入上面的无限重渲染，根本到不了点击。

点击复选框后：

- `toggle` 里 `task.done = !task.done` 确实修改了**原 task 对象**；
- `tasks` 数组本身没有换引用，`set({ tasks: get().tasks })` 传的是同一个数组；
- 因此 `s.tasks` 的 `Object.is` 结果不变。

如果列表子组件只订阅 `const tasks = useTaskStore((s) => s.tasks)`，store 虽然通知了订阅者，但 selector 返回同一个数组引用，React 不会重渲染，界面会停留在旧内容。`DoneBadge` 因为 `doneCount` 的数字变了可能重渲染，但它不会让 `TaskList` 的 `visible.map` 重新执行。

`useShallow` 也补救不了原地修改：

- 如果 `visible` 在 `filter === 'all'` 时返回 `s.tasks`，`useShallow` 首先看到同一个数组引用，直接返回旧值；
- 如果 `filter` 是 `'open'`/`'done'`，`useShallow` 会逐项比较数组元素。原地修改后数组长度相同、每个元素的引用也相同，shallow 比较仍判定相等，返回上一次的数组快照，列表依旧不更新。

`useShallow` 只能比较“引用/顶层值”，看不到对象内部字段的变化。要让它和普通 selector 正确工作，action 必须返回新的数组和新的 task 对象。

#### 4. doneCount 与 clearCompleted

`clearCompleted` 只执行了 `set({ tasks: get().tasks.filter((t) => !t.done) })`，没有同步 `doneCount`。如果之前有 3 个已完成任务，清除后 `doneCount` 仍是 3，`DoneBadge` 会显示错误数量。任何“可以从 tasks 推导出来的值”都不应该在 store 里单独维护，否则每个 action 都要记得同步，迟早漂移。

应该派生：

```tsx
const doneCount = useTaskStore((s) => s.tasks.filter((t) => t.done).length)
```

这是一个数字，selector 结果稳定，只有数量真正变化时才重渲染。也可以在组件里从 `tasks` 用 `useMemo` 计算；不要在 store 里存 `doneCount` 字段。注意派生 selector 每次 store 更新都会 `filter` 一遍，任务很多时可在组件里 `useMemo` 或使用记忆化的派生函数。

#### 5. 不可变 actions 与 selector 修复

不可变 action：

```tsx
toggle: (id) =>
  set((state) => ({
    tasks: state.tasks.map((t) =>
      t.id === id ? { ...t, done: !t.done } : t
    ),
  })),

add: (title) =>
  set((state) => ({
    tasks: [
      ...state.tasks,
      { id: crypto.randomUUID(), title, done: false },
    ],
  })),

clearCompleted: () =>
  set((state) => ({
    tasks: state.tasks.filter((t) => !t.done),
  })),
```

同时从 state 类型和初始值中删掉 `doneCount`。`crypto.randomUUID()` 在 action 中生成是可以的；action 是事件处理逻辑，不是 reducer。若把这段逻辑改写成 reducer，随机 ID 应在 dispatch 前生成并放进 action，保持 reducer 纯。

selector 修复方案一：拆成独立 selector，并在组件里派生：

```tsx
import { useMemo } from 'react'

function TaskList() {
  const tasks = useTaskStore((s) => s.tasks)
  const filter = useTaskStore((s) => s.filter)
  const doneCount = useTaskStore(
    (s) => s.tasks.filter((t) => t.done).length
  )

  const visible = useMemo(
    () =>
      filter === 'all'
        ? tasks
        : tasks.filter((t) => (filter === 'done') === t.done),
    [tasks, filter]
  )

  // ...
}
```

每个 selector 都返回原引用或原始值，`useMemo` 只在 `tasks`/`filter` 变化时重新过滤。主题变化不会重渲染；不可变地 toggle/add/clear 后 `tasks` 换引用，列表才更新。

selector 修复方案二：用 `useShallow` 选择多个切片，并让派生 selector 也使用 `useShallow`：

```tsx
import { useShallow } from 'zustand/react/shallow'

function TaskList() {
  const { tasks, filter } = useTaskStore(
    useShallow((s) => ({ tasks: s.tasks, filter: s.filter }))
  )

  const visible = useTaskStore(
    useShallow((s) =>
      s.filter === 'all'
        ? s.tasks
        : s.tasks.filter((t) => (s.filter === 'done') === t.done)
    )
  )

  const doneCount = useTaskStore(
    (s) => s.tasks.filter((t) => t.done).length
  )

  // ...
}
```

`useShallow` 仍要求不可变更新：如果 action 原地改 task，元素引用不变，shallow 比较会误判“没变化”。此外不要把 `useShallow` 放在条件分支里，它是 Hook。

方案三（更少用）：用 `zustand/traditional` 的 `createWithEqualityFn` 提供自定义相等函数。v5 主入口已不再导出它，且该入口依赖可选的 peer `use-sync-external-store`；一般优先用 `useShallow` 或拆分 selector。

### 评分点（共 3 分）

- 1 分：指出对象 selector 每次返回新对象、数组 selector 在非 `all` 时每次返回新数组；能说出 `getSnapshot` 警告和 `Maximum update depth exceeded`；能判断主题变化在原始代码中会重渲染、修复后不会。
- 1 分：指出 `toggle`/`add` 原地修改，`tasks` 数组和 task 对象引用不变；说明只订阅 `s.tasks` 或使用 `useShallow` 时界面可能不更新；给出不可变的 `map`/展开/`filter` 写法。
- 0.5 分：指出 `doneCount` 是派生值，`clearCompleted` 后不同步；给出 selector 派生或 `useMemo` 派生，并说明应删除该 state 字段。
- 0.5 分：给出至少两种 selector 修复（拆分 selector + `useMemo`；`useShallow`），并正确说明 `useShallow` 不能感知原地修改。

### 简短解释

Zustand v5 的 selector 返回值就是 `useSyncExternalStore` 的快照，默认比较是 `Object.is`。selector 里创建新对象/新数组，会让快照永远“变化”；`useShallow` 通过缓存上一次结果解决这个问题，但它只比较顶层值和引用。不可变更新是 `useShallow` 正确工作的前提：只有新数组、新对象才能让引用比较看到变化。派生值不要存 state，避免多个 action 手动同步。

## 第 3 题（2.5 分｜persist、partialize 与瞬态更新）

### 参考答案

#### 1. localStorage 内容与 partialize

`persist` 写入的值大致是：

```json
{
  "state": {
    "theme": "light",
    "sidebarOpen": true,
    "tasks": [],
    "draft": ""
  },
  "version": 0
}
```

当前 `partialize` 只返回 `theme`、`sidebarOpen`、`tasks`、`draft` 四个字段，所以 `cursorX` 不在存储里。`setTheme`、`setCursorX` 也不会出现：它们没有被 `partialize` 选中；即使 `partialize` 返回整个 state，`JSON.stringify` 也会丢弃函数，动作不会以可调用函数的形式恢复，恢复后仍使用当前初始 state 里的 action。

问题：

- **持久化 `tasks`**：把服务端数据复制到了 localStorage。刷新后会先水合旧任务，可能看到过期列表、已删除任务“复活”、上一账号的数据泄漏给下一账号；Query 重新取数后两份数据还会短暂不一致。
- **持久化 `draft`**：未提交的编辑草稿会跨会话复活，用户下次打开看到上次残留内容，也可能涉及隐私；草稿通常只应存在于当前编辑组件，最多放 `sessionStorage`。
- 应该持久化的是纯客户端、跨会话仍有意义的偏好，例如 `theme`、`sidebarOpen`；服务端数据、加载/错误状态、草稿、动作、瞬态坐标都不应持久化。

#### 2. 水合与合并语义

`persist` 在 store 创建时（同步 localStorage）读取存储并水合。默认 `merge` 是浅合并：

```ts
merge: (persistedState, currentState) => ({
  ...currentState,
  ...persistedState,
})
```

- 存储里 `theme: 'dark'`、初始 `theme: 'light'`，最终是 `'dark'`，持久化值覆盖初始值。
- 以后新增 `fontSize`，旧存储没有这个 key，浅合并不会覆盖它，所以保留当前初始 state 的 `fontSize` 默认值。
- 如果 `partialize` 返回整个 state：所有可序列化字段（包括 `cursorX`、`tasks`、`draft`）都会被存储；函数被 JSON 丢弃；旧版本残留字段会在水合时覆盖同名当前默认值。升级 schema 时可能注入不兼容字段。
- 对破坏性变更，应提升 `version` 并提供 `migrate`；如果版本不匹配又没有 `migrate`，persist 会打印错误并忽略旧存储。SSR 场景可用 `skipHydration` 后在客户端显式 `persist.rehydrate()`。

#### 3. CursorTracker 与瞬态更新

当前 `CursorTracker` 每次 `mousemove` 都调用 `setCursorX`，store 通知订阅者；组件用 `useBoardStore((s) => s.cursorX)` 订阅，`cursorX` 每次都变，于是每个鼠标事件都触发一次 React 重渲染。鼠标移动频率很高，这会造成大量无意义的 render。

改成瞬态更新，只写 DOM，不触发 React render：

```tsx
function CursorTracker() {
  const cursorRef = useRef<HTMLDivElement>(null)

  useEffect(() => {
    return useBoardStore.subscribe((state, prevState) => {
      if (state.cursorX === prevState.cursorX) return
      if (cursorRef.current) {
        cursorRef.current.style.transform = `translateX(${state.cursorX}px)`
      }
    })
  }, [])

  return <div ref={cursorRef} className="cursor" />
}
```

- `subscribe` 的回调直接接收当前的 `state` 和 `prevState`，不依赖组件 render 时的闭包，所以不会读到过期的 `cursorX`。
- Effect 返回 `subscribe` 的取消订阅函数；组件卸载或 Effect 重新执行时会清理，避免重复订阅和泄漏。
- v5 的 `subscribe` 没有 selector 参数；可以在回调里自己比较 `state.cursorX !== prevState.cursorX`。需要 selector 时可用 `subscribeWithSelector` middleware。
- 适合瞬态更新的场景：高频、只需要写 DOM/外部系统、不需要参与 React 渲染的值，例如鼠标坐标、滚动进度、拖拽幽灵位置。需要在 UI 中渲染、参与布局或需要 Suspense/派生计算的值，仍应使用普通 selector，让 React 正常重渲染。
- 注意：瞬态更新只避免 React render，store 仍然会在每次 `set` 时通知所有订阅者；如果订阅者很多，考虑把这类高频值移出全局 store，或做节流/`requestAnimationFrame` 合并。

#### 4. 服务端数据、登出与会话存储

如果 `tasks` 同时由 TanStack Query 管理：

- **刷新后**：persist 会先水合 localStorage 里的旧 `tasks`，而 Query 会重新请求。读 store 的 UI 可能先显示旧列表，甚至显示已删除的任务；Query 成功后又出现一份新列表，两份数据不一致。
- **登出换账号后**：localStorage 不会自动清空。下一个用户可能看到上一个用户的任务，属于数据泄漏；即使 Query 重新取数，水合阶段和请求失败时都可能暴露旧数据。
- 修复：
  - `partialize` 排除服务端数据和草稿：

    ```tsx
    partialize: (state) => ({
      theme: state.theme,
      sidebarOpen: state.sidebarOpen,
    })
    ```

  - 登出时同时清理持久化存储与 Query 缓存，并重置内存中的 store：

    ```tsx
    useBoardStore.persist.clearStorage()
    queryClient.clear() // 或 removeQueries({ queryKey: ['tasks'] })
    useBoardStore.setState({ tasks: [], draft: '' })
    ```

  - 用 `version` + `migrate` 处理 schema 变更；SSR 用 `skipHydration` 避免服务端/客户端水合不一致。
  - 根本上不要让服务端数据进入持久化 store：Query 是服务端数据的唯一所有者。

如果只想让 `sidebarOpen` 在当前标签页会话内保留，关闭标签页即丢弃，把默认 localStorage 换成 `sessionStorage`：

```tsx
import { createJSONStorage, persist } from 'zustand/middleware'

// ...
{
  name: 'kanban-board',
  storage: createJSONStorage(() => sessionStorage),
  partialize: (state) => ({ sidebarOpen: state.sidebarOpen }),
}
```

`sessionStorage` 按标签页隔离，关闭标签页后清除。SSR 环境下 `createJSONStorage` 捕获不可用的 storage 并返回 `undefined`，persist 会警告并跳过水合；此时应配合 `skipHydration` 在客户端显式水合。

### 评分点（共 2.5 分）

- 0.8 分：写出 `{ state, version }` 结构；正确列出 `partialize` 的四个字段并指出 `cursorX`/actions 不在其中；说明 `tasks` 与 `draft` 持久化的问题。
- 0.6 分：正确说明默认浅合并、持久化值覆盖初始值、新增字段保留默认值；能提到 `partialize` 返回整个 state 的后果及 `version`/`migrate`。
- 0.6 分：给出 `store.subscribe` 的瞬态更新实现与 cleanup；说明回调收到最新 `state` 所以无过期闭包；能区分瞬态更新与普通 selector 的适用场景。
- 0.5 分：指出持久化服务端数据的刷新/换账号风险；给出 `partialize` 排除、登出 `clearStorage` + `queryClient.clear()` 等修复；能写出 `createJSONStorage(() => sessionStorage)`。

### 简短解释

persist 只负责“把选中的 state 序列化到 storage，并在启动时浅合并回来”，它不判断数据属于客户端还是服务端。把 Query 的数据也放进去，就有了第二个缓存和第二个生命周期；因此 `partialize` 应只保留纯客户端偏好。高频瞬态值则相反：它们需要更新，但不需要 React render，用 `subscribe` 直接写 DOM 比让每次 `set` 触发组件树更合适。
