## 复习 1（0.5 分｜render 纯度与 StrictMode 双调用）

### 参考答案

`items.reverse()` 不是返回新数组，而是**原地反转**传入的 props 数组。它返回的仍是同一个数组引用。

**开发环境为什么看起来没变：** StrictMode 会在开发环境把组件的 render 函数调用两次。第一次 `reverse()` 把数组变成 `['周三', '周二', '周一']`；第二次又在同一个已被修改的数组上 `reverse()`，变回 `['周一', '周二', '周三']`。React 采用第二次的结果提交，所以屏幕看起来没变。但两次调用都发生了真实的 mutation，只是相互抵消了；StrictMode 恰好掩盖了这个 bug。

**上线后为什么每次刷新都翻转：** 生产环境每次点击只 render 一次，`reverse()` 把父组件 state 中的同一个数组原地反转一次；下一次点击再反转一次，所以顺序在“正序/倒序”之间来回翻转。父组件的数组本身也已经被 Feed 改掉了，其他读取该数组的组件会看到被反转后的数据。

**正确写法：**

```tsx
const newestFirst = items.toReversed()      // ES2023
// 或
const newestFirst = [...items].reverse()    // 先复制再反转
```

**违反的规则：** render 必须是纯函数，不能修改 props、state 或 render 之前就存在的对象。并发渲染下更危险，因为 render 可能执行多次、被中断后重试、在后台重渲染，或被 Activity 预渲染；mutation 会跨这些渲染尝试泄漏，使结果取决于 render 执行了几次、哪一次被提交，而不是只取决于当前的 props/state。

### 评分点（共 0.5 分）

- 0.25 分：正确解释开发环境（两次 reverse 相互抵消）和生产环境（每次点击反转一次、且修改了共享数组）两个现象。
- 0.25 分：给出 `toReversed()` 或复制后 `reverse()` 的正确写法，并指出 render 必须纯、并发渲染下多次/可中断的 render 会让 mutation 泄漏。

### 简短解释

render 是“根据当前输入算出 UI”，不是“修改输入”。任何原地修改都会让后续渲染看到被污染的数据；StrictMode 的双调用只是让这个 bug 在开发环境里碰巧看起来正常。

## 复习 2（0.5 分｜key 与 state 重置）

### 参考答案

**1. 草稿为什么保留：** 从 Ada 切到 Grace 时，`Chat` 在树中的位置没变、组件类型没变、key 也没变（没有显式 key 时 React 用位置作为隐式 key）。React 认为这还是同一个 `Chat` 实例，只更新 `recipient` prop，因此 `useState` 的草稿被保留。

**让每位收件人得到空白草稿：** 用收件人的稳定身份作为 key：

```tsx
<Chat key={recipient.id} recipient={recipient} />
```

key 变化时，React 把旧的 `Chat` 卸载，销毁它的 state 和 DOM，再挂载一个新的 `Chat`，草稿回到初始值。

**2. 为什么不能写 `key={Math.random()}`：**

- 每次 `Messenger` 重新渲染都会生成新的 key，React 会认为 `Chat` 是一个全新的组件：卸载旧的、挂载新的。
- 草稿、焦点、滚动位置、输入框 DOM 状态全部丢失；Effects 会先 cleanup 再重新 setup。
- 即使收件人没变，父组件的任何一次重渲染都会把 `Chat` 重建，造成不必要的性能开销和状态丢失。
- StrictMode 下 render 会执行多次，随机 key 会让同一棵树在不同次 render 之间不断换身份，问题更明显。

key 必须是**稳定的身份标识**，不是随机值，也不是每次 render 都会变化的派生值。

### 评分点（共 0.5 分）

- 0.25 分：说明位置/类型/key 相同导致 React 复用 `Chat`、保留 state；给出 `key={recipient.id}` 的修法。
- 0.25 分：说明随机 key 每次 render 都让组件重新挂载，至少说出两个后果（草稿/焦点/DOM 状态丢失、Effects 重新执行、性能浪费等）。

### 简短解释

key 是 React 判断“这是不是同一个组件实例”的身份。key 不变，state 就跟着实例走；key 一变，旧实例连同 state、DOM 和 Effects 一起被销毁，新的实例从头开始。

## 第 1 题（3 分｜transition、isPending 与输入框）

### 参考答案

#### 1. `handleChange` 的问题与两种修法

**问题有两个：**

1. `startTransition` 把 `setQuery` 和 `setResults` 都标记成了非紧急更新。但 `query` 是受控输入框的 `value`，输入框必须在 change 事件中同步反映用户刚输入的内容。受控输入的状态更新被放进 transition 后，输入框的 DOM 值可能被恢复成旧的 state，表现为字符丢失、输入滞后或光标跳动；React 文档明确说 **Transition updates can’t be used to control text inputs**。所以快速输入 `abc` 时，输入框不能可靠地显示 `abc`。
2. `startTransition` 的回调是**立即同步执行**的，它只把回调期间调度的 state 更新标记为非紧急，并不会把回调里的慢函数延后。所以 `search(e.target.value)` 仍然在事件处理函数里同步执行，直接阻塞这次输入。即使把 `setQuery` 移出 transition，这一行仍会造成卡顿。

**修法 A：保留 `useTransition`，输入 state 紧急更新，昂贵计算放进 transition 触发的渲染。**

```tsx
const [query, setQuery] = useState('')
const [transitionQuery, setTransitionQuery] = useState('')
const [isPending, startTransition] = useTransition()

function handleChange(e: ChangeEvent<HTMLInputElement>) {
  const value = e.target.value
  setQuery(value) // 紧急：输入框同步更新
  startTransition(() => {
    setTransitionQuery(value) // 非紧急：触发结果区的后台渲染
  })
}

const results = useMemo(
  () => search(transitionQuery),
  [transitionQuery]
)
```

紧急 render 时 `transitionQuery` 没变，`useMemo` 复用旧结果，不会执行慢查询；transition render 用新的 `transitionQuery` 在后台执行 `search`。这里 `query` 的更新是紧急的，`transitionQuery` 的更新是非紧急的。也可以把 `transitionQuery` 传给一个 `memo` 结果组件，让它在自己的 render 里计算。

**修法 B：用 `useDeferredValue`。**

```tsx
const deferredQuery = useDeferredValue(query)

function handleChange(e: ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value) // 紧急
}

<ResultList query={deferredQuery} /> // 后台/非紧急渲染
```

`query` 仍然同步更新，输入框立即显示最新值；`deferredQuery` 会“落后”于 `query`，React 先用旧值完成一次紧急渲染，再在后台用新值渲染结果区。把 `search` 放进读取 `deferredQuery` 的结果组件（或基于 `deferredQuery` 的 `useMemo`）里，而不是放进 `handleChange`。这里 `query` 的更新是紧急的，`deferredQuery` 驱动的结果渲染是非紧急/后台的。`useDeferredValue` 没有 `isPending`，通常用 `query !== deferredQuery` 表示结果是否过期。

#### 2. `isPending` 的时序与后台渲染

把 `setQuery` 移出 transition 后：

- `isPending` 在**第一次调用 `startTransition` 时变为 `true`**，并一直保持到这次 transition 的所有 Action 完成、最终 state 已经显示给用户为止。
- 用户继续输入时，输入框的紧急更新会先被处理；正在进行的 results 后台渲染会被**中断并重新开始**，React 用最新的 state 重新渲染 transition。
- `isPending` **不会因为又按了一次键就变回 `false`**；它仍然表示“还有 transition 工作未完成”。等最新的 results 提交后，它才变回 `false`。
- 输入框不会被阻塞：紧急更新优先于后台渲染，所以打字保持响应。但 transition 不是多线程；如果 `search` 是一个无法拆分的超长同步调用，它仍可能占用主线程，必要时把计算拆分或移到 Worker。
- 补充：如果同时有多个 transition，React 目前会把它们批在一起，`isPending` 要等所有相关 Action 完成才变回 `false`。

#### 3. `await` 之后的 `setResults`

**不再是 transition 更新。** `startTransition` 只把在 action 函数**同步执行期间**发生的 state 更新标记为 Transition。遇到 `await` 后，JavaScript 的异步上下文让 React 丢失了 transition 作用域，`await` 之后的 `setResults` 会按普通（紧急）更新处理。React 文档把这称为当前的一个已知限制。

具体风险：

- 更新不再是低优先级的，可能阻塞输入或其他交互，失去 transition 的意义。
- `isPending` 与这次更新不再对应，加载指示可能不准确。
- 连续点击“加载更多”时，多个请求可能乱序返回，旧响应覆盖新结果。
- 异步 action 抛错或返回 rejected Promise 时，要由包裹该组件的 Error Boundary 来显示错误 UI；不要让 rejection 变成无人处理的异常。

改写：在 `await` 之后再用一层 `startTransition` 包住 state 更新：

```tsx
async function handleLoadMore() {
  startTransition(async () => {
    const next = await fetchNextPage(query)
    startTransition(() => {
      setResults(prev => [...prev, ...next])
    })
  })
}
```

如果请求可能乱序，还应用请求 id、`AbortController` 或数据请求库来丢弃过期响应；不要只依赖 transition 解决竞态。

#### 4. transition 与 Suspense/key

- **不加 key：** Suspense 边界还是同一个，且已经显示过内容。transition 更新让 `ResultsByQuery` 挂起时，React 会保留已经显示的旧内容（`a` 的结果），不会显示 `Spinner`；`isPending` 为 `true`。等 `b` 的数据就绪后再切换。
- **加 `key={query}`：** key 变化让 React 把 Suspense 边界当成一个**新的边界身份**。新边界没有“已经显示过的内容”需要保护，而 transition 只承诺“不隐藏已经显示的内容”，并不承诺新边界不显示 fallback。因此新边界挂起时会显示 `Spinner`，旧内容被移除，等 `b` 就绪后显示新结果。

选择原则：刷新同一个视图、希望保留旧内容时不要加 key；切换到另一个实体、旧内容会误导用户时，把 key 加在 Suspense 边界（或上层）上，明确表示“这是一个新的内容身份”。如果外层还有已经显示的 Suspense 边界，它是否保留旧内容取决于外层边界的位置；但最近的新边界仍会显示自己的 fallback。

### 评分点（共 3 分）

- 1 分：指出受控输入不能使用 transition，并指出 `startTransition` 回调同步执行、慢 `search` 仍会阻塞输入；给出两种可行修法；能说明各自哪些更新紧急、哪些非紧急。
- 0.75 分：`isPending` 从第一次 `startTransition` 到最终 state 显示期间为 `true`；新按键会中断并重启后台渲染，但不会让输入阻塞，也不会让 `isPending` 单纯因按键变 `false`。
- 0.75 分：指出 `await` 之后的 `setResults` 不是 transition，说明风险，并用嵌套 `startTransition` 改写。
- 0.5 分：正确区分加 key 与不加 key 时 Suspense 的 fallback/旧内容行为，并说明原因。

### 简短解释

transition 的“非紧急”只适用于它同步作用域内调度的更新；受控输入和 `await` 之后的更新都不在这个作用域里。`isPending` 跟踪的是 transition 何时真正完成，不是“用户是否又输入了”。Suspense 的 key 决定边界身份：同一个边界可以保留旧内容，新边界没有旧内容可保留。

## 第 2 题（2.5 分｜useDeferredValue 的旧值与后台渲染）

### 参考答案

#### 1. 从输入 `a` 到输入 `b` 的渲染过程

假设上一次已提交的值是 `text = ''`、`deferredText = ''`。

1. 输入 `a`：React 先做一次**紧急 render**，此时 `text = 'a'`，`deferredText` 仍是上一次已提交的旧值 `''`。输入框立即显示 `a`；`SlowList` 收到的还是 `''`（旧值）。
2. 这次紧急 render 完成后，React 立即在后台用 `deferredText = 'a'` 再渲染一次。后台渲染是可中断的；如果它完成并提交，列表更新为 `a` 的结果，`text !== deferredText` 变为 `false`。
3. 如果用户在后台渲染完成前又输入 `b`：React 先处理紧急更新，得到 `text = 'b'`；`deferredText` 仍是上一次已提交的值（可能还是 `''`，也可能已经是 `'a'`，取决于后台是否已提交）。React 会**放弃/中断**正在进行的 `a` 后台渲染，用最新的 `b` 重新开始后台渲染。中间态 `a` 可能根本不会显示，最终显示 `b`。
4. `text !== deferredText` 表示“当前显示的结果落后于输入”，常用来做变暗或“更新中…”提示。它只是两个已提交值的比较，不是 transition 的 `isPending`。

`useDeferredValue` 本身没有固定延迟：紧急 render 一结束，React 就尽快开始后台 render；设备越慢，落后越明显。

#### 2. 没有 `memo` 时为什么不能保持流畅

当前 `SlowList` 是普通组件。紧急 render 时，`App` 重新渲染，`SlowList` 收到的是旧的 `deferredText`，但它**没有 `memo`**，所以 React 仍会在这次紧急 render 中重新渲染它，2000 个条目的昂贵计算仍然同步发生，输入依旧会卡。之后后台 render 还会再用新值做一次昂贵计算。

`useDeferredValue` 不会让 `SlowList` 本身变快；它只是让 React 有机会把“用新值渲染 SlowList”放到后台。要利用这一点，`SlowList` 必须在 props 不变时能跳过渲染：

```tsx
const SlowList = memo(function SlowList({ text }: { text: string }) {
  // ...
})
```

这样紧急 render 中 `deferredText` 没变，`memo` 让 `SlowList` 跳过；后台 render 用新值时才真正做昂贵计算。这也说明 `useDeferredValue` 的适用边界：它适合“慢组件能够因 props 相同而跳过渲染”的场景。前提是这段计算能被 React 拆分到多个工作单元；一个巨大的同步函数本身仍会占住主线程。

- 如果 `SlowList` 内部直接读取 `text` 而不是 `deferredText`，它在紧急 render 中总是拿到最新值，昂贵渲染仍然同步发生，defer 对这部分 UI 没有效果。
- 如果写成 `useDeferredValue({ q: text })`，每次 render 都创建一个新对象，`Object.is` 比较总是不同，React 会不断安排不必要的后台渲染。传给 `useDeferredValue` 的应该是原始值，或 render 之外创建的稳定对象。
- 如果更新本身已经在 transition 中，`useDeferredValue` 会直接返回新值，不会再额外产生一次 deferred render，因为更新已经是非紧急的。

#### 3. Suspense、网络请求与适用边界

**后台 render 挂起时：** 用户看到的是**旧列表**，不是 `Spinner`。`useDeferredValue` 与 Suspense 集成：后台更新挂起时，React 会保留旧的 deferred 值，等数据就绪后再显示新结果。只有紧急更新或新挂载的边界才更可能立即显示 fallback。

**不会减少网络请求。** 每个按键仍可能发起一次请求；`useDeferredValue` 延迟的是“显示新结果”，不是请求本身。响应可能被缓存，所以按 Backspace 可能立即显示旧结果、不重新请求。

**与 debounce/throttle 的区别：**

- debounce 等待用户停止输入一段固定时间；throttle 限制固定时间内的执行次数。两者都是时间驱动的。
- `useDeferredValue` 没有固定延迟，紧急 render 一结束就尽快开始后台 render；新输入会中断并重启后台 render，而且会根据设备快慢自适应。它优化的是**渲染优先级**，不是请求频率。
- 如果需要减少请求，应该用 debounce、缓存或请求库；`useDeferredValue` 不能替代它们。

**不适合用的情况：**

- 需要真正延迟/合并网络请求时（用 debounce 或缓存）。
- 慢组件无法跳过渲染（没有 `memo`），或组件内部直接读取实时值，defer 不会带来收益。
- 传入的值每次 render 都是新对象，导致无意义的后台渲染。
- 更新本身已经在 transition 中，`useDeferredValue` 不会额外 defer。
- 必须同步显示最新值的受控输入 state（输入框本身要保持紧急更新；可以 defer 由它派生的结果区）。
- 你希望“新结果准备好之前完全不请求”，这不是 `useDeferredValue` 的职责。

### 评分点（共 2.5 分）

- 1 分：正确描述紧急 render 用旧 deferred 值、后台 render 用新值、后台渲染可被新输入中断并重启；能说明 `text !== deferredText` 的含义。
- 0.75 分：指出没有 `memo` 时紧急 render 仍会重渲染慢组件；给出 `memo` 修法；正确解释直接读 `text` 和每次新建对象两种反例。
- 0.75 分：说明后台挂起时保留旧内容而不是 fallback；不减少网络请求；与 debounce/throttle 的区别；至少说出两个适用边界。

### 简短解释

`useDeferredValue` 做的是“同一份 UI，先用旧值渲染一次，再在后台追上新值”，不是延迟请求，也不是让组件变快。它把“慢”从紧急渲染中挪走的前提是：慢组件能在旧 props 下跳过渲染（`memo`），并且新值的后台渲染可以被下一次输入打断。

## 第 3 题（2.5 分｜Activity 的隐藏、恢复与副作用）

### 参考答案

#### 1. 首次渲染：hidden Activity 的预渲染

首次 `tab = 'home'`，但 `Video` 的 Activity 是 `hidden`：

- `Video` 的**子树仍会被 render**，只是以比可见内容更低的优先级进行预渲染。
- 它的宿主 DOM 会被创建并以 `display: "none"` 隐藏（只返回纯文本的子树例外，见第 4 问）。
- `Video` 的 **Effects 不会挂载**。`Home` 是可见的，它的 Effects 会在 commit 后执行（打印 `subscribe`）。
- 如果 `Video` 用 `use()` 读取一个按组件缓存的 `fetchVideo()` promise：预渲染时组件函数会执行，`use` 读取 promise 并挂起，激活外层 Suspense，数据会在隐藏期间提前请求。
- 如果 `Video` 用 `useEffect(() => { fetchVideo() }, [])` 取数：Effects 没有挂载，因此**不会**在隐藏预渲染期间发请求。Activity 不会检测 Effect 里的数据获取。

之后切到 `video`：

- `Video` 的 state 会保留（预渲染时已经初始化）。
- 已创建的 DOM 会被显示出来（同一个 DOM 节点，不是重新创建）。
- Effects 此时才挂载执行。若数据已通过 `use` 预取，切换会更快；若依赖 Effect 取数，请求从这时才开始。

#### 2. Home 的草稿、DOM 与 Effect 日志

在 textarea 输入 `hello`，切到 video，再切回 home：

- textarea 仍显示 `hello`。`draft` state 和 textarea 的 DOM 都被保留，Activity 只是用 `display: none` 隐藏它们。
- 按非 StrictMode 语义，日志顺序是：

```text
subscribe
unsubscribe
subscribe
```

  - 初始 Home 可见：Effect setup，打印 `subscribe`；
  - 切到 video：Home 被隐藏，Effect cleanup 执行，打印 `unsubscribe`；
  - 切回 home：Home 再次可见，Effect setup 重新执行，打印 `subscribe`。

- DOM 节点没有被销毁重建，只是隐藏和显示；输入框的 DOM 状态（包括 React state 和 DOM 自身的临时状态）都保留。

与 `{tab === 'home' && <Home />}` 条件渲染相比：

- 条件渲染在 `tab !== 'home'` 时**卸载** Home：state 被销毁，DOM 被移除，Effect cleanup 执行；再次显示时重新挂载，`draft` 回到 `''`，DOM 新建，Effect setup 再执行。
- Activity 隐藏时 state 和 DOM 保留，只有 Effects 被清理；再次显示时 state/DOM 恢复，Effects 重新 setup。
- 两种方式都会产生 `subscribe → unsubscribe → subscribe` 的日志模式，**日志相同不代表语义相同**；关键差别在 state 和 DOM 是否被销毁。

#### 3. 隐藏 Video 后媒体仍播放

在 Video 播放时切回 Home，Video 的 Activity 变成 `hidden`，但视频/音频**很可能继续播放**。原因：

- Activity 隐藏只给子树加上 `display: none`，并不会销毁 `<video>` DOM 元素。
- 媒体播放是浏览器对该 DOM 元素产生的副作用，不会因为 React 清理了 Effect 就自动停止。
- 文档特别指出：隐藏的组件 DOM 若带有副作用（例如 `<video>`），需要自己清理。

修复：用 ref 拿到 video 元素，在 `useLayoutEffect` 的 cleanup 中暂停：

```tsx
function Video() {
  const ref = useRef<HTMLVideoElement>(null)

  useLayoutEffect(() => {
    const video = ref.current
    return () => {
      video?.pause()
    }
  }, [])

  return <video ref={ref} src="/cat.mp4" autoPlay loop controls />
}
```

文档推荐 `useLayoutEffect` 而不是普通 `useEffect`，因为这里的 cleanup 与“UI 被视觉隐藏”直接相关，应该及时执行，不能被 Suspense 重新挂起或 View Transition 延迟。是否把 `currentTime` 重置为 0 取决于产品需求；Activity 的默认行为会保留播放进度。

**Activity 隐藏时 Effects 的行为：** React 会销毁/清理子组件的 Effects，cleanup 函数会执行，订阅、定时器等副作用会停止。概念上可以把 hidden Activity 的子组件当成“已卸载”，但 React 会把 state 和 DOM 保存下来，等可见时恢复。再次可见时 Effects 会重新 setup。

**如果清理逻辑写在 setup 里而不是返回的 cleanup 里：** 隐藏时那段清理代码不会运行，订阅/监听器/定时器会泄漏；再次显示时 setup 又执行一次，可能产生重复订阅、重复监听或重复定时器。正确的做法是让 setup 只负责建立，把拆除逻辑放在返回的 cleanup 中。StrictMode 的额外 setup/cleanup 演练可以帮助发现这类问题。

#### 4. 纯文本子树与隐藏期间的重渲染

- 如果 hidden 的 Activity 子树只返回字符串 `Hello`，DOM 里**什么都不会有**。因为 Activity 通过给宿主 DOM 元素设置 `display: none` 来隐藏内容；纯文本没有对应的 DOM 元素可以设置样式，所以 React 不渲染它。`visible` 时才会显示文本。
- 隐藏期间，子组件仍会因父组件传入新 props 而重新渲染，但优先级低于可见内容。它们的 Effects 不会挂载；state 和 DOM 会被保留。可以把 hidden Activity 理解为“低优先级的后台渲染 + 保存 state/DOM，但不运行 Effects”。

### 评分点（共 2.5 分）

- 0.75 分：首次 hidden Activity 仍 render/预渲染、DOM 隐藏存在、Effects 不挂载；`use` 会预取而 `useEffect` 不会；切到 visible 时 state/DOM 保留、Effects 挂载。
- 0.75 分：草稿和 DOM 保留；日志为 `subscribe → unsubscribe → subscribe`；与条件渲染相比 state/DOM 不销毁，能指出“日志相同但语义不同”。
- 0.5 分：说明视频继续播放的原因（DOM 保留 + display:none）；给出 `useLayoutEffect` cleanup 暂停的修复；说明隐藏时 Effects 会被清理，清理逻辑应放在返回的 cleanup 中。
- 0.5 分：纯文本 hidden Activity 不产生 DOM；隐藏期间仍会因新 props 低优先级重渲染。

### 简短解释

Activity 把“隐藏”和“卸载”拆开了：对 Effects 来说它像卸载（cleanup 执行、订阅停止），对 state 和 DOM 来说它像保留（恢复后原样回来）。因此它适合保留草稿、滚动位置等临时状态，但不会自动清理 DOM 自身的副作用（如媒体播放），这些必须用 Effect cleanup 手动处理。
