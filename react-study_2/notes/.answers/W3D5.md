## 复习 1（0.5 分｜state 更新队列）

### 参考答案

初始 `n = 0`，四次调用的 pending state 依次为：

| 调用 | 处理后的 pending state | 原因 |
|---|---|---|
| `setN(n + 1)` | `1` | 直接值：用当前 render 的快照 `n = 0` 算出 `1` |
| `setN(x => x + 1)` | `2` | 更新函数：接收最新的 pending state `1`，加一 |
| `setN(n + 1)` | `1` | 直接值仍用快照 `n = 0` 算出 `1`，替换掉 pending 的 `2` |
| `setN(x => x * 2)` | `2` | 更新函数：接收最新的 pending state `1`，乘二 |

最终显示 **2**。

第三个调用没有在第二个调用的结果上继续加一，因为 `setN(n + 1)` 不是“稍后再用最新的 n 计算”的更新函数。`n + 1` 在事件处理函数执行时就已经用当前 render 的 `n = 0` 算成了常量 `1`，它会**替换**当前 pending state；只有函数形式的 `setN(x => ...)` 才会在队列处理时接收上一步的 pending state。更新按调用顺序处理，混用二者时严格按顺序计算。

### 评分点（共 0.5 分）

- 0.25 分：pending state 序列正确（`1 → 2 → 1 → 2`），最终结果 `2`。
- 0.25 分：正确解释直接值用当前 render 的快照并替换 pending state；更新函数才读取最新 pending state。

### 简短解释

`setN(n + 1)` 里的 `n + 1` 在调用时就算好了；此后不管队列里已经排了什么，它都只是把 `1` 放进队列。`setN(x => x + 1)` 才是“等轮到我时，用最新的 pending state 计算”。

## 复习 2（0.5 分｜key 与 state 重置）

### 参考答案

**草稿为什么保留：** 在 `Messenger` 的同一个位置渲染的始终是同一个组件类型 `Chat`，没有提供 `key`，也没有类型变化。React 协调时按“同一父级下的位置 + 组件类型 + key”判断是否复用；三者都没变，于是复用同一个 `Chat` Fiber，`useState` 的草稿跟着 Fiber 保留下来。`recipient` 只是 props 变了，不会重置 state。

**如何让每位收件人拿到空白草稿：** 给 `Chat` 加稳定且随收件人变化的 key，例如：

```tsx
return <Chat key={recipient.id} recipient={recipient} />
```

从 Ada 切到 Grace 时 key 变化，React 会卸载旧的 `Chat`（执行 Effect cleanup、移除 DOM、销毁 state），再挂载一个新的 `Chat`，草稿回到初始值。以后切回 Ada，也会得到一个新的空白草稿，除非把草稿提升到父级或用其他持久化方式保存。

**为什么不用 `key={Math.random()}`：** 每次 render 都会生成新的随机 key，等于每次 render 都告诉 React“这是一个全新的组件”。父组件任何无关的 state 更新都会让 `Chat` 卸载重建，草稿、输入框焦点、选区、动画和 Effect 都会丢失，还会带来额外的挂载开销。key 应该是稳定的身份标识，只在身份真的变化时才变。

### 评分点（共 0.5 分）

- 0.25 分：正确说明同位置、同类型、无 key 导致复用同一 `Chat` 实例，state 保留；给出 `key={recipient.id}` 之类的稳定 key 来重置。
- 0.25 分：说明随机 key 每次 render 都变，导致每次全部卸载重建，state/DOM/焦点/Effect 丢失；理解 key 是身份而不是“每次刷新”的开关。

### 简短解释

key 是 React 在兄弟列表中识别“这还是不是同一个组件”的身份证。没有 key 时，位置加类型就是身份；`key={recipient.id}` 把身份绑定到收件人；`Math.random()` 让身份每次 render 都变，等于放弃复用。

## 第 1 题（2.5 分｜createElement、工作循环与双缓冲）

### A. 元素形状（1 分）

#### 参考答案

**1. JSX 编译后的调用形式**

经典 runtime：

```js
React.createElement(
  'div',
  { id: 'app' },
  React.createElement('h1', null, 'Hello'),
  React.createElement('p', null, count)
)
```

自动 runtime（`react/jsx-runtime`）会使用 `jsx` / `jsxs`，children 放在 props 里，例如：

```js
jsxs('div', {
  id: 'app',
  children: [
    jsx('h1', { children: 'Hello' }),
    jsx('p', { children: count }),
  ],
})
```

两种形式的目的相同：把嵌套的 JSX 变成对 `createElement` / `jsx` 的嵌套调用。自动 runtime 只是由编译器自动插入导入，并针对静态 children 使用 `jsxs` 等优化。

**2. 简化元素对象**

```js
{
  type: 'div',
  props: {
    id: 'app',
    children: [
      {
        type: 'h1',
        props: {
          children: [
            {
              type: 'TEXT_ELEMENT',
              props: { nodeValue: 'Hello', children: [] },
            },
          ],
        },
      },
      {
        type: 'p',
        props: {
          children: [
            {
              type: 'TEXT_ELEMENT',
              props: { nodeValue: 0, children: [] },
            },
          ],
        },
      },
    ],
  },
}
```

要点：`type` 是字符串 `'div'` / `'h1'` / `'p'`；原生元素的属性在 `props` 里；children 统一放在 `props.children` 数组中；文本被包装成 `type: 'TEXT_ELEMENT'` 的对象，`nodeValue` 保存文本内容（此例中是数字 `0`，真正创建文本节点时再转成字符串即可）。

**3. `App` 出现的位置；元素、Fiber、DOM 的区别**

`<App />` 对应的元素对象形如：

```js
{ type: App, props: { children: [] } }
```

组件函数本身出现在元素的 `type` 字段里（不是 `props`，也不是元素对象的原型）。元素对象只是**一次 render 的 UI 描述**，是一个普通对象；Fiber 是协调器根据元素创建/复用的内部工作节点，保存 DOM 引用、Hooks、alternate、副作用标记等；DOM 节点是 commit 阶段真正操作浏览器的那一层。三者不能混为一谈：元素每次 render 都可能重新创建，Fiber 跨 render 持久化，DOM 只在 commit 阶段被修改。

**4. 真实 React 元素的额外字段，以及 mini 版为什么能省略**

真实 React 元素通常还包含：

- `$$typeof`：一个 Symbol，用来标记“这是一个 React 元素”，也用于一些安全校验；
- `key`：兄弟列表中的身份，通常在 `createElement` 时从 config 中取出，放在元素顶层，**不会作为普通 prop 传给组件**；
- `ref`：引用/转发相关的保留字段；不同版本处理细节不同（React 19 中函数组件也可以把 `ref` 当普通 prop 接收，但元素/宿主组件层面仍有特殊处理）；
- 其他版本/场景下的字段（例如开发环境的校验信息）。

真实 `props` 不包含 `key`；`ref` 在元素层面属于保留/特殊处理，具体是否作为普通 prop 传递随版本和组件类型变化。mini 版为了教学只保留 `type` 和 `props`，因为它不需要 `$$typeof` 做元素识别、不需要完整的 `ref` 转发，key 可以在协调时单独从元素上读取并用于 `Map` 匹配。省略这些字段不影响“元素是描述对象”的核心心智模型，但也意味着 mini 版不等同于真实 React 元素的完整语义。

#### 评分点（A 部分共 1 分）

- 0.25 分：正确说出 JSX 编译为 `React.createElement` / `jsx` / `jsxs` 调用（经典与自动 runtime 各一种即可）。
- 0.5 分：元素对象形状正确：`type`、`props.id`、`props.children` 嵌套、文本用 `TEXT_ELEMENT`/`nodeValue` 表示。
- 0.25 分：正确说明组件函数在 `type` 字段、元素不是 Fiber/DOM；并能指出真实元素的 `key`/`ref`/`$$typeof` 属于顶层/特殊字段，`key` 不进入普通 props。

#### 简短解释

JSX 不是模板字符串，也不是 DOM；它编译成创建普通对象的函数调用。mini 版把 children 统一塞进 `props.children`，文本包成 `TEXT_ELEMENT`；真实 React 还要维护 `key`、`ref`、`$$typeof` 等保留字段。元素只是“这次 UI 长什么样”的描述，Fiber 和 DOM 是后续阶段才出现的东西。

### B. 工作循环与双缓冲（1.5 分）

#### 参考答案

**1. `performUnitOfWork` 的访问顺序**

从 `wipRoot`（HostRoot Fiber）开始：

```text
wipRoot → div → h1 → TEXT("A") → p → TEXT("B") → null
```

逐步解释：

- `wipRoot`：`dom` 已经是 `container`，不需要创建；协调出 `div`，返回 `div`。
- `div`：创建 div DOM，协调出 `h1` 和 `p`；有 `child`，返回 `h1`。
- `h1`：创建 h1 DOM，协调出文本 `"A"`；返回文本 fiber。
- `TEXT("A")`：创建文本 DOM；没有 child；自己也没有 sibling，于是沿 `parent` 回退到 `h1`；`h1` 有 sibling `p`，返回 `p`。
- `p`：创建 p DOM，协调出文本 `"B"`；返回文本 fiber。
- `TEXT("B")`：没有 child；没有 sibling；沿 parent 依次回退到 `p`、`div`、`wipRoot`，都没有 sibling，最终返回 `null`。

如果实现里显式调用 `completeWork`，完成（向上收尾）的顺序是：
`TEXT("A") → h1 → TEXT("B") → p → div → wipRoot`。题目只要求 `performUnitOfWork` 的返回顺序，但能区分“向下 begin”和“向上 complete”更好。

**2. DOM 创建与“看不到半成品”的原因**

每个 fiber 的 `dom` 在 `performUnitOfWork` 的**开始**（对应 `beginWork`）创建：`if (!fiber.dom) fiber.dom = createDom(fiber)`。首次挂载时，div、h1、p 和文本 fiber 都会创建节点；更新时复用的 fiber 已经有 `dom`，会跳过创建。HostRoot 的 `dom` 已经是容器，也跳过。

按题面约定，render 阶段只创建节点、准备变更，**不插入文档，也不修改页面上的 DOM**；`commitWork` 在 commit 阶段才执行插入、删除和属性更新。因此在首次 commit 之前，页面上还看不到这些新节点，或者看到的仍是上一棵 `currentRoot` 对应的旧 UI。工作循环中途停下时，只需要丢弃 `wipRoot`，`currentRoot` 和屏幕上的 DOM 都没有被改过，所以不会出现“只渲染了一半”的界面。commit 是同步的：一旦开始提交，就按 mutation 顺序完成插入/删除/属性更新，然后一次性切换 `currentRoot`（对应真实 React 的 `root.current`）。

需要注意：有些 mini-react 教学实现会在 `completeWork` 里直接 `parentDom.appendChild(child.dom)`，这样 render 阶段就会往容器里插入节点；如果工作循环中途暂停，确实可能看到部分 DOM。这是教学实现的简化，不是真实 React 的行为。真实 React 在 render 阶段构建 work-in-progress 树，commit 阶段才改 DOM，并且 commit 对同一个 root 是同步、原子的。

**3. commit 后的 `currentRoot` / `wipRoot` 与 `alternate`**

`commitRoot()` 完成后：

- `currentRoot = wipRoot`：刚提交的 WIP 树成为新的 current 树，对应屏幕上的 UI；
- `wipRoot = null`：这一轮工作树清空，等待下一次更新；
- 旧 current 树没有立刻消失，而是保留下来，作为下一次 WIP 树的 `alternate`。

下一次调用 `render` 时，新的 `wipRoot` 会设置 `alternate: currentRoot`；协调子节点时，新建的每个 WIP fiber 也会通过 `alternate` 指向旧 current 树中对应的 fiber。这样 React 可以复用旧 fiber 的 DOM、Hook state 和 diff 信息，只把变化的部分标记出来。下一次 commit 后两棵树角色再次互换：新树变 current，旧 current 变 alternate。

**4. 与真实 React 并发渲染的关键区别**

至少可以指出一点：

- 这个 mini 工作循环是**同步跑完**的（或者只是在空闲回调里简单分段），没有 lane/优先级，也没有“高优先级更新打断低优先级 render”的机制；真实 React 的 render 可以按时间片让出主线程、被更高优先级更新打断、丢弃并重做 WIP 树，而 commit 仍然是同步原子的。
- mini 没有 `Suspense`、transition、`useDeferredValue` 等并发特性，也不一定实现 bailout/memo 的完整优化。
- mini 通常没有“同一 root 的多个 lane 合并/重放”逻辑；更新只是简单地把 `wipRoot` 指向 current 再跑一遍工作循环。

答出任意一处关键区别即可；重点是知道 mini 的“双缓冲”只保留了 current/WIP 两棵树和提交切换的形式，并不等于真实 React 的完整并发调度实现。

#### 评分点（B 部分共 1.5 分）

- 0.5 分：访问顺序正确，包含 `wipRoot`、DOM 元素、文本 fiber，并最终到 `null`；能解释 child/sibling/parent 的回退规则。
- 0.5 分：正确说明 `dom` 在 `beginWork`/`performUnitOfWork` 开始创建；render 只创建不插入、commit 才插入；中断/丢弃 WIP 不会影响屏幕；知道“在 completeWork 直接 append”的教学实现是简化、不是真实 React 行为更好。
- 0.5 分：正确说明 commit 后 `currentRoot` 指向新树、`wipRoot` 清空；下一次 `wipRoot.alternate` 指向 current，子树 `alternate` 对应旧 fiber；能指出至少一处与真实并发渲染的区别。

#### 简短解释

工作循环是“向下 begin，没孩子就找 sibling，没 sibling 就沿 parent 回退，最后返回 null”。render 在 WIP 树上创建节点，commit 才把结果接到屏幕上；两棵树通过 `alternate` 互相引用，commit 后交换角色。mini 版只实现了双缓冲的骨架，没有 lane、优先级和可中断调度，所以不要把它的同步工作循环当成真实 React 并发实现的全部。

## 第 2 题（2.5 分｜keyed diff 找 bug）

### A. 找 bug（0.75 分）

#### 参考答案

**错误在 `if (old.index < lastPlacedIndex) ... else` 的 `else` 分支里，这一行：**

```js
lastPlacedIndex = index
```

应改为：

```js
lastPlacedIndex = old.index
```

**`lastPlacedIndex` 的含义：** 在从左到右扫描新列表、复用旧节点的过程中，记录已经复用过的节点在**旧列表中的最大 index**。如果当前复用的旧节点的 `old.index` 小于这个最大值，说明它在旧列表中位于某个已处理节点的**前面**，但在新列表中却排到了该节点的**后面**，因此需要往右移动，标记 `PLACEMENT`；否则它保持相对顺序，更新 `lastPlacedIndex = old.index`。

**为什么必须与旧位置比较：** 判断“是否移动”问的是“当前节点在旧列表中的相对顺序，是否被新列表破坏”。`old.index` 是它在旧列表中的位置，`lastPlacedIndex` 是已处理旧节点的最大旧位置；两者比较才能发现“新列表把后面的节点提到了前面”。而 `index` 是新列表中的位置，随着循环单调递增，拿它当 `lastPlacedIndex` 会让比较失去意义。

**以 `[A, B, C] → [C, A, B]` 为例：**

旧 index：A=0，B=1，C=2；新 index：C=0，A=1，B=2。

使用错误的 `lastPlacedIndex = index`：

- C：`old.index = 2`，`2 < 0` 为假 → `lastPlacedIndex = 0`；
- A：`old.index = 0`，`0 < 0` 为假 → `lastPlacedIndex = 1`；
- B：`old.index = 1`，`1 < 1` 为假 → `lastPlacedIndex = 2`。

没有任何节点被标记 `PLACEMENT`，所以 commit 不会移动 DOM，顺序保持旧顺序。

使用正确的 `lastPlacedIndex = old.index`：

- C：`2 < 0` 为假 → `lastPlacedIndex = 2`；
- A：`0 < 2` 为真 → A 标记 `PLACEMENT`；
- B：`1 < 2` 为真 → B 标记 `PLACEMENT`。

因此 A、B 会被移动到 C 后面，最终得到 `C, A, B`。

> 补充：这趟算法是线性启发式，不保证移动次数最少；它的目标是保证正确的相对顺序，而不是做最小编辑距离或最长递增子序列。移动标记的具体 commit 方式（`appendChild` 或 `insertBefore`）可以不同，但判断“是否需要移动”的依据必须是旧 index。

#### 评分点（A 部分共 0.75 分）

- 0.5 分：准确指出 `lastPlacedIndex = index` 应改为 `lastPlacedIndex = old.index`（或等价描述），并结合 `[C, A, B]` 说明不会产生 `PLACEMENT`。
- 0.25 分：正确解释 `lastPlacedIndex` 记录的是已复用节点的最大旧 index，移动判断必须比较旧位置；能说明使用新 index 会让比较失效。

### B. 预测行为（1 分）

#### 参考答案

**1. 使用有 bug 的代码**

DOM 中三个 `<li>` 的顺序仍是 **A, B, C**；`hello` 仍在 A 那一行（实际显示为第一行）。

原因：A/B/C 的 key 和 type 都没变，协调器按 key 找到了旧 fiber，复用了各自的 `dom`、Hook state 和 `alternate`，只更新 props。`hello` 是 A 所在 fiber 的 `useState`，状态跟着 A 的 fiber/DOM 保留。但由于 bug 没有给任何节点打 `PLACEMENT`，commit 只做属性更新，没有移动 DOM，所以视觉顺序没有变成 `C, A, B`。这不是 state 串行，而是**提交顺序/移动标记**出错。

**2. 修复那一行后**

DOM 顺序变为 **C, A, B**；`hello` 仍在 A 的输入框里，但 A 现在位于第二行。

按 `appendChild` 的提交方式：

- 旧 DOM 顺序是 A, B, C；
- 新 fiber 顺序是 C, A, B；
- C 是 UPDATE，不移动，仍在最后；
- A 带 `PLACEMENT`，`parentDom.appendChild(A.dom)` 把 A 移到父节点末尾，DOM 变成 B, C, A；
- B 带 `PLACEMENT`，`appendChild(B.dom)` 把 B 移到末尾，DOM 变成 C, A, B。

最终顺序正确。A/B/C 的对应关系始终不变：新 fiber 通过 `alternate` 复用旧 fiber 的 DOM 和 Hook state，只是 DOM 被移动；state 没有在行之间转移。

**3. 这属于什么错误？为什么输入框内容没有串行？**

这是 **commit/移动顺序错误**（没有设置 `PLACEMENT`），不是 state 错位。keyed diff 按稳定 key 正确匹配了 A/B/C，每个输入框的 state 仍然在它所属的 fiber 上，所以 `hello` 不会跑到 B 或 C 的输入框。只有 DOM 节点需要重新排列；没有移动标记，DOM 就保持旧顺序，看起来像“数据顺序变了但界面顺序没变”。

对比：如果使用 `key={index}`，身份会绑定到位置而不是数据，插入/重排时才会出现“输入内容跟着位置走、串到别的数据行”的 state 错位。

#### 评分点（B 部分共 1 分）

- 0.4 分：正确预测 bug 版本 DOM 顺序仍为 A, B, C，`hello` 在 A 行；说明 A/B/C 的 Fiber/DOM/state 被复用。
- 0.4 分：正确预测修复后顺序为 C, A, B，`hello` 跟着 A 到第二行；能结合 `PLACEMENT` 和 `appendChild` 说明移动过程（A 移到末尾、B 再移到末尾）。
- 0.2 分：正确区分“提交顺序错误”与“state 错位”，并解释输入框内容为什么没有串行。

### C. index key 与 key 变化（0.75 分）

#### 参考答案

**1. 使用 `key={index}` 从顶部插入 X**

旧列表：A(key=0)、B(key=1)、C(key=2)；新列表：X(key=0)、A(key=1)、B(key=2)、C(key=3)。

React 按“同父级/同列表 + 同 key + 同 type”复用：

- X 找到旧 A（key=0，type 相同）→ 通过 `alternate` 复用旧 A 的 DOM 和 state，所以 A 输入的 `hello` 会显示在 **X 这一行**（第一行，label 变成 X，但输入框里仍是 hello）；
- A 找到旧 B（key=1）→ 复用旧 B 的 state（通常是空）；
- B 找到旧 C（key=2）→ 复用旧 C 的 state（通常是空）；
- C 的 key=3 找不到旧节点 → 新建 Fiber/DOM，state 初始化。

所以 `hello` 出现在 X 行；A、B、C 三行的输入框状态整体错位，最后 C 是新挂载的。

**2. React 复用旧 Fiber 的条件**

同一父级（同一个兄弟列表）下：

- `key` 相同（单节点没有显式 key 时，用位置作为隐式 key）；
- `type` 相同（同一个 DOM 标签或同一个组件函数）；
- 两者都满足才复用 Fiber，进而复用 DOM 和 state。

key（或 type）变化时：

- 旧 Fiber 被标记删除/卸载：执行 Effect cleanup，移除 DOM，丢弃 Hook state；
- 新 Fiber 重新挂载：创建新 DOM，state 用初始值初始化；
- 不会把旧组件的 state “迁移”给新 key 或新类型。

**3. key 的唯一性范围**

key 只需要在**同一个父级的兄弟列表内唯一**，不需要全局唯一。不同数组、不同父级可以使用相同的 key，因为它们不会参与同一个列表的匹配。同一列表内重复 key 会导致匹配/复用混乱，应该避免。

#### 评分点（C 部分共 0.75 分）

- 0.35 分：index key 插入 X 后，正确说明 X 复用 A 的 Fiber/state，`hello` 出现在 X 行；A/B/C 状态整体错位，最后一个新挂载。
- 0.25 分：正确列出复用条件（同父级/同列表、同 key、同 type），并说明 key 变化会卸载旧 Fiber、重建 DOM、重置 state。
- 0.15 分：指出 key 只在兄弟列表内唯一，不需要全局唯一。

### 简短解释

keyed diff 先用 key 找到旧 fiber，再用 type 确认能否复用；复用后 state 和 DOM 跟着 fiber 走。`lastPlacedIndex` 是“已处理节点的最大旧位置”，用来发现新列表中需要往右移的节点；拿新 index 来更新它会让移动检测失效，props 更新了但 DOM 不重排。index key 则把身份绑在位置上，插入/重排后 state 会跟着位置错位。

## 第 3 题（3 分｜useState 的 Hook 链表、更新队列与纯度）

### A. Hook 顺序（1 分）

#### 参考答案

**1. Hook 链表与点完 `count+1` 后的 `getHook(fiber, 1)`**

首次渲染时 `count = 0`，条件 `count > 0` 为假，所以只调用两个 Hook：

```text
hook 0: useState(0)   → count = 0
hook 1: useState(10)  → step = 10
```

条件分支里的 `useState('flag')` 没有执行。因此首次渲染的 Hook 链表为 `count@0 → step@1`。

点击 `step+1` 后，step Hook 的更新队列里有一个 `s => s + 1`，触发第二次渲染。此时 `count` 仍为 0，条件仍为假，Hook 调用顺序还是：

```text
hook 0: useState(0)   → count = 0（复用旧 hook 0）
hook 1: useState(10)  → step = 11（复用旧 hook 1，处理队列 s => s + 1）
```

所以第二次渲染后 Hook 链表仍是 `count@0 → step@1`，只是 step 的 state 变成 11。

再点击 `count+1`，触发第三次渲染。此时 `count = 1`，条件为真，Hook 调用顺序变成：

```text
hook 0: useState(0)      → count（复用旧 hook 0）
hook 1: useState('flag') → flag（getHook(fiber, 1) 取到旧的 step Hook）
hook 2: useState(10)     → step（getHook(fiber, 2) 没有旧 Hook）
```

`getHook(fiber, 1)` 沿旧 Hook 链表走 1 步，取到的是**旧的 step Hook**。旧 step Hook 的状态是 11；第三次渲染创建 index 1 的新 Hook 时，先复制 11（旧 step Hook 的队列已经在第二次渲染时处理完，此时为空），所以新 Hook（`flag`）的 state 是 **11**，而不是 `'flag'`。

**2. 点完 `count+1` 后的显示**

- `count` 显示 `1`；
- `step` 在 hook index 2，没有旧 Hook，使用初始值 `10`，所以显示 **10**；
- `flag` 实际是 **11**（虽然组件没有把它渲染出来）。

界面显示 **`1 / 10`**。`step` 从 11 被重置回 10，因为条件分支插入了一个新的 Hook，后续 Hook 的索引整体后移；旧的 step Hook 被 flag 占用了。

**3. 真实 React 的行为与 Hook 规则**

真实 React 在这里会抛错，开发环境信息类似：

```text
Rendered more hooks than during the previous render.
```

首次渲染 2 个 Hook；点完 `count+1` 的那次渲染变成 3 个 Hook，React 根据调用顺序匹配 Hook 状态，发现数量/顺序不一致，无法安全复用，于是报错。React 不知道变量名，它只知道“第 n 个 Hook”。如果 Hook 放在条件、循环或嵌套函数里，某些 render 可能多调用或少调用，后面所有 Hook 的状态都会错位；所以 Rules of Hooks 要求：

- 只在 React 函数组件或自定义 Hook 的顶层调用 Hook；
- 每次 render 都按相同顺序调用相同数量的 Hook；
- 不要放在 `if`、`for`、`while`、嵌套函数、`try/catch` 等可能改变调用顺序的位置；
- 需要条件逻辑时，把条件放在 Hook **调用之后**，或把 Hook 提到自定义 Hook 里并在顶层调用。

（`use()` 不是 Hook，规则不同，可以条件调用；这里说的是 `useState`、`useEffect` 等 Hook。）

mini-react 的 `getHook` 只是按索引走链表，没有真实 React 的 Hook 数量/顺序校验，所以它不会报错，而是**静默地**把旧 step 的 state 交给 flag，并把 step 重置为初始值。这种“不报错但状态错位”正是 Hook 顺序规则要防止的。

#### 评分点（A 部分共 1 分）

- 0.45 分：正确写出首次与 `step+1` 后的 Hook 链表都是 count@0、step@1；点完 `count+1` 后为 count@0、flag@1、step@2；指出 `getHook(fiber, 1)` 拿到旧 step Hook。
- 0.3 分：正确算出 `flag = 11`、`step = 10`，界面显示 `1 / 10`，并解释 Hook 按调用顺序而不是变量名匹配。
- 0.25 分：说明真实 React 会抛“Rendered more hooks than during the previous render”一类的错误；能说明 Hooks 必须在顶层、每次 render 顺序一致，以及 mini 版为什么静默错位。

### B. 更新队列与重渲染（1 分）

#### 参考答案

**1. 两个 Hook 的更新队列与最终结果**

点击一次按钮，`handleClick` 中依次执行四个调用：

- n Hook 的队列（按调用顺序）：
  1. `setN(n + 1)`：直接值，用当前 render 的快照 `n = 0` 算出 `1` → pending `1`；
  2. `setN(x => x + 1)`：更新函数，接收最新 pending `1` → `2`；
  3. `setN(x => x * 2)`：更新函数，接收最新 pending `2` → `4`。
- step Hook 的队列：
  1. `setStep(step + 10)`：直接值，用当前快照 `step = 1` 算出 `11` → pending `11`。

最终显示 **`4 / 11`**。

注意：事件处理函数里调用顺序是 `n, n, step, n`，但每个 Hook 的队列只保存发给自己的 action，并按各自调用顺序处理；两个 Hook 的 state 独立计算。n 的队列是 `[1, x=>x+1, x=>x*2]`，step 的队列是 `[11]`。

**2. 组件函数执行次数与日志**

这次点击会让 `Counter` 函数执行 **1 次**（一轮工作循环、一次 commit）。假设没有 StrictMode 的双调用，控制台日志是：

```text
render 0 1      // 首次挂载
render 4 11     // 点击后的一轮更新
```

不是每个 `setState` 都立即重渲染，因为 `setState` 只是把 action 压入对应 Hook 的更新队列并调用 `scheduleUpdate`；在题面约定下，同一事件处理函数中的多次调用会合并到事件结束后的一轮工作循环里，下一次 render 时才消费队列。这和真实 React 在事件处理函数中的自动批处理方向一致，但 mini 版没有 lane/优先级，只是“排队 + 一轮工作循环”。

如果事件处理函数里有 `await` 并在之后调用 `setState`，在真实 React 中批处理边界可能不同；mini 题面模型仍然是排队后由下一轮工作循环处理。本题只要求题面模型。

**3. 改成 `setN(n * 2)`**

队列变为：

1. `setN(n + 1)`：直接值，`n = 0` → `1`；
2. `setN(x => x + 1)`：更新函数，接收 `1` → `2`；
3. `setN(n * 2)`：直接值，仍用当前 render 的快照 `n = 0` 算出 `0`，替换 pending 的 `2`。

最终 n 为 **0**，界面显示 **`0 / 11`**。

原因和复习 1 相同：直接值在调用时就已经用当前 render 的变量算好，不会读取队列里最新的 pending state；只有函数形式的更新才会接收最新 pending state。要让第三次调用基于最新值，应写成 `setN(x => x * 2)`。

#### 评分点（B 部分共 1 分）

- 0.4 分：两个队列的 action 顺序和 pending state 正确，最终 `4 / 11`；能区分直接值与更新函数。
- 0.3 分：说明点击后组件函数只执行一次、日志为首次 `render 0 1` 和更新 `render 4 11`；解释 setState 是入队并调度，不是每个调用立即 render。
- 0.3 分：改成 `setN(n * 2)` 后正确得到 0（显示 `0 / 11`），并解释直接值使用当前快照、不会读取 pending state。

### C. 纯度（1 分）

#### 参考答案

**1. 两处违反纯度的地方及后果**

**第一处：`items.reverse()`**

`reverse()` 会**原地修改** `items` 数组；`items` 是 props，属于父组件/外部数据。render 必须是纯函数：给定相同的 props/state，应该返回相同的结果，且不能修改输入。这里的后果包括：

- 父组件或其他使用同一数组的组件会看到被修改的顺序；
- 每次 `List` 重新渲染都会再翻转一次，列表顺序取决于 render 执行了多少次，而不是 props 是什么；
- StrictMode 在开发环境会双调用 render，两次 `reverse()` 可能相互抵消，让 bug 时隐时现；但这不代表代码是对的；
- 真实 React 的 render 可能被中断、重做或丢弃，原地修改会作用在可能永远不会提交的渲染上，污染共享数据。

**第二处：`setCount(count + 1)`**

在 render 函数体里调用 `setState` 会在渲染过程中安排新的更新；真实 React 会检测到渲染期间不断产生更新，报 “Too many re-renders” 一类的错误。mini 版没有这层保护，`scheduleUpdate` 可能在 render 中反复安排新的工作循环，或者让本轮尚未提交的更新与正在进行的 render 交错，行为不可预测、可能表现为无限重渲染或更新丢失。即使写成 `setCount(0)`，在 render 中无条件 `setState` 仍会反复调度，属于反模式。`count` 在这个组件里也没有被使用，说明它很可能是多余的 state。

**2. 没有 StrictMode / 并发，是否就能在 render 中做这些事？**

不能。纯度不是 StrictMode 或并发渲染的可选规则，而是 React 渲染模型的基本要求：

- 组件会因为父组件更新、自身 state 更新、Context 变化、错误重试等原因多次 render；mini 版每次更新也会重新执行整个组件函数。
- 真实 React 的 render 可能被中断、重做或丢弃；只有 commit 的结果才算数。render 中的副作用会重复执行，或者作用在从未提交的 WIP 树上。
- 如果 render 依赖“只执行一次”或依赖外部可变状态，同样的 props/state 可能得到不同 UI，无法预测，也无法安全优化（memo、Compiler、并发）。
- StrictMode 只是**放大**问题、让重复调用显式发生；没有 StrictMode 只是让 bug 更隐蔽，不会让它合法。

**3. 修复方式**

```jsx
function List({ items }) {
  // 复制后再反转，不修改 props；也可以使用 items.toReversed()（若运行环境支持）
  const ordered = [...items].reverse()

  return (
    <ul>
      {ordered.map(item => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  )
}
```

- 删除 `const [count, setCount] = useState(0)` 和 `setCount(count + 1)`：`count` 没有参与 UI，若确实需要长度等派生值，直接在 render 中计算，例如 `items.length`；不要把派生值同步进 state。
- 如果 `count` 是交互产生的状态，把更新放到事件处理函数（或确实需要同步外部系统时放到 Effect），不要放在 render 中。
- 如果需要在 `items` 变化时重置某些 state，优先用 key 重置组件身份，或使用真实 React 中“带 prev 值守卫的条件 setState”模式；不要无条件自增。

#### 评分点（C 部分共 1 分）

- 0.4 分：指出 `items.reverse()` 原地修改 props 及后果（外部数据被改、每次 render 翻转、StrictMode 双调用相互抵消、渲染结果依赖执行次数）；指出 render 中无条件 `setCount` 会导致无限重渲染/Too many re-renders。
- 0.3 分：说明纯度与 StrictMode/并发无关：render 本来就可能多次执行，mini 版每次更新也会重跑；副作用会重复或作用于未提交的渲染；没有 StrictMode 只是让 bug 更隐蔽。
- 0.3 分：给出正确修复：复制后反转（`[...items].reverse()` 或 `toReversed()`），移除 render 中的 setState/多余 state，改为事件处理或直接派生。

### 简短解释

Hook 的状态按**调用顺序**存放在链表里，不是按变量名；条件分支插入 Hook 会让后面的 Hook 整体错位。更新队列把 action 按入队顺序在下一轮 render 中消费：直接值用当前 render 的快照替换 pending state，更新函数才读取最新 pending state。render 必须是纯函数：不能改 props/外部数据，也不能在 render 里无条件 setState 触发新一轮渲染；StrictMode 和并发只是让不纯行为更容易暴露或造成更隐蔽的 bug，而不是这条规则的来源。
