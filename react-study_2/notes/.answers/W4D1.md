## 复习 1（0.5 分｜transition、受控输入与 Suspense）

### 参考答案

#### 1. `query`、`submitted` 与 `isPending`

- `setQuery(next)` 是**紧急更新**。每次输入时，受控 input 的 value 应立即更新；不能在用户输入时丢掉字符或让输入框显示旧值。
- `setSubmitted(next)` 在 `startTransition` 中是**过渡更新**。React 会以较低优先级渲染新的 `Results`；如果用户继续输入，上一次过渡可以被中断/重启，最终只提交最新的相关结果。
- `isPending` 从调用 `startTransition` 开始，到这次过渡完成并提交为止为 `true`。它表示“有一个 transition 正在等待提交”，不代表普通紧急输入也被延迟。用户继续输入时，transition 可能重启，但 input 仍然响应。
- `query` 会立即反映每个字符；`submitted` 可能短暂落后，`Results` 读到的是某次过渡对应的值，而不是每个字符的同步结果。

**为什么不能把 `setQuery(next)` 放进 transition：** 受控 input 的 value 必须跟手。transition 是可中断、可丢弃的低优先级工作；把控制输入值的 state 更新放进去，可能导致输入框不能可靠地显示用户刚键入的字符，输入体验被阻塞或“回跳”。transition 应用于不阻塞紧急交互的派生结果（例如搜索结果列表），紧急输入本身必须留在普通更新中。

#### 2. 有 key 与没有 key 的 Suspense 行为

- **保留 `<Suspense key={submitted}>`：** 每次 `submitted` 变化都会创建新的 Suspense 边界身份。新边界没有已经展示过的内容；里面的 `Results` 读取新数据并挂起时，浏览器看到的是 fallback（“加载中…”），旧结果被替换。这里 key 让每次查询拥有独立的 Suspense 生命周期。适合希望明确显示“正在加载这一份结果”的场景。
- **去掉 Suspense 上的 key：** 仍是同一个 Suspense 边界和 `Results` 实例。已经显示过的内容在过渡更新中通常会被保留，React 不会为了一个低优先级的更新把旧内容立刻藏起来；用户会继续看到旧结果，直到新结果准备好（`isPending` 用来提示正在更新）。这适合“保留旧结果、避免闪屏”的搜索体验。
- 注意关键区别：**把 key 放在 `<Results>` 上而不是 `<Suspense>` 上，通常在 transition 中仍会保留旧内容**，因为 Suspense 边界还是原来那个；key 必须改变边界身份，才会让新边界因为无内容而展示 fallback。
- 如果这是首次挂载、还没有任何已显示内容，没有旧内容可保留，也可能看到 Suspense fallback；上面的“保留旧内容”主要针对已经展示过的边界。transition 中的更新不会让已经 reveal 的旧 Suspense 边界退回 fallback。

### 评分点（共 0.5 分）

- 0.25 分：说明 `query` 紧急更新、`submitted` 过渡更新、`isPending` 的区间；说明受控 input 的 value 不能放进 transition，否则输入不能可靠跟手。
- 0.25 分：说明 key 在 Suspense 上时新边界显示 fallback，无 key 时同一边界在过渡中保留旧内容；能指出 key 放在 Results 上通常不等于换 Suspense 边界，并能联系 `isPending`/用户体验说明场景。

### 简短解释

`startTransition` 只改变更新的优先级，不会让同步代码自动跑进后台；受控输入的值属于紧急更新。Suspense 边界的 key 改变边界身份，因而改变“挂起时是新边界还是旧边界”的行为；只给内部子组件加 key 不会自动让旧边界退回 fallback。

## 复习 2（0.5 分｜memo、props 引用与 children 组合）

### 参考答案

#### 1. 为什么 `Panel` 仍然重新 render

`memo` 默认对 props 做浅比较，任何一个 prop 引用变化都会重新渲染。这里是两个同时存在的原因：

1. `options={{ compact: true }}`：每次 `Dashboard` render 都会新建一个对象，`Object.is` 比较失败。
2. `children` 也是 prop。每次 `Dashboard` render 都会新建 `<ExpensiveTable />` 这个 React 元素，引用不同，所以即使 `options` 稳定，`memo` 也不会 bail out。传给 Panel 的 children 元素重新创建后，Panel 渲染它时 React 会重新协调 `ExpensiveTable`；如果 `ExpensiveTable` 自己也没有 memo，就会重新执行。

`memo` 不会自动深入比较对象的字段，也不会忽略 children；它只做浅比较。

#### 2. 两种不同层级的修法

**只稳定 props（局部补丁）：**

```tsx
const PANEL_OPTIONS = { compact: true } // 模块级常量，引用稳定

function Dashboard() {
  const [note, setNote] = useState('')
  const table = useMemo(() => <ExpensiveTable />, [])

  return (
    <>
      <input
        aria-label="备注"
        value={note}
        onChange={(event) => setNote(event.target.value)}
      />
      <Panel options={PANEL_OPTIONS}>{table}</Panel>
    </>
  )
}
```

`options` 变成稳定常量，`children` 元素由 `useMemo` 固定。注意这仍要求 `ExpensiveTable` 本身不会因其他原因重渲染；如果它很贵，还应考虑它自己的边界。

**从结构上缩小更新范围（更彻底）：** 把 `note` 这个与 Panel 无关的 state 下沉到独立组件，让包含 `<Panel>` 的父组件根本不会因输入而 render：

```tsx
function NoteEditor() {
  const [note, setNote] = useState('')
  return (
    <>
      <input
        aria-label="备注"
        value={note}
        onChange={(event) => setNote(event.target.value)}
      />
    </>
  )
}

function Dashboard() {
  return (
    <>
      <NoteEditor />
      <Panel options={PANEL_OPTIONS}>
        <ExpensiveTable />
      </Panel>
    </>
  )
}
```

现在输入只重渲染 `NoteEditor`，`Dashboard` 不 render，`Panel` 和 `ExpensiveTable` 的 elements 引用保持稳定。这比“逐个用 memo 缓存 props”更彻底：以后新增一个与 Panel 无关的 state，也不会再击穿 Panel；它从源头避免了无关更新进入这棵昂贵子树。

另一种结构方案是让一个小的包装组件持有 `note`，同时通过 `children` 接收稳定的 `<Panel>…</Panel>` 子树；核心都是“让高频 state 只影响它真正需要影响的组件”。

### 评分点（共 0.5 分）

- 0.25 分：同时指出 `options` 每次新建对象、`children` 每次新建 JSX 元素，导致浅比较失败；理解 children 也是 prop。
- 0.25 分：给出稳定 props 的修法和状态下沉/组合的结构修法，并说明结构修法更彻底的原因。

### 简短解释

`memo` 只比较传入的引用；`children` 不是“免费插槽”，父组件 render 时新建的子树同样会改变 prop。让无关 state 不触发父组件 render，通常比维护一堆引用稳定更可靠。

## 第 1 题（3 分｜RSC vs SSR、模块边界与可序列化 props）

### 参考答案

#### 1. 分类、bundle 与首屏/导航

- `Page`：Server Component。它是 `app/orders/page.tsx`，没有客户端标记，可以 `await getOrders()`，其源码和 `lib/orders` 的服务端依赖不会发到浏览器。
- `Chart`：Client Component。`'use client'` 是客户端图入口，`chart.tsx` 会进入客户端 bundle，并在首屏被预渲染成 HTML、在浏览器 hydration。
- `format`、`Tooltip`：被 `Chart` import，属于客户端图的传递依赖，因此也会进入客户端 bundle、作为客户端代码执行。`Tooltip` 自己没写 `'use client'` 不影响这一点；`'use client'` 的指令只写在客户端子树入口即可。
- `lib/orders`：server-only 模块，只能留在服务端图。它有数据库访问和 `import 'server-only'`，不能进入客户端图。

首屏直接访问时：

1. 服务端渲染 Server Components，并把结果、Client 占位与 props 序列化为 RSC payload。
2. Next.js 用 RSC payload 和 Client Components 预渲染 HTML。
3. 浏览器先显示 HTML（可先看到非交互内容），再下载 Client Components 的 JS，接收 RSC payload，完成 hydration 和交互。

所以 HTML 是给首屏和 SEO 的预览；RSC payload 是组件树的序列化描述和跨边界数据。`Page`/`lib/orders` 的源码不在浏览器；`Chart`/`format`/`Tooltip` 的 JS 会进入浏览器。

后续客户端导航时，Next.js 通常获取新的 RSC payload（可预取/缓存），客户端据此更新 Server/Client 组件树；Client Components 在浏览器中渲染，不重新为这一段生成服务端 HTML。（具体缓存行为还受路由与 Next.js 缓存策略影响。）

#### 2. `'use client'` 标记的是什么；两个 import 方向

`'use client'` 标记的是**客户端模块图的入口**，作用于整个文件及其传递依赖，不是“这个组件只在浏览器里运行”。`Tooltip` 没有指令，但被 `Chart` import，处在客户端模块图内，所以它的代码也会被打包到客户端；这里的“Client Component”描述的是它在当前图中的使用，不是文件名标签。

- `chart.tsx`（Client 模块）直接 import `lib/orders`（server-only）：错误方向。服务端模块不能进入客户端模块图，Next.js/构建器会报错；即使暂时去掉 `server-only`，也等于试图把数据库代码打进浏览器，通常会在运行或构建时失败，安全上也不可接受。
- `page.tsx`（Server 模块）import `Chart`（Client 模块）：允许，也是 App Router 的常态。服务端图看到的是 client reference；真正执行 Chart 的是客户端。Server Component 可以渲染 Client Component。

#### 3. 四个 prop 与泄密问题

- `orders`：如果 `getOrders()` 返回 Prisma 类实例（或带方法的对象），序列化不支持类实例；需要转换成普通 DTO（例如 `{ id, total, status }` 的数组）。即使类型上能过，原始记录里的内部字段也会进入 payload，所以应按 UI 需要裁剪。
- `generatedAt`：`Date` 是 React RSC 支持的可序列化类型，可以传。
- `options`：普通对象，且其中只有序列化标量，可以传。要避免把函数或类实例塞进对象。
- `onSelect`：普通箭头函数不能跨 Server -> Client 边界。若点击需要在服务端执行逻辑，应使用 `'use server'` 的 Server Function 引用（通常作为 form action，或通过客户端可调用的 action）；如果只是客户端交互，处理函数应定义在 Client Component 内部。

安全：`orders` 每项带有 `internalNote`、`costPrice` 时，它们会随 props 进入 RSC payload，浏览器用户可以看到。`server-only` 只防止模块被错误 import，不会自动脱敏。修复至少包括：

1. 在服务端数据访问层/映射层构造 DTO，只返回页面需要的公开字段（不要返回整行数据库记录）。
2. 不把 `apiKey`/token/密码哈希等秘密放进任何传给 Client 的 props；`server-only` 标记数据层，配合审查/taint 做额外防护。
3. 需要服务端行为时使用 Server Function，并做鉴权、输入校验和最小返回；不要把“函数”当成普通数据硬传。

### 评分点（共 3 分）

- 1 分：正确分类 Page/Chart/format/Tooltip/orders；说明服务器源码不进浏览器、client 传递依赖进 bundle；区分首屏 HTML + RSC payload + hydration 与后续导航 RSC payload。
- 1 分：说明 `'use client'` 是模块图入口/传递依赖；Chart 不能 import server-only，Page 可以 import Chart 并拿到 client reference。
- 1 分：正确判断四个 prop（Date、普通对象可传；类实例、普通函数不可传）；指出内部字段泄露；给出 DTO、server-only、Server Function/最小化数据等修复。

### 简短解释

RSC vs SSR 的关键不是“有没有服务端渲染”，而是“Server Component 代码是否仍发到浏览器”。模块图决定打包；props 决定数据跨边界。`onSelect` 是普通函数所以过不去，`generatedAt` 是 Date 所以可以过去，但可序列化不代表可以公开。

## 第 2 题（2.5 分｜children 组合、owner/parent 与 Provider）

### 参考答案

#### 1. 错误示例为什么失败

`cart-modal.tsx` 有 `'use client'`，它是客户端模块图的入口。它 `import { Cart } from './cart'` 时，`cart.tsx` 会被拉进客户端模块图；而 `cart.tsx` 又 `import 'server-only'`，所以真实 Next.js 会在构建/打包时直接报混合边界的错误。用“模块图”解释：Client 模块的传递依赖全部进入客户端 bundle，不能在客户端图中夹带服务端模块。

关键不是“Server Component 不能被 Client 组件渲染”这句话本身，而是：

- 服务端代码（数据库、`server-only`、`fs` 等）不能进入客户端模块图。
- 客户端不能 import Server Component 的组件定义；跨边界的只能是服务端已经渲染好的 JSX/输出。
- 即使移除 `server-only` 让构建“勉强通过”，`cart.tsx` 及其服务端依赖也会被拉进客户端，可能因 Node API 失败，更可能造成敏感服务和数据泄露。所以移除 `server-only` 不是修复，只是拆掉报警器。
- 正确方向是由 Server Component 作为 owner 把 Cart 传给 Client Shell。

#### 2. 用 children 改写

```tsx
// app/ui/cart-modal.tsx
'use client'

import { useState, type ReactNode } from 'react'

export function CartModal({ children }: { children: ReactNode }) {
  const [open, setOpen] = useState(false)

  return (
    <div>
      <button onClick={() => setOpen((value) => !value)}>购物车</button>
      {open && children}
    </div>
  )
}
```

```tsx
// app/page.tsx —— Server Component，负责创建并渲染 Cart
import { Cart } from '@/app/ui/cart'
import { CartModal } from '@/app/ui/cart-modal'
import { getCurrentUserId } from '@/lib/auth'

export default async function Page() {
  const userId = await getCurrentUserId()

  return (
    <CartModal>
      <Cart userId={userId} />
    </CartModal>
  )
}
```

- **owner**：`Page` 的源码里写了 `<CartModal>` 和 `<Cart>`，所以 `Page` 是两者的 owner。`Cart` 的 owner 属于 Server Component，因此 `Cart` 在服务端执行并渲染。
- **parent**：渲染树中直接包住 `Cart` 的是 `CartModal`，所以它是 parent。但 parent 只是接收并摆放 `children` 的已有输出，没有 import Cart 的代码，也不会调用 Cart 组件。
- 点击按钮只改变 `CartModal` 的 client state `open`，重新执行的是 Client 的 `CartModal`；`children` 是上次服务端渲染得到的输出，**不会因这个 client state 变化而重新执行 Cart**。如果购物车数据需要更新，需要服务端重新渲染（例如导航、重新验证、Server Action 触发刷新）并下发新的 RSC payload。这就是“把 Server UI 当插槽传进来”的边界效果。

#### 3. Context Provider 与 Server children

Server Component 不能创建 Context，但可以渲染一个来自 Client 模块的 Provider，并把 Server 子树作为 `children` 塞进去：

```tsx
// app/providers.tsx
'use client'

import { createContext } from 'react'

export const ThemeContext = createContext<'light' | 'dark'>('light')

export function Providers({ children }: { children: React.ReactNode }) {
  return <ThemeContext value="dark">{children}</ThemeContext>
}
```

```tsx
// app/layout.tsx —— Server Component
import { Providers } from './providers'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html>
      <body>
        <Providers>{children}</Providers>
      </body>
    </html>
  )
}
```

`Providers` 是 Client Component，但它只包住 `{children}`；Server Component 渲染出的布局和页面内容作为 children 传入，仍然在服务端渲染。Provider 应尽量放深（只包需要它的子树），而不是无条件包住整个文档或整个应用，这样能让更多静态 Server 内容保持可优化/可缓存。

### 评分点（共 2.5 分）

- 1 分：从客户端模块图和传递依赖解释为什么 import Server-only 的 Cart 会失败；指出移除 server-only 不是正确修复，客户端 bundle 不应包含服务端代码。
- 1 分：用 `children` 正确改写 Client Shell 和 Server 调用方；说明 owner/parent 分离；说明 client state 变化不会重新执行 Server Cart，更新需要新的服务端渲染/payload。
- 0.5 分：给出 Client Provider 接收 Server children 的模式，并说明 Provider 应尽量放深。

### 简短解释

Server Component 能“出现在” Client Component 的子树里，是因为它先在服务端渲染，再把输出作为 children 传入；而不是因为 Client 能 import 它。owner 决定代码在哪个模块图里，parent 决定渲染树中的位置。不要把这两件事混为一谈。

## 第 3 题（2.5 分｜跨边界序列化、安全与误区）

### 参考答案

#### 1. 逐项判断

- `user`：假设是 `getUserRecord()` 返回的类实例（Prisma model 或带方法的对象），真实 RSC 不支持类实例跨边界，会报错。即使改成普通对象，直接传数据库记录也会有过量字段泄露风险；应映射成普通 DTO。
- `lastSeen`：`Date` 是支持的可序列化类型，可以传。
- `flags`：`Set` 本身是 React RSC 支持的 Iterable 类型，可以传，前提是内部的字符串等元素都可序列化。注意本练习的 ex2 只模拟更严格的子集，会拒绝 `Set`；不要把练习子集当成 React 的真实上限。
- `apiKey`：字符串本身可序列化，因此**序列化检查不会阻止它**；但它是密钥，绝不能从 Server 传给 Client。合法可序列化 ≠ 安全。
- `onLogout`：这里是一个普通的异步闭包函数，不是 Server Function，也没有从客户端模块导出，不能跨 Server -> Client 边界。修复可以是在 Client 内定义登出交互逻辑，或者定义 `'use server'` 的 Server Function 并传递其引用；服务端函数必须自行鉴权、校验输入，不能信任客户端。

#### 2. `passwordHash` 会不会到浏览器？怎么修？

会。只要 `user` 被作为 prop 传给 `ClientProfile`，React 会尝试把它序列化进 RSC payload；如果它是可序列化的普通对象，`passwordHash` 会原样到达浏览器（用户可在 DevTools/Network 中看到）。如果是类实例而序列化失败，用户可能看不到 payload，但这是“报错”不是“安全”。无论哪种情况，都不应把整行数据库记录交给边界。

修复顺序：

1. **数据最小化/DTO**：在服务端只构造 `{ id, name, avatarUrl, bio }` 这类 UI 需要的字段，明确不带 `passwordHash`、内部备注、权限位等。
2. **`server-only`**：把数据访问/映射模块标记为 `import 'server-only'`，防止它被客户端图错误 import；但记住它不负责检查 props 内容。
3. **行为用 Server Function**：登出等服务端操作写成 `'use server'` 函数；在函数内重新验证 session/权限，返回最小结果。不要传 `apiKey`，环境变量只在服务端使用。
4. **额外防线**：React Taint API（实验性）可以帮忙让指定对象/值无法被传过边界；生产项目仍要靠代码审查、类型/DTO 和测试。

#### 3. 三句话纠正

1. **“`'use server'` 就是 Server Component 的标记。”** 错。Server Component 没有专用指令，App Router 的页面/布局默认就是 Server Component；`'use server'` 标记的是 Server Functions（可从客户端调用的服务端函数）。
2. **“用了 RSC 就不需要 hydration 了。”** 错。Server Component 不进浏览器 bundle，但 Client Components 仍然要下载 JS 并在浏览器 hydration，才能绑定事件、运行 state 和 Effect。RSC 减少的是 Server Component 的代码，不是所有客户端交互。
3. **“Client Component 永远不会在服务端执行。”** 错。首次访问时 Client Component 会被预渲染成 HTML（在服务端执行），然后在浏览器 hydration；后续客户端导航时可能只在浏览器渲染。更准确的说法是：Client Component 既进入浏览器，也可能在服务端预渲染；Server Component 的代码只在服务端图运行，不进浏览器。

### 评分点（共 2.5 分）

- 1 分：正确判断四类值的序列化：Date/Set 支持、普通函数与类实例不支持、apiKey 可序列化但不可安全传递；能把序列化与安全分开。
- 1 分：明确 `passwordHash` 会进入 RSC payload（或序列化失败），给出 DTO、server-only、Server Function/鉴权、最小化等修复。
- 0.5 分：三条误区全部纠正：`'use server'` 不是 Server Component 标记、仍需要 hydration、Client Component 也参与首屏服务端预渲染。

### 简短解释

RSC 的序列化能力只回答“这个值能不能过网络边界”，不回答“该不该让用户看到”。`server-only` 防止模块进入客户端图，但不能自动删掉你主动传出的字段；真正可靠的保护是数据最小化、鉴权和最小返回。
