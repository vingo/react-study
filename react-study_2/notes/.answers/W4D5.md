## 复习 1（0.5 分｜index key 与 state 身份）

### 参考答案

1. **`hello` 会出现在 B 的输入框里。** 删除 A 后列表变成 `[B, C]`，但 key 仍是 `0, 1`。React 在同层按“位置 + 类型 + key”复用：旧 key `0` 的 `Row`（持有 `hello`）被复用来渲染 B，旧 key `1` 的 `Row`（空）被复用来渲染 C。A 对应的 state 并没有被“销毁”，而是留在位置 0 上被 B 继承；C 的 `Row` state 仍在位置 1。
2. **改成 `key={item.id}` 后，`hello` 随 A 一起销毁。** 新列表的 key 是 `b, c`，旧 key `a` 没有匹配，React 删除 A 的 Fiber/DOM/state；B、C 分别按 key 匹配到原来的 Row，备注保持为空。焦点、输入框 DOM、组件 state 都跟着 key 走。
3. **解释角度。** 协调阶段只比较同层元素；index key 让“位置”成为身份，列表删除/插入时位置上的数据换了，但 state 仍按位置保留。commit 阶段会更新文本、删除多余的 DOM，但不会因为“A 被删了”就自动把 `hello` 也删掉——state 绑定的是 Fiber 身份，不是数据对象。render 阶段计算新树时，旧 DOM 还是上一次 commit 的结果；真正移除 A 的 DOM 发生在 commit。

一句话：**key 是身份，不是索引；用 index 当 key，等于告诉 React“位置就是身份”。**

### 评分点（共 0.5 分）

- 0.25 分：正确判断 `hello` 出现在 B 的输入框，并说明是位置/key 复用导致 A 的 state 被 B 继承（只说“index key 不好”不给分）。
- 0.25 分：正确说明 `key={item.id}` 时 A 被卸载、B/C 保留自己的 state；能提到 Fiber/协调按同层 type + key 匹配，或 render/commit 的分工。

### 简短解释

index key 在列表稳定时问题不大；一旦插入、删除、排序，位置与数据错位，state 就跟着错位。稳定业务 ID 才能让 state、DOM、焦点和 Effects 跟随正确的数据。

## 复习 2（0.5 分｜URL / Query / Zustand 的三份真相）

### 参考答案

**至少两处问题：**

1. **筛选有两份真相。** 组件从 Zustand 读 `status`，却完全忽略 URL 的 `searchParams`。用户切换筛选只改 store，URL 不变：刷新后 store 可能恢复默认值（或 persist 的旧值），分享链接/前进后退也无法还原筛选；浏览器后退不会触发 store 更新。正确 owner 是 URL。
2. **queryKey 没有包含 status。** `['cards']` 不随筛选变化，切换筛选时 Query 会命中同一份缓存，可能直接返回旧数据、不按新 status 请求；即使函数闭包读到了新 status，缓存地址也没变，失效和共享都会错乱。key 应包含所有影响结果的参数，例如 `['cards', { status }]`。
3. **服务端数据被复制进 local state。** `useState(data ?? [])` + `useEffect(() => setCards(data))` 制造了第三份真相：Query 后台刷新、失效、乐观更新都不会自动同步到 `cards`；Effect 还会多一轮 render，并可能在切换时短暂显示旧列表。应直接渲染 `data`。

**修正后的归属：**

- 筛选：URL 的 `searchParams`，setter 用 `setSearchParams` 写回；Zustand 不再存筛选。
- 查询键：`['cards', { status }]`（或 `['cards', status]`），确保筛选变化就是新缓存条目；Query 直接渲染 `data`。
- 服务端数据：TanStack Query 是唯一 owner；不要再 `setCards` 复制。Zustand 只留真正的客户端全局状态（如 sidebar、presence）。

### 评分点（共 0.5 分）

- 0.25 分：指出筛选与 URL 脱节（刷新/分享/后退失效），或 queryKey 缺 status 导致缓存不更新；指出服务端数据复制进 state 造成第三份真相。
- 0.25 分：给出正确归属（URL / key 含 status / 直接渲染 Query data），并说明“同一份数据只设一个 owner”。

### 简短解释

三道题其实是一条原则：**owner 不清，所有工具都会互相打架**。URL 负责可分享状态，Query 负责服务端缓存，Zustand 只负责客户端全局；把它们混在一起，刷新、后退、失效、乐观更新总有一个对不上。

## 第 1 题（3 分｜Kanban v4 架构白板）

### 参考答案

#### 1. 边界表（1.25 分）

| 模块 | 边界 | 数据来源 | 路由 | 缓存 tag | 失效点 |
|---|---|---|---|---|---|
| 看板快照 | Server（RSC） | 服务端 fetch | `/boards/:boardId` | `board:${boardId}` | 移动/编辑/创建卡片成功后 |
| 筛选栏 | Client | URL `searchParams` | `/boards/:boardId?assignee=&q=` | 无 | 不失效，导航即变 |
| 拖拽画布 | Client 岛屿 | RSC 初始 props + `useOptimistic` | `/boards/:boardId` | 读 `board:${boardId}` | 调用 Server Action 后失效 board tag |
| 实时评论 | Client | TanStack Query + 订阅 | `/boards/:boardId`（评论组件） | `comments:${boardId}` | 发/删评论成功后 |
| presence | Client | Zustand / WebSocket | 同看板 | 无 | 过期即丢，不持久化 |
| 权限设置 | Server（RSC） | 服务端 fetch | `/boards/:boardId/settings` | `members:${projectId}` | 角色变更成功后 |
| 审计日志 | Server（RSC） | 服务端 fetch | `/boards/:boardId/settings/audit` | `audit:${projectId}` | 新审计记录写入后 |

路由树：

```text
/boards                              RSC：看板列表
/boards/:boardId                     RSC：认证 + 项目/看板归属，渲染快照
/boards/:boardId/cards/:cardId       RSC：卡片详情
/boards/:boardId/settings            RSC：权限门禁
/boards/:boardId/settings/audit      RSC：审计日志
```

页面段默认都是 Server Component；`'use client'` 只标记筛选栏、拖拽画布、评论、presence 这些交互岛屿/订阅。

#### 2. 状态放置与双写（1 分）

**看板快照不复制进 Zustand 的原因：**

- 它是服务端状态：真相在数据库，受权限过滤，可能被其他人修改；Zustand 只是浏览器内存，不解决缓存、去重、失效、重试。
- 复制会造成两份真相：`revalidateTag`/RSC 刷新只更新服务端与 RSC payload，刷不到 Zustand 里的旧数组；用户会看到“服务端已变、界面没变”。
- 2000 张卡片的快照放进全局 store 还会增加内存、序列化和 hydration 负担，并让权限数据在客户端多留一份。

**如果客户端也要用 Query 缓存看板，只能二选一：**

- 方案 A（推荐）：RSC 是 owner。RSC 取数后把初始快照作为可序列化 props 传给客户端岛屿；客户端不另建同数据的 Query 条目，实时/乐观只在岛屿内做临时层，成功后靠 Action + tag 刷新 RSC。
- 方案 B：Query 是 owner。RSC 只渲染 shell，客户端用 Query 取数；需要 SSR 时用 `dehydrate`/`HydrationBoundary` 把同一 QueryClient 的缓存传给客户端，绝不能再用 `setQueryData` 双写一遍。关键是“同一份数据只设一个 owner”。

**评论与 presence 不是同一种状态：**

- 评论是服务端状态：需要持久化、按 board 缓存、失败重试、失效与多用户同步，归 TanStack Query（配实时订阅）。
- presence 是瞬态客户端状态：谁在线、正在拖哪张卡，断开即失效，不需要服务端历史与缓存，高频更新且只影响局部 UI，归 Zustand/selector 或 WebSocket 客户端状态。把 presence 放进服务端缓存会制造无意义的 tag 和失效。

#### 3. 加载/错误与测试（0.75 分）

**加载/错误三层：**

- **页面级**：`loading.tsx` 或 Suspense 骨架负责首屏/慢 RSC；`error.tsx`/Error Boundary 负责取数失败与重试；错误边界要按路由段放置，避免整页被替换。
- **查询级**：Query 的 `isPending`/`isError`/`error` 负责评论等客户端数据；`placeholderData: keepPreviousData` 保留旧列表，失败提供重试。
- **交互级**：`useTransition` 的 `isPending` + `useOptimistic` 负责移动卡片；失败回滚并显示 `role="alert"`；按钮禁用防重复提交。

**测试策略：**

- 决策层单测：`planKanban` 的边界/路由/tag；`moveCardAction` 的未登录、越权、非法输入、跨看板、成功、persist 失败回滚。
- 组件集成：Testing Library + 注入 action/deferred promise，断言乐观态、pending、回滚、服务端结果收敛；筛选用 URL 变化断言列表。
- 路由/RSC/E2E（本机可用 Playwright 时）：深链、登录/权限、缓存失效后看到新数据；MSW 模拟接口失败与延迟。
- 回归：每个 bug 留一条先红后绿的测试；性能只做趋势护栏。

### 评分点（共 3 分）

- 1.25 分：七个模块的 Server/Client 划分基本正确（0.5）；数据来源正确（0.25）；路由树补全（0.25）；tag 与失效点合理（0.25）。权限/审计若放客户端，该项最多 0.5。
- 1 分：说明看板快照不复制进 Zustand 的理由（服务端真相/失效/权限/内存，0.4）；给出 RSC 与 Query 二选一或 HydrationBoundary 的单 owner 方案（0.3）；区分评论（服务端状态）与 presence（瞬态客户端状态）（0.3）。
- 0.75 分：三层加载/错误（0.4）；三层测试 + 关键安全/回滚用例（0.35）。

### 简短解释

架构题不考 API 名称，考“每份数据的 owner 和信任边界”。页面段留在服务端，交互下沉为客户端岛屿；看板快照、评论、权限、审计各有缓存 tag；presence 和筛选分别归 Zustand 与 URL。只要 owner 清楚，RSC、Query、Zustand 就不会互相打架。

## 第 2 题（2.5 分｜Server Action 安全评审）

### 参考答案

#### 1. 至少 5 个问题（1.25 分）

1. **相信客户端的 `canEdit`。** 客户端可以随便构造 FormData，把 `canEdit` 设为 `true`；按钮显隐只是 UX，不是授权。服务端必须根据 session + 项目成员表判断角色。
2. **相信客户端的 `projectId`。** 攻击者可以传另一个项目的 ID，配合 `where: { id: cardId, projectId }` 尝试越权更新；项目归属必须从卡片/看板关系在服务端推导，不能由客户端提供。
3. **只有认证，没有授权。** `if (!session)` 只回答“你是谁”，没有检查用户是不是该项目成员、角色是不是 owner/editor；viewer 或外部用户也能通过直接调用 Action 改卡。
4. **没有输入校验。** `cardId`/`toListId` 可以是空串、任意字符串；`toIndex` 完全没有；`toListId` 可能属于另一个看板。需要校验非空、整数、目标列表属于同一看板。
5. **没有业务归属校验/事务。** 没有确认卡片属于目标看板/项目，也没有在事务中重排 position；并发移动可能产生重复位置或半更新。真实实现要在事务里锁定并重排。
6. **错误处理粗糙。** 直接 `throw new Error` 会变成 500/泄露内部信息；应返回结构化错误码（UNAUTHENTICATED/FORBIDDEN/INVALID_INPUT/NOT_FOUND/PERSIST_FAILED），并避免把数据库错误透给客户端。
7. **缓存失效粒度过大。** `revalidateTag('cards')` 会让所有看板/卡片缓存失效，浪费且可能造成惊群；应按 `board:${boardId}`（必要时再失效 `cards:${cardId}`）。
8. **没有审计与限流/幂等。** 敏感变更应写审计日志；公开端点还需要限流、幂等（重复提交）与框架提供的 Origin/CSRF 防护。
9. **失败时没有回滚语义。** 客户端如果做了乐观更新，Action 失败必须让乐观层撤回；服务端事务失败也要回滚，不能留下部分写入。

#### 2. 安全流水线（0.75 分）

```ts
'use server'

export async function moveCard(formData: FormData) {
  // 1. 认证
  const session = await requireSession() // 401 / UNAUTHENTICATED

  // 2. 输入校验（不信任任何字段）
  const input = parseMoveInput(formData)
  // cardId/toListId 非空 string；toIndex 非负整数
  if (!input) return err('INVALID_INPUT')

  // 3. 事务内读取 + 授权 + 归属校验
  return db.transaction(async (tx) => {
    const card = await tx.card.findUnique({
      where: { id: input.cardId },
      include: { board: { include: { project: { include: { members: true } } } } },
    })
    if (!card) return err('NOT_FOUND')

    const member = card.board.project.members.find(
      (m) => m.userId === session.userId,
    )
    if (!member || (member.role !== 'owner' && member.role !== 'editor')) {
      return err('FORBIDDEN')
    }
    if (!card.board.lists.includes(input.toListId)) {
      return err('INVALID_INPUT')
    }

    // 4. 事务内移动 + 重排 position；失败自动 rollback
    await tx.card.move({
      id: card.id,
      toListId: input.toListId,
      toIndex: input.toIndex,
    })
    await tx.audit.create({
      action: 'card.move',
      actorId: session.userId,
      cardId: card.id,
      boardId: card.boardId,
    })

    // 5. 事务提交后失效该看板的 tag（不要用全局 'cards'）
    revalidateTag(`board:${card.boardId}`)
    return ok({ cardId: card.id })
  })
}
```

顺序要点：**认证 → 输入校验 → 读取实体 → 授权/归属 → 事务写入 → 提交后失效 tag**。任何一步失败都返回结构化错误，不产生写入。真实代码中 `tx.card.move` 要处理并发/行锁；`revalidateTag` 的签名与是否需要 `updateTag`/`refresh` 以 Next.js 16 文档为准。

#### 3. tag、回滚与安全公告（0.5 分）

- **粒度**：`'cards'` 是全局 tag，会让所有看板/卡片的缓存一起失效；应该用 `board:${boardId}`（该看板快照）以及必要时 `cards:${cardId}`。tag 应表达“哪些读取依赖这份数据”，失效点跟着写操作走。
- **失败回滚**：数据库事务回滚，不留下半更新；客户端 `useOptimistic` 的乐观层随 action/transition 结束自动撤回；失败时不要调用成功路径的 `revalidateTag`（或者即使调用了也只是让下次重取，不能代替回滚）。返回结构化错误供 UI 显示和重试。
- **安全公告行动项**：2025 年末披露的 RSC/Server Actions 相关 CVE 要求及时升级 `react-server-dom-*` 与框架补丁；升级后审计所有 Action 端点，确认每个都做服务端认证/授权/校验；不要依赖“客户端已经判断过”；关注官方公告、限流、日志与依赖扫描。补丁修复的是运行时漏洞，不能修复业务越权。

### 评分点（共 2.5 分）

- 1.25 分：至少 5 个有效问题，且覆盖“客户端 canEdit/projectId 不可信、缺少角色/归属授权、缺少输入/目标列表校验、无事务/回滚、tag 过宽、错误泄露/审计/限流”中的核心项。每项 0.25，最多 1.25；只说“没鉴权”给 0.25。
- 0.75 分：流水线顺序正确（认证→校验→读取→授权→事务→失效），能区分认证与授权（0.25）；输入/目标列表/项目归属校验（0.25）；事务与失败返回（0.25）。
- 0.5 分：tag 粒度合理并解释（0.25）；失败回滚 + 乐观层撤回 + CVE/升级/审计行动项（0.25）。

### 简短解释

Server Action 不是“后端的私有函数”，而是任何人都能调用的 POST 端点。客户端传来的每个字段都要当作恶意输入；权限必须从 session 和服务端关系推导。缓存失效是写成功后的副作用，不是安全边界；CVE 补丁和业务鉴权是两条独立的防线。

## 第 3 题（2.5 分｜搜索、拖拽与 2000 张卡片）

### 参考答案

#### 1. 诊断（1 分）

- `actualDuration ≈ baseDuration`（182ms vs 190ms）说明这次 commit 几乎整棵被 profiled 子树都 render 了，memoization 没有带来跳过；`CardList` 每次输入都 render 也印证了这一点。
- **瓶颈更可能在 commit/DOM 与布局**：题目明确说提交耗时主要来自 DOM 更新与布局。`memo` 只减少 render，不减少已经存在的 2000 个 DOM 节点的更新/布局；`useDeferredValue` 也只调整优先级，不减少总工作。
- **`memo` 失效的两个具体原因**：
  1. `options={{ dragging }}` 每次 `Board` render 都创建新对象，浅比较失败；
  2. `onDragStart={(id) => setDragging(id)}` 每次都是新函数，浅比较失败。
- **`useDeferredValue` 没生效的链路**：输入 `query` 变化会让 `Board` 紧急 render；即使 `deferredQuery` 还是旧值，`CardList` 仍收到新的 `options`/`onDragStart`，`memo` 放行，于是用旧查询再 render 一次；后台再 render 一次。若子组件没有 memo，deferred 基本白用。`DragOverlay` 没有 memo，也跟着每次输入 render。过滤本身 `cards.filter` 每次 render 都跑，2000 条虽不贵，但会叠加。
- 另一个关键点：**2000 张卡片全部在 DOM 里**，过滤会改变可见集合，commit 要更新/删除/插入大量节点并触发布局；这部分不是 render 优化能解决的。

#### 2. 优化顺序与复测（1 分）

1. **测量/确认**：同一条“输入一个字符”的交互，用 React Profiler 看最慢 commit、CardList/Card 的 render 与 commit、DOM 更新数量；Chrome Performance 看 layout/paint。先确认是 render 还是 DOM/layout 主导，再动手。
2. **结构/隔离**：把搜索框状态与不相关区域隔离——`DragOverlay` 只依赖 `dragging`，用 memo/拆分让它不因 `query` render；`options` 用 `useMemo`，`onDragStart` 用 `useCallback`，或直接传原始值 `dragging`，让 `CardList` 的 props 稳定。更彻底的是把输入框下沉到独立组件，只有列表区域消费 deferred 查询。
3. **虚拟化**：用 TanStack Virtual 只渲染视口内几十行，直接减少 DOM 数量和 commit 工作量；这是解决 2000 行 commit/布局的关键。虚拟化后，过滤仍要计算，但 DOM 更新量大幅下降。
4. **行级缓存**：`Card` 用 `memo`，每行的 props 保持稳定；避免在 map 里创建新对象/新回调。
5. **并发兜底**：输入值保持紧急更新；把列表查询/派生放进 transition 或继续用 deferred，保证输入不被慢列表阻塞。注意 transition 不减少 commit 的 DOM 工作。
6. **最后 Compiler**：开启后用同场景复测，看它是否自动稳定了 props/JSX；不要用它替代虚拟化。
7. **复测**：同一交互、同一 CPU 降速、同一构建模式；对比最慢 commit、DOM 更新数、输入延迟。不要断言毫秒数，性能和功能测试分开。

#### 3. Compiler 与 transition（0.5 分）

- **Compiler 能做的**：在符合 Rules of React 的前提下，自动 memo 化组件/Hook 内的表达式、回调和 JSX，可能让 `CardList` 的 `options`/`onDragStart` 引用更稳定，减少不必要的子组件 render。
- **Compiler 不能做的**：不会减少 2000 个 DOM 节点，不会消除过滤/布局/commit 成本，不会把非虚拟列表变快；它主要改善更新时的 render 级联，不替代虚拟化、拆分和测量。
- **transition 的正确用法**：受控 input 的 `value` 必须同步更新，不能放进 transition；可以把“列表使用的查询值”放到另一个 state，在 `startTransition` 里更新它，或用 `useDeferredValue` 延迟列表消费。transition 只保证输入不被慢 render 阻塞，commit 仍是同步的；如果 commit/DOM 本身很重，必须靠虚拟化/减少 DOM 解决。

### 评分点（共 2.5 分）

- 1 分：正确读出 `actualDuration ≈ baseDuration` 的含义（0.25）；判断瓶颈在 commit/DOM/布局而非单纯 render（0.25）；指出 `options` 与 `onDragStart` 两个新引用击穿 memo（0.3）；解释 deferred 与 memo 的配合/失效链路（0.2）。
- 1 分：给出“测量 → 结构/稳定 props → 虚拟化 → 行级缓存 → 并发 → Compiler → 复测”的合理顺序（0.5）；每一步有验证方式，复测同场景/同条件（0.3）；明确虚拟化解决 DOM 数量（0.2）。
- 0.5 分：Compiler 的能与不能（0.25）；受控输入不能进 transition、transition 不减少 commit 工作（0.25）。

### 简短解释

这道题把所有性能工具放在一起：`memo` 管 render 级联，deferred/transition 管优先级，虚拟化管 DOM 数量，Compiler 管构建期自动缓存。Profiler 的数字先告诉你“哪一层贵”；如果 commit/DOM 是主因，继续堆 render 优化只会原地打转。受控输入永远保持紧急更新，延迟的是下游列表。
