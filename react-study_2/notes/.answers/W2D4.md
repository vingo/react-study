## 复习 1（0.5 分｜Effect 的 cleanup 与 setup 时序）

### 参考答案

日志顺序是（按非 StrictMode 语义）：

```text
connect general
disconnect general
connect random
disconnect random
```

开发环境的 StrictMode 会在首次挂载后额外执行一次 setup → cleanup 演练，因此会多出一对 `connect general` / `disconnect general`；`roomId` 变化和卸载的 cleanup → setup 顺序不变。

过程：

1. 首次挂载：执行 setup，连接 `general`。
2. `roomId` 从 `general` 变为 `random`：React 先执行上一次 Effect 的 cleanup（断开 `general`），再执行新的 setup（连接 `random`）。顺序是“旧 cleanup → 新 setup”，不是先建新连接再拆旧连接。
3. 组件卸载：执行最后一次 setup 对应的 cleanup，断开 `random`，之后不会再有新的 setup。

`theme` 变化不会重连，因为 `theme` 不在依赖数组中；Effect 不会重新执行，连接保持不变。但这意味着 Effect 内部（包括连接成功后的回调）看到的 `theme` 是 Effect 上次执行那一轮的闭包值，可能是旧的。若连接成功回调需要读取最新 `theme`、又不希望 `theme` 变化触发重连，应把读取 `theme` 的那段逻辑包进 `useEffectEvent`：

```tsx
const onConnected = useEffectEvent(() => {
  showToast(`已连接，当前主题：${theme}`)
})

useEffect(() => {
  const conn = connect(roomId)
  conn.onConnected(onConnected)
  return () => conn.close()
}, [roomId])
```

`useEffectEvent` 里的函数总能读到最新的 props/state，但它本身不进入依赖数组；依赖数组仍只写 `[roomId]`。不要为了拿最新 `theme` 把 `theme` 加进依赖，否则每次切换主题都会重连。若连接参数本身必须在建立连接时使用 `theme`，那就是另一回事：此时重连是语义要求，`theme` 应当进入依赖。

### 评分点（共 0.5 分）

- 0.3 分：日志顺序完全正确，明确“roomId 变化时先 cleanup 旧连接，再 setup 新连接”，卸载时执行最后一次 cleanup。
- 0.2 分：指出 theme 不在依赖中所以不重连；能说出闭包可能读到旧 theme；正确使用 `useEffectEvent`（或等价的 ref 方案）读取最新值且依赖仍为 `[roomId]`。

### 简短解释

Effect 的 cleanup 属于“上一次 Effect”，不是“下一次 Effect 的开头”。依赖变化时 React 先清理旧的外部系统连接，再建立新的；卸载时只清理最后一次。Effect Event 用来把“需要最新值、但不应该触发重跑”的读取从响应式依赖中分离出来。

## 复习 2（0.5 分｜Error Boundary 重试与请求竞态）

### 参考答案

1. 点击“重试”后很可能立刻又回到错误 UI，因为 `commentsPromise` 的 `useMemo` 依赖只有 `[postId]`。`setAttempt` 让组件重渲染，但 `attempt` 不在依赖里，`useMemo` 仍返回**同一个已 rejected 的 promise**。`resetErrorBoundary()` 只是把 Error Boundary 从错误状态复位，让它重新渲染 children；children 一读到同一个 rejected promise，又立刻抛出同一个错误，fallback 再次出现。
   两件事都必须做：
   - 重置边界：`resetErrorBoundary()`；
   - 换一个新的 promise：把 `attempt` 放进依赖，例如 `useMemo(() => fetchComments(postId), [postId, attempt])`，或者按 `attempt` 生成新的 promise/缓存键。
   只重置边界，会继续用旧 promise；只换 promise，边界仍停留在错误状态，不会渲染 children。两者缺一不可。
2. 当前 `ErrorBoundary` 没有 `key`。错误 UI 显示时把 `postId` 从 A 改成 B，用户仍会看到 A 的错误 fallback：`postId` 变化会让父组件重渲染，但 Error Boundary 自身的错误状态还在，它不会自动尝试渲染 B 的 children。`key` 应加在 `ErrorBoundary` 上（或加在包含 Error Boundary 与 Suspense 的更上层），例如 `<ErrorBoundary key={postId} ...>`。这样 postId 变化会重建边界、清空错误状态。只给 `Suspense` 或 `CommentsList` 加 key 不够，因为错误状态在边界自身。
3. 最终会显示 **A** 的数据。A 的响应后到，执行 `setComments(A)`，把 B 已经写入的数据覆盖掉。用 cleanup 让旧请求失效：

```tsx
useEffect(() => {
  let ignore = false

  fetchComments(postId)
    .then(data => {
      if (!ignore) setComments(data)
    })
    .catch(err => {
      if (!ignore) setError(err)
    })

  return () => {
    ignore = true
  }
}, [postId])
```

也可以用 `AbortController`，在 cleanup 中 `abort()`，并把 `signal` 传给 fetch；catch 中忽略 `AbortError`。切换时最好同时清掉旧数据/旧错误，避免短暂显示上一个 post 的内容。

### 评分点（共 0.5 分）

- 0.2 分：指出 `useMemo` 依赖缺少 `attempt`，重试仍拿到同一个 rejected promise；说明必须同时重置边界和创建新 promise，只改一处不够。
- 0.15 分：指出没有 `key` 时边界错误状态会跨 postId 保留；key 应加在 ErrorBoundary 或更上层。
- 0.15 分：正确预测旧响应覆盖新数据；给出 ignore 标记或 AbortController 的 cleanup，并说明旧错误也要忽略。

### 简短解释

Error Boundary 的重试不是“再渲染一次”这么简单：边界状态和导致错误的 promise 身份都要更新。请求竞态则要通过 cleanup 让旧请求的结果失效；仅仅依赖“后发请求先返回”是不可靠的。

## 第 1 题（2.5 分｜嵌套路由、布局与 404）

### 参考答案

1. 访问 `/` 时只渲染 `RootLayout`：页面上有 `<Header />` 和一个空的 `<main />`。`Dashboard` **不会**渲染。`Dashboard` 是根路由的 index route，按设计应渲染到父路由的 `<Outlet />` 中；`RootLayout` 没有渲染 `<Outlet />`，所以 index route 没有出口。index route 不是独立 URL，它渲染在父路由的 URL（这里是 `/`）上。

2. 访问 `/projects/42/tasks` 时 `TaskList` **不会**渲染，页面实际仍然只有 `RootLayout` 的 Header 和空的 `<main />`。原因有两层：`RootLayout` 没有 `<Outlet />`，所以 `ProjectLayout` 根本不会渲染；即使根布局有出口，`ProjectLayout` 自身也没有 `<Outlet />`，`TaskList` 仍然没有出口。
   最小修复：在 `RootLayout` 的 `<main>` 里放 `<Outlet />`，并在 `ProjectLayout` 的 `<section>` 里也放 `<Outlet />`：

   ```tsx
   function RootLayout() {
     return (
       <div>
         <Header />
         <main>
           <Outlet />
         </main>
       </div>
     )
   }

   function ProjectLayout() {
     const { projectId } = useParams()
     return (
       <section>
         <h2>项目 {projectId}</h2>
         <Outlet />
       </section>
     )
   }
   ```

   修复后的渲染：
   - `/`：`RootLayout` + `Dashboard`（index route）；
   - `/projects/42`：`RootLayout` + `ProjectLayout` + `ProjectOverview`（index route）；
   - `/projects/42/tasks`：`RootLayout` + `ProjectLayout` + `TaskList`。

3. 子路由 loader 抛出的 404 会冒泡到最近的 `errorElement`。这条链上只有根路由有 `errorElement`，所以 `RootError` 会渲染，并且它替换的是**根路由的 element**——`RootLayout` 整体被替换，`<Header />` 不再显示，不是只替换 `ProjectOverview` 那一小块。`useRouteError()` 返回一个路由错误响应对象，关键字段包括：
   - `status: 404`；
   - `data: 'Project not found'`（`throw new Response` 的响应体文本）；
   - `statusText`：对 `new Response('Project not found', { status: 404 })` 来说通常是空字符串，除非显式传了 `statusText: 'Not Found'`；
   - `internal: false`（这是业务 loader 主动抛出的，不是路由器内部生成的）。
   `isRouteErrorResponse(error)` 为 `true`，所以 `RootError` 会走 `status/statusText` 分支。
   如果 `ProjectLayout` 自己也有 `errorElement`，那么最近边界就是 `ProjectLayout`，只会替换 `ProjectLayout` 的 element，根布局的 Header 仍会保留。

4. 访问 `/nope` 时没有任何路由匹配。Data Router 会生成一个内部的 404 路由错误响应，并交给最近的 `errorElement`；这里仍是根路由的 `RootError` 渲染，`RootLayout` 被替换。`useRouteError()` 得到：
   - `status: 404`；
   - `statusText: 'Not Found'`；
   - `data` 是包含 `No route matches URL "/nope"` 的错误字符串/错误对象；
   - `isRouteErrorResponse(error)` 为 `true`。
   如果根路由没有 `errorElement`，React Router 会显示内置的默认错误页面（404 / Unexpected Application Error），而不是应用自己的 404 UI。

### 评分点（共 2.5 分）

- 0.5 分：正确说明 `/` 只有 RootLayout，Dashboard 不渲染；原因是父路由缺少 `<Outlet />`，index route 需要父级出口。
- 0.75 分：正确说明 `/projects/42/tasks` 连 ProjectLayout 都不会渲染；指出根布局和 ProjectLayout 都需要 `<Outlet />`；修复后能说清三个 URL 各自的渲染树。
- 0.75 分：正确说明 loader 404 冒泡到根 errorElement，RootLayout/Header 被整体替换；`useRouteError` 的 status/data 正确，`isRouteErrorResponse` 为 true。
- 0.5 分：正确说明未匹配 URL 也走 404 路由错误，根 errorElement 渲染；无根 errorElement 时是默认错误页。

### 简短解释

嵌套路由的父组件通过 `<Outlet />` 给子路由留出口；index route 是父 URL 的默认子路由，不是额外的一段路径。`errorElement` 按“最近祖先”冒泡，边界替换的是它所在路由的 element，因此根边界会连布局一起替换。未匹配 URL 在 Data Router 中同样是 404 路由错误，而不是普通组件渲染。

## 第 2 题（3 分｜loader / action 的数据流）

### 参考答案

1. 首次渲染时：
   - `useLoaderData()` 返回 loader 的对象 `{ project }`；
   - `useActionData()` 返回 `undefined`（还没有执行过 action）；
   - `navigation.state` 是 `'idle'`。

   当前 `<Form>` 没有写 `method`，默认是 **GET**。用户点击“创建任务”时，浏览器/React Router 会把表单字段序列化到查询字符串，执行的是**当前路由的 loader**，不是 action。URL 会变成类似 `/projects/42/tasks/new?title=...`，`actionData` 仍然是 `undefined`，因此不会显示“标题不能为空”，也不会调用 `createTask`。GET 表单提交不会触发 action 的校验逻辑。

2. 补上 `method="post"` 后：

   **标题为空：**
   - 提交开始：`navigation.state` 变为 `'submitting'`，`navigation.formData` 含有 `title`；
   - action 执行 `await request.formData()`，读到空字符串，返回 `{ error: '标题不能为空' }`；
   - 没有 redirect，URL 不变，页面不跳转；
   - `useActionData()` 变为 `{ error: '标题不能为空' }`，`<p role="alert">` 显示错误；
   - action 正常返回（非错误状态码），React Router 会自动重新执行当前页面所有 loader：期间 `navigation.state` 可能变为 `'loading'`，完成后回到 `'idle'`。所以 loader 会再执行一次，但因为参数没变，通常拿到同样的 project。
   - 如果 action 是 `throw new Response(..., { status: 400 })` 而不是 `return { error }`，则会进入错误边界，而不是 `useActionData` 分支；这里用的是 return，所以是正常数据。

   **标题合法：**
   - action 调用 `createTask(params.projectId, title)`；
   - `redirect(...)` 只是**创建并返回一个 Response**，当前代码没有 `return` 也没有 `throw`，这个 Response 被丢弃；
   - 接着 action 返回 `{ error: null }`，所以页面不跳转，仍停留在新建页；`useActionData()` 变为 `{ error: null }`；
   - action 正常返回后 loader 仍会重新验证并执行一次；
   - 正确写法是 `return redirect(...)` 或 `throw redirect(...)`。这样 React Router 会读取 Response 的 `Location` 并导航到 `/projects/42/tasks`，目标路由的 loader 会执行。`redirect` 默认是 302。

3. pending UI 的 bug 是 `isSaving = navigation.state === 'loading'`。POST 提交到 action 期间，`navigation.state` 是 `'submitting'`，不是 `'loading'`；`'loading'` 通常出现在 action 完成后的 loader 重新验证阶段，或者 GET 导航期间。因此 action 正在写数据的那段时间，按钮既不显示“保存中…”也不禁用，用户可能重复提交。
   修法（任选其一）：
   - `const isSaving = navigation.state !== 'idle'`；
   - `const isSaving = navigation.state === 'submitting'`（只覆盖 action 阶段）；
   - 按官方 pending UI 的写法，用 `navigation.formAction === '/projects/42/tasks/new'` 判断这次提交是否属于当前表单（该值在 submitting 和后续 loading 阶段都可用来标识提交目标）。

   如果把路由 path 的 `:projectId` 改成 `:id`，`params` 的键会随之变成 `id`。当前 loader 里的 `params.projectId` 和 action 里的 `params.projectId` 都会变成 `undefined`：`getProject(undefined)` 取不到正确项目，`createTask(undefined, title)` 会把任务写到错误/不存在的位置；如果 redirect 被正确返回，URL 也会变成 `/projects/undefined/tasks`。所有读取 `params.projectId` 的地方（包括组件里的 `useParams()`）都要同步改成 `params.id`。

4. `await request.formData()` 返回一个 `FormData` 实例；`formData.get('title')` 返回 `FormDataEntryValue | null`，即 `string | File | null`。对文本 input 通常是 string；代码用 `String(... ?? '')` 把它安全地转成字符串。
   如果漏掉 `await`，`formData` 是一个 Promise，`formData.get` 不是函数，action 会抛出 `TypeError: formData.get is not a function`。这个错误会冒泡到最近的路由 `errorElement`（本题路由没有自己的 errorElement，就会到根边界），而不是被 `useActionData` 接住。也不要写 `new FormData(request)`：`FormData` 构造函数不接受 `Request`，应该从 `request.formData()` 读取请求体。
   另外，v8 中不要写 `return json({ ... })`；`json` 已被移除。直接 `return { ... }`，需要状态码/headers 时用 `data({ ... }, { status: 201 })`。

### 评分点（共 3 分）

- 1 分：首次渲染三个值正确（loader 数据、actionData 为 undefined、navigation idle）；指出 `<Form>` 默认 GET，点击后执行 loader 而非 action，URL 带上查询参数，actionData 仍为 undefined。
- 1 分：空标题时能描述 submitting → action 返回错误对象 → 不跳转 → actionData 显示错误 → loader 重新验证；合法标题时指出裸 `redirect(...)` 被丢弃、不跳转、最终返回 `{ error: null }`，并给出 return/throw redirect 的修复。
- 1 分：指出 pending 判断应为 submitting 或非 idle（或 formAction）；参数改名后 `params.projectId` 全失效；`request.formData()` 是 Promise、`get` 返回 string/File/null，漏 await 会在 action 内抛 TypeError 并进入错误边界；能提到 v8 的 `json` 已移除。

### 简短解释

`<Form>` 的 method 决定走 loader 还是 action：GET 走 loader 并把字段放进 URL；POST 才调用 action。action 返回普通对象供 `useActionData` 读取；`redirect()` 只有被 return/throw 才会被路由器处理。提交期间的网络状态在 `useNavigation` 上：action 阶段是 `submitting`，loader 重新验证阶段是 `loading`，两者都不是 idle。loader/action 的 `params` 键名由路由 path 的动态段名字决定。

## 第 3 题（2.5 分｜URL 作为状态）

### 参考答案

1. 用户只是在输入框里输入 `router` 时，loader **不会**执行。`setSearch` 只改变组件的本地 state，URL 没有变化，也没有发生导航；React Router 不会因为本地 state 变化而重新验证 loader。输入框显示 `router`。
   点击“搜索”后，`setParams({ q: 'router', page: '1' })` 会发起一次导航；默认是 push，会新增一条历史记录。URL 变为 `/tasks?q=router&page=1`。由于 search params 发生变化，`/tasks` 的 loader 会重新执行，返回新的 `q`、`page` 和 tasks。`TaskList` **不会重新挂载**：还是同一个路由、同一个组件实例，只是 `useLoaderData()` 的数据更新了。此时 `q` 是 `'router'`，`page` 是 `1`，`search` 也是 `'router'`（用户已经输入过）。`useEffect` 的依赖 `[q]` 从 `'react'` 变成 `'router'`，所以会执行，把 `search` 再设为 `'router'`（值相同，不会造成可见变化）。
   注意：用对象调用 `setParams` 会**替换整个查询字符串**，不是合并；如果 URL 里还有其他参数，这次搜索会把它们丢掉。

2. 点击“下一页”后 URL 变为 `/tasks?q=react&page=3`，`sort=due` **不在了**。因为 `setParams({ q, page: String(page + 1) })` 把整个 search 替换成只含 `q` 和 `page` 的新字符串。要保留现有参数，应基于当前 params 复制后修改：

   ```tsx
   setParams(prev => {
     const next = new URLSearchParams(prev)
     next.set('q', q)
     next.set('page', String(page + 1))
     return next
   })
   ```

   或者显式把 `sort` 等参数一起带上。注意 `useSearchParams` 的函数式更新不像 React 的 `setState` 那样支持同一 tick 内多次排队；一次更新里完成复制和修改即可。

3. 历史记录依次是：
   1. `/tasks?q=react&page=1`
   2. `/tasks?q=vue&page=1`
   3. `/tasks?q=vue&page=2`

   连续两次后退：
   - 第一次后退到 `?q=vue&page=1`：这是一次 POP 导航，loader 会执行（search params 变了），`useNavigationType()` 返回 `'POP'`。`TaskList` 不重新挂载，`q` 为 `'vue'`、`page` 为 `1`；输入框仍是 `vue`。
   - 第二次后退到 `?q=react&page=1`：同样是 POP，loader 执行，`useNavigationType()` 返回 `'POP'`；`q` 变为 `'react'`、`page` 为 `1`。`useEffect` 的依赖 `[q]` 变化，执行 `setSearch('react')`，所以输入框显示 `react`。

   也就是说，URL 的前进/后退会重新驱动 loader，组件实例和本地 state 默认保留；这里正是 Effect 把 URL 中的 `q` 同步回输入框的草稿 state。若用户在后退前又输入了未提交的草稿，后退时该草稿可能被 URL 的值覆盖，这是“本地草稿 + URL 状态”并存的常见取舍。

4. 用户输入 `vue` 但没点搜索，直接点“下一页”：
   - `q` 仍来自 loader，是 `'react'`；点击处理函数用的是 `setParams({ q, page: String(page + 1) })`，不是 `search`；
   - URL 变为 `/tasks?q=react&page=3`；
   - 列表显示 `react` 的第 3 页结果；
   - 输入框仍显示本地草稿 `vue`。因为 `q` 从 `'react'` 到 `'react'` 没有变化，`useEffect` 不执行，不会把输入框重置。
   于是输入框（`vue`）和列表/URL（`react`）不一致。根因是同一份“搜索词”有两个来源：本地 `search` 草稿和 URL 中的 `q`，而“下一页”只读取了后者。

   两种避免设计：
   - **让 URL 成为唯一来源**：输入框的 `value` 直接来自 `params.get('q') ?? ''`，`onChange` 里更新 URL（可配合防抖）；“下一页”也从 URL 读取。这样不存在两份状态。
   - **保留草稿，但显式处理未提交值**：点“下一页”时把草稿一起写进 URL（`q: search`），或者在 `search !== q` 时禁用翻页/提示先搜索，或者在页码变化时把草稿重置为 `q`。更符合 HTML 的做法是用 `<Form method="get">`，让 input 的 `name="q"` 和隐藏的 `page` 一起提交，由浏览器/React Router 统一生成 URL。

### 评分点（共 2.5 分）

- 0.5 分：输入时不执行 loader（URL 未变）；点击搜索后 loader 执行、组件不重挂载、q/page/search 的值正确；知道 search 变化会触发 loader 重新验证。
- 0.75 分：正确指出 `sort` 被丢掉，原因是对象参数替换整个 search；给出基于 `new URLSearchParams(prev)` 的函数式修复。
- 0.75 分：两次后退都是 POP、loader 都会执行；q/page 变化正确；第二次后退输入框被 Effect 同步为 `react`。
- 0.5 分：正确描述草稿未提交时点下一页造成的 URL/列表/输入框不一致；指出两个状态源；给出至少两种合理设计。

### 简短解释

URL 是路由的数据源：`useSearchParams` 的 setter 本质是导航，search params 变化会重新执行 loader，但不会重新挂载同路由组件。对象形式的 setter 会替换整个查询字符串，需要保留其他参数时先复制再改。本地草稿 state 和 URL 状态并存时，必须明确谁是唯一真相，否则“下一页”这类只读 URL 的操作会和输入框里的未提交值分叉。
