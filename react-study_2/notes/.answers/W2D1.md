## 复习 1（1 分｜key 重置 state）

### 参考答案

1. Ada 里输入 `hello` 后，三个时刻都显示 `hello`：切到 Grace 时仍是 `hello`，切回 Ada 仍是 `hello`。因为 `Chat` 在 `Messenger` 返回树中的位置和类型都没变，又没有 key，React 按「同位置 + 同类型」复用同一个组件实例，`draft` state 被保留。
2. 最小改动：`<Chat key={contact.id} contact={contact} />`。联系人变化 -> key 变化 -> React 卸载旧 `Chat`、挂载新 `Chat`，草稿和所有后代 state 一起重置。
3. `key={Math.random()}` 每次渲染都会生成新 key，等于每次渲染都卸载并重建整个 `Chat` 子树：草稿丢失、输入框失焦、性能变差，也无法再按“联系人身份”复用组件。若只是“发送成功后清空草稿”，用 key 重置会重建整个子树，范围过大；应在 action 或事件处理函数中 `form.reset()` / `setDraft('')`，或让 action 返回后清空。

### 评分点（共 1 分）

- 0.4 分：三个时刻都保留 `hello`，并指出同位置同类型复用 state。
- 0.3 分：给出 `key={contact.id}`（稳定、绑定业务身份）。
- 0.3 分：说明随机 key 每次渲染都重建；并指出发送后清空草稿不应靠 key 重置（重置范围过大，`form.reset()`/`setDraft('')` 更合适）。

### 简短解释

key 是同级组件的身份标签；身份变化才重置 state。它适合“切换到另一个收件人”，不适合“提交成功后清空当前表单”。

## 复习 2（1 分｜Effect 职责边界）

### 参考答案

1. 第一次点击「发送」发 **1 次**请求：`setSubmitted(true)` 改变 state，Effect 在 commit 后运行并 `fetch`。
2. 修改文字后再次点击「发送」，**不会再发请求**。`submitted` 已经是 `true`，`setSubmitted(true)` 的值相同，React 会在该 state 上 bail out；Effect 的依赖 `[submitted]` 没有变化，所以不会重新执行。只有第一次提交有效。即使把 `text` 补进依赖，也不能解决“第二次点击没有状态变化”的问题。
3. 提交是用户动作，应放在事件处理函数或 form action 中。React 19 写法：

```tsx
async function sendComment(formData: FormData) {
  await fetch('/api/comments', {
    method: 'POST',
    body: String(formData.get('comment')),
  })
}

function CommentForm() {
  return (
    <form action={sendComment}>
      <textarea name="comment" />
      <button>发送</button>
    </form>
  )
}
```

需要 pending 或返回结果时，再配合 `useActionState` / `useFormStatus`。

4. 职责边界：render 计算 UI；事件处理函数/action 处理由用户动作触发的一次性副作用；Effect 只用于让组件与 React 外部的系统保持同步。

### 评分点（共 1 分）

- 0.25 分：第一次点击发 1 次请求。
- 0.4 分：第二次点击不发请求，并正确解释“同值 setState bail out + Effect 依赖未变”。
- 0.35 分：改写成 form action（或事件处理函数）并把提交放进 action/事件；能说清 render / 事件 / Effect 的边界。

### 简短解释

Effect 不是“提交表单”的工具。把一次用户动作编码成 `submitted` state，既多了一次 render-Effect 往返，又会在“再次执行同一个动作”时因为 state 值没变而静默失效。

## 第 1 题（2 分｜useActionState 的签名与返回值）

### 参考答案

1. `await` 期间：`state` 仍然是上一次提交后的状态，即初始的 `{ count: 0, message: '' }`；`isPending` 为 `true`。按钮显示「提交中…」且被禁用，段落显示 `0 `（message 为空）。本次 `increment` 收到两个实参：
   - `prev`：`{ count: 0, message: '' }`
   - `formData`：包含 `delta = "2"` 的 `FormData`

   1 秒后 action resolve，`state` 变为 `{ count: 2, message: '+2' }`，`isPending` 回到 `false`。

2. 两次快速提交（假设都成功触发）时，React **排队顺序执行**，不会并发。第一次 `prev` 是 `{ count: 0, message: '' }`，返回 `{ count: 2, message: '+2' }`；第二次 `prev` 是第一次的返回值 `{ count: 2, message: '+2' }`，返回 `{ count: 4, message: '+2' }`。最终 `state.count = 4`，`state.message = '+2'`。`isPending` 会一直为 `true`，直到队列中的 action 全部结束。

3. 写成 `const [state, isPending, formAction]` 后：
   - 第二个元素实际是 dispatch 函数，函数是 truthy，所以 `disabled={isPending}` 会让按钮**始终禁用**。
   - 第三个元素实际是布尔值，`<form action={formAction}>` 拿到的是 `false`/`true` 而不是函数，真正的 dispatch 没有被传给表单，提交不会执行 `increment`，state 也不会更新。

   正确顺序是 `[state, formAction, isPending]`。`useActionState(action, initialState, permalink?)` 的**第三个参数**是可选字符串 `permalink`（用于 Server Function 的渐进增强：JS 尚未加载时提交表单会导航到该 URL），它不是返回值。

### 评分点（共 2 分）

- 0.75 分：pending 期间 state 保持旧值、`isPending=true`、按钮/段落文字正确，且能写出 action 收到的 `prev` 与 `FormData`。
- 0.75 分：两次调用按队列顺序执行，`prev` 分别正确，最终 `count=4`（message 仍为 `'+2'`）。
- 0.5 分：指出错误解构导致按钮恒禁用、form action 拿不到函数；正确顺序为 `[state, formAction, isPending]`；第三个参数是 `permalink`。

### 简短解释

`useActionState` 的 action 是“带副作用的 reducer”：第一次接收 `initialState`，之后接收上一次的返回值；每次 dispatch 都在 Transition 中执行，`isPending` 覆盖整个队列，直到全部结束。返回数组只有三项，`permalink` 是第三个入参。

## 第 2 题（2 分｜useFormStatus 的作用范围）

### 参考答案

1. 只有 `SaveButton` 里的按钮会在提交期间禁用。「外层保存按钮」**不会**禁用，因为它的 `disabled` 用的是 `ProfileForm` 里的 `pending`，而那个 `pending` 永远是 `false`。
2. `ProfileForm` 里的返回值是 `{ pending: false, data: null, method: null, action: null }`。不会报错，只是读不到状态。
3. 原因：`useFormStatus` 读取的是**最近的父级 `<form>`** 通过 context 提供的提交状态。`ProfileForm` 是渲染 `<form>` 的组件：调用 Hook 时，这个 form 是它的**子节点**，不是父节点，所以读不到。它也不会读取同一个组件或子组件里渲染的 form；若外层还有祖先 form，它只会报告那个祖先 form。修复：把 Hook 移到一个作为 `<form>` 子组件的组件中，例如：

```tsx
function FormFooter() {
  const { pending, data } = useFormStatus()
  return (
    <>
      <button type="submit" disabled={pending}>外层保存按钮</button>
      {pending && <p>正在提交：{String(data?.get('nickname'))}</p>}
    </>
  )
}

// <form action={save}> 内：
// <SaveButton />
// <FormFooter />
```

4. `SaveButton` 中的 `data` 是本次提交的 `FormData` 快照，`data.get('nickname')` 能拿到提交时的昵称。提交期间用户继续编辑输入框，`data` **不会**跟着变；它是提交开始时的数据，不是实时的受控值。

### 评分点（共 2 分）

- 0.75 分：只有 `SaveButton` 禁用；外层的 `pending` 为 false，并指出“必须读取父级 form”的原因。
- 0.5 分：`ProfileForm` 返回 `pending:false, data:null`（method/action 为 null），不报错。
- 0.5 分：用“form 的子组件”修复，并能说明它读不到同组件/子组件渲染的 form。
- 0.25 分：`data` 是提交快照，提交期间编辑不会改变它。

### 简短解释

`useFormStatus` 不是读“我所在的组件有没有 form”，而是读“我的父级 form 正在提交吗”。Hook 的调用位置必须在 form 子树内部，因此通常要专门抽一个 `SubmitButton` / `FormFooter` 子组件。

## 第 3 题（3 分｜useOptimistic 的纯函数约束与撤销时机）

### 参考答案

1. 更新函数有两个纯度问题：
   - `current.push(...)` **原地修改**了传入的数组，并且返回同一个引用。`current` 就是 `todos` prop 指向的数组，这等于在 render/更新计算期间修改父组件的数据。
   - 在更新函数里调用 `crypto.randomUUID()`。随机值属于副作用，每次重放都会得到不同 ID。

   React 对 `useOptimistic` 的 reducer/updater 要求是纯函数（与 `useReducer` 一样）：不修改参数、不生成随机值、不依赖当前时间。StrictMode 或 React 重放/重试该函数时，`push` 可能执行两次，导致同一条目出现两次；随机 ID 还会让 React 把它当成不同的列表项，造成额外重建。修正：ID 在事件/action 中生成，reducer 只返回新数组。

```tsx
const [optimisticTodos, addOptimisticTodo] = useOptimistic(
  todos,
  (current: Todo[], newTodo: Todo) => [...current, newTodo]
)

async function handleSubmit(formData: FormData) {
  const text = String(formData.get('text'))
  const newTodo = { id: crypto.randomUUID(), text } // 在 action/事件里生成
  addOptimisticTodo(newTodo)
  await createTodo(text)
}
```

2. 提交后、`await` 尚未结束时，列表会**立即**显示这条乐观条目（`optimisticTodos` 由 reducer 计算得出）。如果 `createTodo` reject，action 随抛出而结束，Transition 结束；React 不再使用乐观值，而是按 `value`（这里是当前的 `todos` prop）渲染。父组件在失败时通常没有更新 `todos`，所以条目消失，界面回到提交前。**这不是 reject 时专门的“回滚”逻辑**，而是“乐观状态只在 Action/Transition 进行期间显示”；Action 一结束（成功或失败），就以真实 `value` 为准。

3. 如果 `createTodo` resolve 了，但父组件的 `todos` 更新晚 500ms：Action 结束时真实 `todos` 还是旧数组，乐观条目会先消失，500ms 后真实数据到达又出现，造成闪烁。避免方式：让真实 state 在同一个 Action/Transition 内、在 promise resolve 前完成更新，使乐观值与真实值在**同一次 commit** 收敛（例如 action 返回服务端确认后的新列表，并用它更新真实 state；或让 `createTodo` 在 resolve 前更新父级数据）。不要用“延迟清除乐观状态”来硬撑。

4. 在既不属于 action、也没有 `startTransition` 的普通回调（如 `setTimeout`）里调用 setter：开发环境会警告；乐观值会短暂显示，然后立即恢复成 `value`，因为没有 Transition “托住”这个乐观状态。应在 action 或 `startTransition(async () => { ... })` 内调用。

### 评分点（共 3 分）

- 1 分：指出原地修改（0.5）和 reducer 内生成随机 ID（0.5），并说明 StrictMode/重放导致重复或列表项身份不稳定；给出正确写法（ID 在 action/事件中生成，reducer 返回新数组）。若只指出问题但修正不完整，最多 0.75。
- 1 分：说明 pending 时立即显示（0.25）；reject 后 Action/Transition 结束、按真实 `value` 渲染（0.5）；明确这不是 reject 专属回滚（0.25）。
- 0.5 分：说明成功但父级更新延迟时会先消失再出现，并给出“在同一次 Transition 内让真实值与乐观值收敛”的修正方向。
- 0.5 分：说明在 Action/Transition 外调用会警告、短暂显示后立即恢复。

### 简短解释

`useOptimistic` 只负责“Action 进行期间临时显示”；它的生命周期跟着 Action/Transition，而不是跟着某个错误分支。更新函数必须纯，否则 StrictMode 重放和 React 重试会放大副作用。
