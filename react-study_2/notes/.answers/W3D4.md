## 复习 1（0.5 分｜interval 的过期闭包与 cleanup）

### 参考答案

**1. 大约 3 秒后，页面显示 `已运行 1 秒`。**

`useEffect` 的依赖数组是 `[]`，所以 interval 只在首次挂载时创建一次。回调闭包捕获的是**首次 render 时的 `seconds`**，它的值一直是 `0`：

- 第 1 个 tick：`setSeconds(0 + 1)`，队列中的新值为 `1`，React 渲染 `1`。
- 第 2 个 tick：闭包里的 `seconds` 仍是 `0`，再次 `setSeconds(1)`。`Object.is(1, 1)` 为 true，React 认为 state 没有变化，直接 bail out，不重新渲染。
- 第 3 个 tick：仍然是 `setSeconds(1)`，依旧 bail out。

因此每 1000ms 回调都在执行，但 UI 永远停在 `1`。这是典型的**过期闭包（stale closure）**，不是 interval 没跑。

**2. 修复与测试：**

```tsx
useEffect(() => {
  const id = setInterval(() => {
    setSeconds(s => s + 1)
  }, 1000)
  return () => clearInterval(id)
}, [])
```

- 更新函数 `s => s + 1` 不读取外层闭包，而是接收 React 的 pending state，因此每次都能得到 `1, 2, 3, …`。
- cleanup 仍然必须是 `clearInterval(id)`：StrictMode 在开发环境会对 Effect 执行 setup → cleanup → setup，如果第一次的 interval 没清掉，挂载后会有两个 interval 同时自增，速度翻倍。

不等待真实 3 秒的确定性测试：

```tsx
test('每秒加一', () => {
  vi.useFakeTimers()
  try {
    render(<Stopwatch />)

    act(() => {
      vi.advanceTimersByTime(3000)
    })

    expect(screen.getByText('已运行 3 秒')).toBeInTheDocument()
  } finally {
    vi.useRealTimers()
  }
})
```

要点：

- `vi.useFakeTimers()` 接管 `setInterval`；`vi.advanceTimersByTime(3000)` 同步触发 3 次回调。
- 用 `act(...)` 包住计时器推进，让 React 处理并刷新由 timer 回调产生的 state 更新；否则可能看到 act 警告，或在断言时 DOM 还没更新。
- 在 `finally` 或 `afterEach` 中调用 `vi.useRealTimers()`，不要让假定时器泄漏到后续测试。
- 如果测试里还有 promise 驱动的异步更新，用 `await vi.advanceTimersByTimeAsync(...)`，并同样放在 `act` 中。
- 这个测试没有使用 user-event，所以不会遇到下面第 3 题提到的“Vitest 假定时器 + user-event”组合问题；如果同一测试还要 `await user.type(...)`，优先改用真实定时器，或参考第 3 题的环境说明。

### 评分点（共 0.5 分）

- 0.25 分：正确判断显示 `1`（而不是 3），并解释空依赖闭包捕获初始 `0`、每次 tick 都设置成 `1`，以及相同值导致 bail out。
- 0.25 分：给出更新函数 `setSeconds(s => s + 1)` 和 cleanup；说明测试用假定时器推进并放在 `act` 中、结束后恢复真实定时器；提到 StrictMode 下 cleanup 防止重复 interval。

### 简短解释

空依赖 Effect 里的回调只在首次渲染时创建，闭包看到的 `seconds` 永远是初始值。直接值更新会反复写入 `1`，React 用 `Object.is` 比较后跳过重渲染。更新函数让 React 把上一步的 pending state 交给回调，才能得到递增结果。

## 复习 2（0.5 分｜不可变更新与 StrictMode 双调用）

### 参考答案

**1. 点击“添加”一次后立刻查询：0 个 `<li>`。**

`addTask` 直接 `tasks.push(...)` 修改了原数组，然后返回**同一个数组引用**。`setTasks` 用 `Object.is` 比较新旧 state；引用相同，React 会认为 state 没有变化，可能直接 bail out，不重新渲染。虽然数组内容已经被改了，但当前这次更新没有产生新的引用，所以界面仍然是空的。

**2. 紧接着点击“刷新”一次：2 个 `<li>`，文本都是“写周报”。**

StrictMode 在开发环境会**双调用更新函数**（reducer/updater 等）来暴露不纯逻辑：

- 第一次调用：向 `prev` 数组 push 第 1 个任务。
- 第二次调用：又向同一个 `prev` 数组 push 第 2 个任务。
- 两次都返回同一个数组引用。

随后 `setN(x => x + 1)` 是一次正常的、返回新值的更新，它触发了真正的重新渲染；这次渲染读取被原地修改过的 `tasks` 数组，发现里面有两个对象，于是渲染出两个“写周报”。

注意：即使不开 StrictMode，这段代码也是坏的——push 后返回同一引用会让“添加”这次更新 bail out，界面不会立即变；在后续某个无关更新时才可能看到被修改的数据。StrictMode 只是把隐藏的重复写放大了。

**3. 修复：**

```tsx
function handleAdd() {
  const task: Task = {
    id: crypto.randomUUID(),
    title: '写周报',
    done: false,
  }
  setTasks(prev => [...prev, task])
}

<button onClick={handleAdd}>添加</button>
```

或者保留 helper，但让它变成纯函数并把新任务作为参数：

```tsx
function addTask(tasks: Task[], task: Task): Task[] {
  return [...tasks, task]
}

function handleAdd() {
  const task = { id: crypto.randomUUID(), title: '写周报', done: false }
  setTasks(prev => addTask(prev, task))
}
```

两个关键点：

- **不可变更新**：返回新数组、复制需要修改的部分，不修改参数和已有对象。
- **随机 ID 在事件处理函数里生成**：`crypto.randomUUID()` 放在 updater/reducer 里会让它变成不纯函数；StrictMode 双调用会生成两个不同 ID（虽然 React 通常只采用其中一次结果），重放、调试和测试都不稳定。更稳妥的是在事件中生成一次，再把完整的 task 交给 updater/reducer。

### 评分点（共 0.5 分）

- 0.25 分：正确回答“立刻 0 个”，指出原地 `push`、返回同一数组引用、React 因引用相同而 bail out（StrictMode 双调用会 push 两次）。
- 0.25 分：正确回答“刷新后 2 个、都是写周报”，说明第二次渲染读取了被原地修改的数组；给出 `[...prev, task]` 的不可变更新，并说明随机 ID 应在事件处理函数中生成，而不是 updater/reducer 中。

### 简短解释

React 判断 state 是否变化看引用。`push` 改的是旧数组，返回的又是旧引用，所以“添加”不会触发渲染；被改坏的数据会在下一次无关渲染时暴露。StrictMode 双调用 updater 会把一次 push 变成两次，于是刷新后看到两条重复任务。

## 第 1 题（3 分｜查询、可访问名称与用户事件）

### 参考答案

#### A. 查询预测（1.25 分）

| 查询 | 结果 | 原因与修正 |
|---|---|---|
| `getByRole('textbox', { name: '例如：写周报' })` | **抛错** | 输入框的可访问名称来自 `<label htmlFor="title">标题</label>`，是“标题”，不是 placeholder。修正：`getByRole('textbox', { name: '标题' })`，或 `getByLabelText('标题')`。`getByPlaceholderText('例如：写周报')` 能查到，但优先级更低。 |
| `getByRole('button', { name: '保存' })` | **返回元素** | `<button type="submit">保存</button>` 的可访问名称来自其文本内容“保存”。 |
| `getByRole('button', { name: '清空' })` | **抛错** | 这是一个只有 SVG 图标的按钮；`aria-hidden="true"` 的 SVG 不进入可访问名称，按钮没有任何可访问名称。`getByRole('button')` 能找到两个按钮，但 name 为“清空”的没有。修正组件：给按钮加 `aria-label="清空"`，或加视觉隐藏文本 `<span className="sr-only">清空</span>`；然后 `getByRole('button', { name: '清空' })`。不要首选 `getByTestId` 掩盖可访问性问题。 |
| `getByText('剩余 10 个字符')` | **抛错** | `getByText` 按元素的文本节点匹配。这里 `<p>` 的直接文本是“剩余 ”，`<strong>` 里是“10”，完整字符串没有出现在同一个元素的可匹配文本中。修正：用函数匹配并限定元素，例如 `screen.getByText((_, el) => el?.tagName === 'P' && el.textContent === '剩余 10 个字符')`；或先 `const p = screen.getByText(/剩余/)`，再 `expect(p).toHaveTextContent('剩余 10 个字符')`。更语义化的做法：给这段状态加 `role="status"` 或 `aria-live="polite"`，用 `getByRole('status')` 查询后再断言文本。 |
| `getByLabelText('标题')` | **返回元素** | `<label htmlFor="title">` 与 `<input id="title">` 正确关联，`getByLabelText` 能找到输入框；`getByRole('textbox', { name: '标题' })` 也可以。 |

**查询优先级（从高到低）：**

1. `getByRole`（配合 `name`）——最接近用户在可访问性树中的体验；如果查不到，往往说明 UI 本身缺少语义或可访问名称。
2. `getByLabelText`——表单字段的常用查询，用户就是通过 label 找到字段的。
3. `getByPlaceholderText`——placeholder 不能替代 label；只有在没有 label 时才退而求其次。
4. `getByText`——适合非交互的文本内容（段落、span、div 等）。
5. `getByDisplayValue`——适合已填值的表单元素。
6. `getByAltText`、`getByTitle`——语义查询；`title` 对屏幕阅读器和视觉用户都不稳定。
7. `getByTestId`——最后手段；用户看不到也听不到 test id，只在没有角色/文本等语义查询时使用。

`getByRole` 的 `name` 匹配的是**可访问名称**；字符串默认按完整名称匹配，正则或函数可以做模糊匹配。可访问名称可能来自 `aria-labelledby`、`aria-label`、原生 `<label>`、元素内容（按钮）等；`aria-hidden="true"` 的内容会被排除。

**本题的额外结论：** 输入框应优先用 `getByRole('textbox', { name })` 或 `getByLabelText`；placeholder 不是 label。图标按钮应补 `aria-label` 或视觉隐藏文本，而不是给测试加 test id 绕过。

#### B. 事件与输入约束（1 分）

**为什么会失败：**

1. **`fireEvent.keyDown` 只派发了一个 `keydown` 事件，不执行浏览器的默认动作。** 在真实浏览器里，焦点在文本输入框时按 Enter 会触发隐式表单提交；`fireEvent.keyDown(input, { key: 'Enter' })` 不会触发默认的 form submit，`onSubmit` 不会执行，`fetch` 也不会发出。测试随后等待“已保存”，超时失败。`fireEvent` 是低层事件派发工具，不会模拟完整的键盘/指针事件序列，也不会执行默认行为。
2. **`fireEvent.change` 直接设置整个 value，绕过了 `maxLength`。** 真实用户逐字符输入时，浏览器和 user-event 会阻止超过 `maxLength={10}` 的内容；`fireEvent.change(input, { target: { value: '这是一个超过十个字的任务标题' } })` 可以一次性写入 14 个字符。即使再手动触发提交让测试变绿，它也没有验证“用户最多只能输入 10 个字”这个约束，属于假阳性。
3. **补充：** `fireEvent` 也不会像 user-event 那样检查 `pointer-events: none`、可见性、disabled 等交互前提。比如对 `pointer-events: none` 的按钮 `fireEvent.click` 仍会调用 handler，而 `userEvent.click` 会报“Unable to perform pointer interaction”。

**用 user-event 重写：**

```tsx
test('按 Enter 保存标题', async () => {
  vi.stubGlobal(
    'fetch',
    vi.fn().mockResolvedValue({ ok: true, json: async () => ({}) }),
  )

  const user = userEvent.setup()
  render(<TaskComposer />)

  const input = screen.getByRole('textbox', { name: '标题' })
  await user.type(input, '这是一个超过十个字的任务标题{Enter}')

  expect(await screen.findByText('已保存')).toBeInTheDocument()
})
```

- `userEvent.setup()` 建议在 render 之前调用，后续所有 API 都要 `await`。
- `user.type` 会先聚焦/点击元素，然后逐字符派发 `keydown`、`keypress`、`beforeinput`、`input`、`keyup` 等事件，并尊重 `maxLength`；输入值会被截断到 10 个字符。
- `{Enter}` 会触发真实的隐式表单提交（等价于点击 submit 按钮），因此 `onSubmit` 执行并发出请求。
- 最后用 `findByText` 等待异步保存结果，而不是立即 `getByText`。

**什么时候还可以用 `fireEvent`：**

- 只测试某个低层事件处理函数，例如直接 `fireEvent.submit(form)` 验证 `onSubmit` 逻辑，不关心键盘如何触发提交；
- 需要派发 user-event 没有覆盖的特定事件，或测试非常底层的 DOM 行为；
- 已有代码明确处理某个非用户交互事件。即使如此，也应该优先考虑 `userEvent` 能否表达同样的用户行为。

#### C. act 警告与异步等待（0.75 分）

**1. 为什么 await 了还找不到，并且出现 act 警告？**

`await user.click(...)` 只等待 user-event 模拟的**点击事件序列**以及点击处理器中同步触发的 React 更新；它**不会等待点击处理器里启动的 `fetch` promise**。这里的 `fetch` 在 50ms 后才 resolve，`setSaved(true)` 发生在：

- `user.click` 已经完成并返回之后；
- 测试的 `getByText('已保存')` 已经执行并抛错之后；
- 测试（或 act 作用域）已经结束后。

因此断言时 DOM 里还没有“已保存”。随后 promise resolve，`setSaved(true)` 在 act 之外触发更新，React 在测试环境（RTL 设置了 `IS_REACT_ACT_ENVIRONMENT`）发出 “An update to TaskComposer inside a test was not wrapped in act(...)” 警告。这个警告提示有异步更新没有被测试等待/刷新；它和“找不到元素”是同一个根因。

**2. 最小修复：**

```tsx
expect(await screen.findByText('已保存')).toBeInTheDocument()
```

或者：

```tsx
await waitFor(() => {
  expect(screen.getByText('已保存')).toBeInTheDocument()
})
```

- `findBy...` 等价于 `getBy...` + `waitFor`：它会反复查询，直到找到元素或超时；找到时返回元素，超时则抛出最后一次查询错误。
- `waitFor` 会重试回调，直到回调不再抛错或超时。回调里应放会**抛错**的查询/断言（例如 `getBy...`/`expect`），不要放副作用（点击、发请求等），因为回调可能执行多次。
- 默认超时是 **1000ms**，轮询间隔约 **50ms**。可以调整：
  - `await screen.findByText('已保存', {}, { timeout: 3000 })`
  - `await waitFor(() => { ... }, { timeout: 3000 })`
- RTL 的 `waitFor`/`findBy` 会在内部的 async wrapper 中管理 act 环境，所以用它们等待异步更新通常不会产生 act 警告。不要为了“消警告”把整个测试包进 `act`；应该等待具体的异步结果。

**3. mock 延迟 1500ms 时：**

```tsx
expect(
  await screen.findByText('已保存', {}, { timeout: 3000 }),
).toBeInTheDocument()
```

不要写 `await new Promise(r => setTimeout(r, 1500))` 然后 `getByText`：

- 任意 sleep 仍然是“猜时间”，在慢 CI 上可能不够，导致 flaky；在快机器上又浪费时间。
- 裸 sleep 不会自动刷新 React 的 act 环境；异步更新仍可能在 act 之外发生，继续出现警告。
- `findBy`/`waitFor` 会在条件满足时立即返回，并且失败时给出明确的“找不到元素”错误；把 timeout 调到大于 mock 延迟即可。

补充：如果测试启用了 Vitest 假定时器，`findBy`/`waitFor` 的时间不会自动前进；需要显式推进定时器（并注意 act），或者尽量使用真实定时器。详见第 3 题的相关说明。

### 评分点（共 3 分）

- **A 共 1.25 分：** 5 个查询每个 0.2 分（正确判断通过/抛错并给出原因；抛错的查询需要给出可用的修正），共 1 分；再 0.25 分给查询优先级、placeholder 不是 label、可访问名称来源等解释。只判断对错但说不出原因，酌情扣分。
- **B 共 1 分：** 0.25 分说明 `fireEvent.keyDown` 不会执行默认提交/完整事件序列；0.25 分说明 `fireEvent.change` 绕过 `maxLength`（并指出这会造成假阳性）；0.5 分给出正确的 user-event 重写（setup、await、`{Enter}`、maxLength 行为、findBy 等待）。
- **C 共 0.75 分：** 0.25 分解释 `user.click` 不等待 fetch、更新发生在 act 之外；0.25 分给出 `findBy`/`waitFor` 修复；0.25 分说明默认 1000ms/如何调整，以及为什么裸 sleep 不行。

### 简短解释

查询要尽量从用户/可访问性视角出发：角色 + 可访问名称优先，placeholder 不是 label，文本被元素拆开时 `getByText` 匹配不到完整字符串。事件要用 user-event 模拟完整交互，fireEvent 只派发单个事件，容易绕过默认行为和浏览器约束。断言异步 UI 时，await 用户事件不等于 await 网络；用 `findBy`/`waitFor` 等待可观察结果，act 警告自然会消失。

## 第 2 题（2.5 分｜MSW 3 生命周期、override 与错误语义）

### 参考答案

#### A. 两个测试与 handler 覆盖（1 分）

**1. 第二个测试不会通过，会超时/失败地等待“写周报”，实际看到的是第一个测试留下的空状态“暂无任务”。**

原因：

- `server.use(...)` 注册的是 **runtime handler**，它被**前置（prepend）**到当前 server 的 handler 列表，优先于 `setupServer(...handlers)` 的初始 handler。第一个测试用它覆盖了 `GET /api/tasks`，返回 `[]`。
- 这个 runtime handler 会一直留在 server 实例上，直到被显式移除或 server 关闭；第一个测试结束后它仍然生效。
- `afterEach(() => server.restoreHandlers())` 不会移除 runtime handler。`restoreHandlers()` 的作用是把**被标记为 `{ once: true }` 且已经用过的 handler 重新标记为可用**，它不负责清空 `server.use` 添加的覆盖。
- 第二个测试因此仍然命中“返回空数组”的 handler，页面显示“暂无任务”，`findByText('写周报')` 超时失败。

**2. 匹配顺序与多次 `server.use`：**

- runtime handler 优先于初始 handler。MSW 按注册顺序检查，`server.use` 把新 handler 放在最前面，所以它先匹配。
- 连续两次 `server.use` 同一个接口：第二次添加的 handler 会被前置到最前面，因此**最后一次 `server.use` 生效**（更早的 runtime handler 仍在列表中，但排在后面）。
- `server.resetHandlers()` 会移除所有 runtime handler，把 handler 列表恢复为 `setupServer(...handlers)` 传入的初始列表。

**3. 正确的生命周期与清理：**

```tsx
beforeAll(() => server.listen({ onUnhandledFrame: 'error' }))
afterEach(() => server.resetHandlers())
afterAll(() => server.close())
```

- `beforeAll` 只启用一次请求拦截；`afterEach` 在每个测试后清掉 runtime handler；`afterAll` 关闭拦截并恢复原生请求模块。
- `server.listen()` 和 `server.close()` 都是**同步**的，不需要 `await`。
- `resetHandlers()` 与 `restoreHandlers()` 的区别：
  - `resetHandlers()`：移除所有通过 `server.use` 添加的 runtime handler，恢复到初始 handler 列表。
  - `restoreHandlers()`：只把 `{ once: true }` 的 handler 恢复为未使用状态，让它们能再次匹配；不会清掉普通 runtime handler。
  - `resetHandlers(handler1, handler2, ...)`：不仅移除 runtime handler，还会把传入的这组 handler 作为新的初始列表（原来的初始 handler 也被替换）。

因此本题的 setup 应把 `afterEach` 改成：

```tsx
afterEach(() => server.resetHandlers())
```

这样第二个测试会命中初始 handler，看到“写周报”。

#### B. HTTP 错误与网络错误（1 分）

**1. 不会看到 alert。实际会发生什么？**

`fetch` 在收到 HTTP 500 时**不会 reject**。HTTP 错误状态码仍然是“成功完成的 HTTP 响应”，`fetch` 的 promise 会 resolve，只是 `res.ok === false`。所以：

- `.catch` 不会执行，因为没有抛出网络错误。
- `res.json()` 成功解析 `{ message: 'boom' }`。
- `setTasks(data)` 把 `tasks` 设成一个对象，而不是数组。
- 重新渲染时：`tasks` 是 truthy，`tasks.length` 是 `undefined`，`undefined === 0` 为 false，于是执行 `tasks.map(...)`；对象没有 `map` 方法，抛 `TypeError`。
- 这个渲染期错误不会被前面的 `.catch` 捕获（它不在那个 promise 链里），也不会显示“加载失败”；测试在等待 alert 时失败（并可能看到 React 的渲染错误）。

**2. 模拟“HTTP 500，客户端检查 `res.ok`”：**

Handler 可以保持：

```tsx
server.use(
  http.get('/api/tasks', () =>
    HttpResponse.json({ message: 'boom' }, { status: 500 }),
  ),
)
```

或者返回无 JSON 的 500：

```tsx
http.get('/api/tasks', () => new HttpResponse(null, { status: 500 }))
```

组件需要显式检查 `res.ok`：

```tsx
useEffect(() => {
  async function load() {
    try {
      const res = await fetch('/api/tasks')
      if (!res.ok) {
        throw new Error(`HTTP ${res.status}`)
      }
      const data = await res.json()
      setTasks(data)
    } catch {
      setError('加载失败')
    }
  }
  load()
}, [])
```

如果服务端错误响应是 JSON 错误体，也可以先 `res.json()` 读取错误信息再决定 UI，但前提仍然是先判断 `res.ok` / status，不能假设 `fetch` 会 reject。

**3. 模拟网络层失败：**

```tsx
server.use(
  http.get('/api/tasks', () => HttpResponse.error()),
)
```

- `HttpResponse.error()` 返回一个网络错误响应，MSW 会让请求以网络错误结束，`fetch` 会 reject。
- Fetch 规范没有提供自定义网络错误消息的方式，客户端通常收到通用的 `TypeError: Failed to fetch`。组件里的 `.catch` 会执行，可以显示“加载失败”。
- 注意：`HttpResponse.json(..., { status: 500 })` 和 `new HttpResponse(null, { status: 500 })` 都是 HTTP 响应，不是网络错误；不要混淆。

**4. 为什么 MSW 比直接 stub `fetch` 更好：**

- MSW 在**网络边界**拦截，返回真实的 Fetch `Response`，包括 status、headers、body、`res.ok`、JSON 解析、网络错误等语义。这样测试才能真正覆盖客户端对 500、204、网络失败的处理。
- 直接 `vi.stubGlobal('fetch', ...)` 往往只返回一个手写对象，容易漏掉 `res.ok`/status/headers 等真实语义；测试可能因为 mock 太理想而放过 bug（本题就是典型：开发者以为 500 会 reject）。
- MSW 还能验证请求的 URL、method、body（虽然 MSW 官方建议尽量通过 UI 行为断言，而不是过度断言请求），并让同一份 handler 在开发、测试、Storybook 中复用。它把“网络”这个外部系统替换掉，而不是替换组件内部的实现细节。

#### C. MSW 3 迁移与生命周期（0.5 分）

**1. 不符合 MSW 3.0.7 的地方：**

```tsx
// 错误：MSW 3 不再从根入口导出 http / HttpResponse / delay
import { http, HttpResponse, delay } from 'msw'
```

应改为：

```tsx
import { http, HttpResponse } from 'msw/http'
import { delay } from 'msw/utils/delay'
```

`setupServer` 仍然来自 `msw/node`（本题外层已有，不需要改）。MSW 3 还要求 Node.js ≥ 22.12.0；当前 Node 24 满足。

```tsx
server.listen({ onUnhandledRequest: 'error' })
```

`onUnhandledRequest` 在 3.x 改名为 **`onUnhandledFrame`**：

```tsx
server.listen({ onUnhandledFrame: 'error' })
```

它现在统一处理未处理的“网络帧”，包括 HTTP 请求和 WebSocket 连接。策略值有 `'warn'`（默认）、`'error'`、`'bypass'`，也可以传自定义回调。`'error'` 会打印错误并中止未处理的请求，让测试失败；默认 `'warn'` 只警告，然后按原样放行请求。

```tsx
beforeAll(() => {
  server.listen({ onUnhandledFrame: 'error' })
})
beforeEach(() => {
  server.listen()
})
```

在 MSW 3 中，`listen()` 和 `close()` 都有状态保护：**重复 `listen()` 或重复 `close()` 会抛错**（为了避免错误的副作用管理）。`beforeAll` 已经启用后，`beforeEach` 再次 `listen()` 会抛 “already enabled” 一类的错误。移除 `beforeEach` 的 `listen()`；如果确实需要在每个测试前后启停，就配对使用 `beforeEach(listen)` + `afterEach(close)`，但通常 `beforeAll` + `afterEach(resetHandlers)` + `afterAll(close)` 更高效。

```tsx
afterAll(() => {
  await server.close()
})
```

`server.close()` 是同步 API，不需要 `await`（`await` 一个非 promise 值不会报错，但会误导读者）。MSW 3 中 `worker.stop()` 才是返回 Promise 的；Node 的 `setupServer().close()` 是同步的。

另外，如果在 `isolate: false` 等场景下多个测试文件共享同一个 server 实例，不要无条件重复 `listen()`/`close()`；可以检查 `server.readyState`（`NetworkReadyState`）后再切换。

**2. `onUnhandledFrame: 'error'` 的作用：**

- 当组件发出了没有被任何 handler 匹配的请求（或 WebSocket 连接）时，`'error'` 策略会报错并中止该帧，测试通常会因此失败。这能防止“忘记 mock 某个接口，测试却悄悄打到真实网络/拿到意外响应”的问题。
- 默认是 `'warn'`：打印警告，然后按原样执行请求（可能打到真实网络，或得到未 mock 的响应）。在测试里通常希望用 `'error'`（或 `'bypass'` 仅用于已知的静态资源）。

### 评分点（共 2.5 分）

- **A 共 1 分：** 0.5 分说明第二个测试会失败/超时、看到“暂无任务”，原因是 `server.use` 的 runtime handler 持续存在且 `restoreHandlers` 不会移除它；0.25 分给出正确的 `beforeAll(listen)` / `afterEach(resetHandlers)` / `afterAll(close)`；0.25 分说明 runtime handler 前置、最后一次 `use` 生效、`resetHandlers` 与 `restoreHandlers` 的区别。
- **B 共 1 分：** 0.35 分说明 HTTP 500 不会让 `fetch` reject、`.catch` 不执行，以及当前组件拿到对象后 `map` 报错/不显示 alert；0.3 分给出 HTTP 500 handler 与组件 `res.ok` 检查；0.2 分给出 `HttpResponse.error()` 模拟网络错误及通用 `TypeError`；0.15 分说明 MSW 在真实 Response/网络边界上的优势。
- **C 共 0.5 分：** 0.2 分改正 `msw/http` / `msw/utils/delay` 入口；0.2 分改正 `onUnhandledFrame` 并说明 `'error'`/默认 `'warn'`；0.1 分指出 `listen`/`close` 同步、重复 `listen` 在 v3 会抛错。

### 简短解释

MSW 3 的 server 是文件级单例：`listen` 一次、每个测试后 `resetHandlers`、最后 `close`。`server.use` 的覆盖是前置且持久的，`restoreHandlers` 只重新武装 `once` handler，不能代替 `resetHandlers`。HTTP 错误码不会让 fetch reject，必须检查 `res.ok`；只有网络层错误才走 catch，而 `HttpResponse.error()` 正是模拟它的方式。

### 参考答案

#### A. 测试隔离/顺序问题（1 分）

至少能指出以下问题：

1. **假定时器没有恢复。** `beforeEach(() => vi.useFakeTimers())` 之后没有 `afterEach(() => vi.useRealTimers())`。Vitest 5 的假定时器会跨测试保留（实测第二个测试里 `vi.isFakeTimers()` 仍为 true）。在本环境（Vitest 5.1 + RTL 16.3.3 + user-event 14.6）中，`await user.type` / `await user.click` 可能直接超时：user-event 的 `wait()` 用 `setTimeout(delay)`（默认 delay 0），RTL 的 `asyncWrapper` 也等待一个 `setTimeout(0)`；RTL 16.3.3 的假定时器检测只认 Jest 的全局 `jest`，不会自动推进 Vitest 的假定时器，所以这些 promise 无法完成。**实测只传 `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })` 仍可能挂起；`vi.useFakeTimers({ shouldAdvanceTime: true })` 或干脆使用真实定时器才稳定。** 应在 `afterEach` 中 `vi.useRealTimers()`，并优先在不需要精确控制时间时使用真实定时器。

2. **模块级 `nextId` 没有重置。** `beforeEach` 只重置了 `tasks`，`nextId` 仍会从之前的测试继续递增。ID 依赖测试顺序/执行历史，`getByTestId('task-1')` 可能在某个顺序下找不到；即使能找到，断言内部 ID 也没有用户价值。应重置计数器，或者更好地让 ID 在事件/工厂中生成，不在测试里断言原始 ID。

3. **第二个测试依赖第一个测试的 DOM 和数据。** 它没有 `render(<TaskList />)`，直接 `document.querySelector('.task-card')`，隐含假设第一个测试留下的卡片还在。但本环境 `globals: true`，且从 `@testing-library/react`（不是 `pure`）导入，RTL 会自动注册 `afterEach(cleanup)`；每个测试后 DOM 都会被清理。第二个测试查询到 `null`，随后 `within(card)`（或非空断言后的访问）会抛错。并且 `beforeEach` 又把 `tasks` 清空了，所以即使 DOM 没清理也没有数据。每个测试必须自己准备数据、自己 render，不能依赖顺序。

4. **`setState({ tasks: [] })` 只重置了部分 store。** Zustand 5 的 `setState` 默认是浅合并，只覆盖 `tasks`；如果 store 以后增加 `filter`、`draft`、`error` 等字段，它们会从上一个测试泄漏。更稳妥的是重置完整初始状态（例如保存初始 state 后 `setState(initial, true)` 做替换），或者为每个测试创建独立的 store 工厂/注入测试 store。

5. **`vi.spyOn` 没有恢复。** spy 和调用记录会泄漏到后续测试；用 `afterEach(() => vi.restoreAllMocks())`，或在 Vitest 配置里开启 `restoreMocks: true`。`vi.clearAllMocks()` 只清调用记录，不恢复原实现。

6. **补充：** 如果组件会发请求，MSW 的 runtime handler 也需要在每个测试后 `resetHandlers()`（见第 2 题）；否则网络层的状态同样会跨测试泄漏。

在本环境会直接让第二个测试崩溃/超时的点：假定时器导致 `user.*` 挂起；第二个测试没有 render，加上 RTL 自动 cleanup，`querySelector` 得到 `null` 后 `within` 崩溃；`beforeEach` 清空 tasks 后第二个测试没有数据。`nextId` 和 partial reset 更多是可重复性/顺序依赖问题，可能表现为 test id 找不到或状态串味。

#### B. 实现细节反模式与改写（1 分）

至少能指出以下问题：

1. **`expect(addSpy).toHaveBeenCalledWith('写周报')`**：断言 store 内部 action 被调用，是实现细节。重构 store（换 action 名、用中间件包装、在组件内直接 setState）就会破坏测试；而且 action 被调用不代表 UI 更新成功——测试可能绿，页面却坏了。应断言用户能看到任务（例如列表中出现“写周报”）。
2. **`document.querySelectorAll('.task-card')` 和 `toHaveClass('completed')`**：CSS 类名是样式实现细节，改名/换样式方案就失败；类名也不等于用户感知的完成状态。应使用可访问状态：checkbox 的 `toBeChecked()`，或列表项/文本内容。
3. **`screen.getByTestId('task-1')`**：test id 用户看不到、听不到，而且这里还把内部自增 ID 编码进断言；测试顺序一变就脆弱。优先用角色/可访问名称/文本；只有在没有语义查询时才用 test id。
4. **`document.querySelector('.task-card')!` + `within(card)`**：非空断言掩盖“元素不存在”，失败信息也不如 `screen.getByRole(...)` 清晰；从全局 DOM 抓一个类再往下找，耦合结构。应直接从可访问查询入手。
5. **`within(card).getByRole('checkbox')` 没有名称**：这个 checkbox 目前没有 label/aria-label，用户无法知道它对应哪个任务；测试虽然能按角色找到它，但没有覆盖可访问性。组件应加 `aria-label={`完成 ${task.title}`}` 或用 `<label>` 包裹，让 checkbox 有可访问名称。
6. **测试只检查 class，没有检查交互结果**：点击 checkbox 后应验证 `checked` 状态变化、任务标题仍可见等用户可观察结果。

**改写后的“切换完成状态”测试（不依赖上一个测试）：**

```tsx
test('切换完成状态', async () => {
  const user = userEvent.setup()
  render(<TaskList />)

  await user.type(screen.getByRole('textbox', { name: '标题' }), '写周报')
  await user.click(screen.getByRole('button', { name: '添加' }))

  const list = screen.getByRole('list', { name: '任务列表' })
  expect(within(list).getAllByRole('listitem')).toHaveLength(1)

  const checkbox = screen.getByRole('checkbox', { name: /写周报/ })
  expect(checkbox).not.toBeChecked()

  await user.click(checkbox)

  expect(checkbox).toBeChecked()
  expect(within(list).getByText('写周报')).toBeInTheDocument()
})
```

要让 `getByRole('checkbox', { name: /写周报/ })` 可用，组件需要给 checkbox 一个可访问名称，例如：

```tsx
<input
  type="checkbox"
  checked={task.done}
  onChange={() => toggle(task.id)}
  aria-label={`完成 ${task.title}`}
/>
```

或者用 `<label>` 包裹 checkbox 和标题文本。这样测试既验证了用户可见结果，也暴露并修复了原本缺失的可访问名称。

#### C. 为什么 `vi.spyOn(useTaskStore.getState(), 'add')` 不可靠（0.5 分）

**1. 为什么不可靠：**

- `useTaskStore.getState()` 返回的是**当前 state 快照对象**。`vi.spyOn` 是在这个对象的 `add` 属性上做替换，而不是在 store 的稳定 API 上。Zustand 的 `setState` 会创建/合并新的 state 对象；组件可能通过 selector 在 render 时读取 `state.add`，也可能已经捕获了原始 action 引用，还可能通过 `getState().add` 动态读取。不同写法下 spy 是否被调用并不稳定。
- 如果 store 使用中间件（persist、devtools、immer 等）包装 action，或以后把 action 从 state 中拆出去，spy 可能失效。
- 它断言的是“内部函数被调用”，不是用户结果；action 被调用但 UI 没更新、或调用参数对但渲染出错时，测试仍可能通过。这正是实现细节测试的典型问题。
- spy 还会改变对象/函数身份，可能影响依赖引用相等性的逻辑（memo、Effect 依赖等），让测试环境与真实环境不同。
- 最后，`vi.spyOn` 需要恢复；否则会污染后续测试。

**2. 更合适的分层测试：**

- **Store 单元测试（纯逻辑层）：** 直接调用 store 的公开 action，断言 store 的公开 state。例如：
  ```tsx
  test('add 添加一条任务', () => {
    const taskStore = createTaskStore() // 每个测试独立实例
    taskStore.getState().add('写周报')
    expect(taskStore.getState().tasks).toHaveLength(1)
    expect(taskStore.getState().tasks[0].title).toBe('写周报')
  })
  ```
  如果组件已经订阅了同一个 store，直接 `setState` 需要用 `act` 包住以刷新 React；独立的 store 实例更适合纯逻辑测试。不要在组件测试里 spy store。
- **组件集成测试（用户行为层）：** render、输入、点击，断言用户能看到任务、checkbox 状态等；不要关心 store 内部调用了什么。
- **网络边界：** 用 MSW 模拟 `/api/tasks`，而不是 mock fetch 或 store。
- 如果确实需要观察“添加”这个动作，可以给组件一个公开回调 prop（例如 `onAdd`）并在集成测试中断言回调；或者通过 store 的公开 state/selector 断言，而不是 spy 内部方法。

这种分层的好处是：store 逻辑挂了，单元测试直接指出；组件交互/渲染挂了，集成测试指出；重构内部实现不会无谓地打破测试。

### 评分点（共 2.5 分）

- **A 共 1 分：** 至少 3 个隔离/顺序问题，每个 0.25 分（fake timers 未恢复、`nextId` 未重置、第二个测试依赖前一个测试/DOM、partial store reset、spy 未恢复、MSW handler 未重置等）；0.25 分说明本环境下哪些会直接导致崩溃/超时（假定时器 + user-event 挂起、RTL 自动 cleanup 后 `querySelector` 为 null、beforeEach 清空数据）。
- **B 共 1 分：** 至少 3 处实现细节断言并说明为什么脆弱（0.5 分）；改写后的“切换完成状态”测试正确准备数据、自己 render、使用 user-event + role/within + `toBeChecked`（0.5 分）。改写中如果仍依赖 class/testid/内部 ID，酌情扣分。
- **C 共 0.5 分：** 0.25 分说明 spy 依赖 state 快照/实现、不能证明用户可见结果、可能因重构失效；0.25 分给出分层方案（store 纯逻辑单元测试 + 组件用户行为集成测试 + MSW 网络边界，或公开回调/store state 断言），而不是在组件测试里 spy store 内部 action。

### 简短解释

测试隔离的本质是让每个测试自带前置条件：DOM 由 RTL 自动清理，但模块级计数器、Zustand 单例、假定时器、MSW runtime handler 和 spy 都不会自动恢复。测试实现细节（class、test id、内部 ID、store action spy）会在重构时给出假失败，也可能在行为已经坏掉时给出假通过；面向角色、可访问名称和可见状态断言，既更稳定，也更接近用户真正的体验。
