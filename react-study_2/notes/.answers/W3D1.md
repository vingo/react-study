## 复习 1（1 分｜state 更新队列）

### 参考答案

最终显示 **2**。逐行看 pending state：

| 行 | 代码 | 执行后的 pending state | 原因 |
|---|---|---|---|
| 初始 | — | 0 | — |
| 1 | `setN(n + 1)` | 1 | 直接值，`n` 是本次渲染的快照 0，结果为 1 |
| 2 | `setN(n => n + 1)` | 2 | 更新函数接收上一步的 pending state 1 |
| 3 | `setN(n + 1)` | 1 | 直接值仍用快照 0，算出 1，**替换**掉队列中的 2 |
| 4 | `setN(n => n * 2)` | 2 | 更新函数接收上一步的 pending state 1，得到 2 |

所以队列最终是 `[2]`，界面显示 2。

### 评分点（共 1 分）

- 0.5 分：最终答案 2。
- 0.5 分：四步 pending state 的推导正确，明确指出第 3 行的直接值基于渲染快照 `n = 0`，并且会替换此前排队的值；更新函数则读取最新 pending state。

### 简短解释

直接值 `setN(n + 1)` 中的 `n` 来自本次渲染闭包，在同一事件里始终是 0；它不会读取队列里已经排队的 1。更新函数 `setN(fn)` 由 React 依次传入最新的 pending state，所以能累加。两者混用时严格按调用顺序处理，直接值会覆盖它之前累积的队列结果。

## 复习 2（1 分｜render、事件处理函数与 Effect 的职责边界）

### 参考答案

1. **POST 请求：放在点击的事件处理函数里。** 它由一次明确的用户交互触发，只应执行一次，和“组件当前渲染成什么样”无关。
2. **WebSocket：放在 `useEffect` 里，依赖 `[roomId]`。** setup 建立连接，cleanup 关闭连接。`roomId` 变化时先执行旧 cleanup 再执行新 setup；卸载时执行最后一次 cleanup。这是与外部系统保持同步。
3. **`fullName`：直接在 render 中计算**，例如 `const fullName = firstName + ' ' + lastName`。它完全由现有 props/state 派生，不需要额外存储。

把第 1 项放进 Effect 的问题：

- Effect 在渲染提交后运行，无法准确表达“用户点击了保存”这个意图；它会在挂载时以及依赖变化时反复执行。
- 如果依赖数组写得不好，可能在该保存的时候不保存、在不该保存的时候重复 POST；StrictMode 开发环境还会额外执行一次 setup/cleanup 演练，容易造成重复请求。
- 事件处理函数能直接拿到这次点击相关的参数，也不需要为了触发请求而额外引入 state 作为“信号”。

把第 3 项用 `useState` + `useEffect` 同步的问题：

- 首次渲染只能先显示旧值或空值，Effect 里再 `setFullName`，多出一次渲染，用户可能看到一帧不一致的内容。
- 两份真相（`firstName`/`lastName` 与 `fullName`）需要手动保持同步；只要有一条更新路径忘了同步，就会显示过期数据。
- 派生值应在 render 中计算，不需要 state，也不需要 Effect。

### 评分点（共 1 分）

- 0.6 分：三个需求的位置都正确（各 0.2 分）。
- 0.2 分：说明 POST 属于事件语义，放 Effect 会重复执行/依赖难写/与点击意图脱节。
- 0.2 分：说明派生值放 state + Effect 会多一次渲染并产生不同步风险。

### 简短解释

判断标准不是“这段代码什么时候运行”，而是“它为什么存在”：由交互触发的一次性动作放事件处理函数；与外部系统持续同步放 Effect；能由现有数据算出来的值直接在 render 中算。

## 第 1 题（2 分｜Fiber 树与双缓冲）

### 参考答案

**1. 节点的三个方向指针**

每个 Fiber 是一个可变的 JS 对象，至少通过三个链接字段描述树结构：

- `child`：第一个子节点；
- `sibling`：下一个兄弟节点；
- `return`：父节点。

要遍历所有子节点，从 `child` 开始沿 `sibling` 链前进即可。它不是 `children: Fiber[]` 数组，因为链表让 React 在任意时刻只持有“当前 Fiber”就能一步一步深度优先遍历：有子节点就下到 `child`，没有子节点就 `completeWork` 后看 `sibling`，没有兄弟就沿 `return` 回退。这样每个节点不需要维护子节点数组，插入、移动、删除和中断后恢复都只需要改少量指针，适合“把渲染拆成可中断的工作单元”。

Fiber 不是 JSX 元素本身。JSX 元素是不可变的描述对象；Fiber 是 React 内部用来记录组件实例、props、state、DOM 节点、优先级和副作用的可变工作单元。

**2. 深度优先访问顺序**

只看题目中出现的节点：

```text
main → Header → ul → li(A) → li(B) → Footer
```

过程：

1. 从 `main` 开始，先访问它自己，再下到第一个子节点 `Header`；
2. `Header` 的子树完成后，沿 `Header` 的 `sibling` 到 `ul`；
3. `ul` 下到第一个子节点 `li(A)`，`li(A)` 没有子节点（或子树完成）后沿 `sibling` 到 `li(B)`；
4. `li(B)` 没有兄弟，沿 `return` 回到 `ul`；`ul` 完成后沿 `ul` 的 `sibling` 到 `Footer`；
5. `Footer` 完成后，沿 `return` 一路回到 `main` 和根。

也就是说：**有子节点就下探；没有子节点就完成当前节点并找兄弟；没有兄弟就沿父节点回退，直到找到兄弟或回到根。** 这正是 `beginWork` 向下、`completeWork` 向上、`sibling` 横向的连接方式。

**3. current 与 work-in-progress**

- `current` 树：当前已经提交、屏幕上正在显示的那棵树，`root.current` 指向它。
- work-in-progress 树：本次更新正在构建的新树。每个 work-in-progress Fiber 通过 `alternate` 指向 `current` 树中对应的 Fiber，反向也成立。

render 阶段只调用组件、计算新的 JSX、做 diff、构建 work-in-progress 树，**不会修改真实 DOM**。因此这个阶段可以被暂停、放弃或重新开始；即使用户此时看屏幕，看到的仍是完整的 `current` 树，不会出现“改了一半”的 UI。

commit 阶段拿到已经完成的 work-in-progress 树，同步执行必要的 DOM 插入、更新、删除，把 `root.current` 切换到新树，然后附加/分离 ref、运行 layout effect，浏览器随后绘制。commit 的这部分工作是同步的、不可中断的，所以用户看到的是从旧 UI 到新 UI 的一次切换（passive effect 会在 commit 之后另行调度）。

**4. commit 之后与下一轮复用**

commit 完成后：

```text
root.current = finishedWork   // 新树成为 current
```

旧 `current` 树不会立刻被销毁，而是成为新 `current` 的 `alternate`。下一轮更新时，React 以新的 `current` 为基准，通过 `alternate` 复用这些 Fiber 对象，构建下一棵 work-in-progress 树；两棵树就这样轮流充当“屏幕上的树”和“正在构建的树”，这就是双缓冲。被删除且不再被任何树引用的 Fiber 才会成为垃圾回收的对象。

### 评分点（共 2 分）

- 0.5 分：说出 `child` / `sibling` / `return` 三个方向，并能解释链表相对于子节点数组的遍历/中断优势。
- 0.5 分：访问顺序完全正确，且说明“无子节点完成、无兄弟沿父级回退”的规则。
- 0.5 分：区分 current 与 work-in-progress，说明 render 阶段不修改 DOM，所以中断/丢弃不会露出半成品；commit 同步提交。
- 0.5 分：commit 后 `root.current` 指向新树，旧树通过 `alternate` 保留并在下一轮复用。

### 简短解释

Fiber 的核心是把“渲染一棵树”拆成可中断的小工作单元：链表指针让 React 能从任意节点继续或回退，双缓冲让未完成的树与屏幕上的树互不干扰。commit 才真正改 DOM 并切换 `root.current`。

## 第 2 题（2 分｜render 与 commit 的时序）

### 参考答案

**1. 首次挂载**

```text
render 0 null
layout 0 0
passive 0 0
```

- 首次 render 时 DOM 还不存在，ref 尚未附加，所以 `pRef.current` 是 `null`。
- commit 阶段创建 `<p>` 并把它插入 DOM，然后附加 ref；`useLayoutEffect` 在 DOM 更新后、浏览器重绘前运行，读到 `"0"`。
- `useEffect` 在这之后运行（通常是绘制后），同样读到 `"0"`。

**2. 点击一次按钮**

```text
render 1 0
layout 1 1
passive 1 1
```

- `setCount` 触发重渲染，render 阶段重新调用 `App`。此时 DOM 仍然是上一次 commit 的结果，`<p>` 里还是 `"0"`，所以 render 日志读到旧值 `"0"`。render 阶段只计算新的 JSX，不会把 `"1"` 写进 DOM。
- 进入 commit 后，React 才把 `<p>` 的文本更新为 `"1"`；随后 `useLayoutEffect` 读到 `"1"`。
- `useEffect` 最后运行，也读到 `"1"`。日志顺序固定是 layout 先于 passive。

补充：`useEffect` 相对“浏览器绘制”的时机并不总是严格在绘制之后。react.dev 说明，由交互触发的更新，React 可能在该次绘制之前运行 passive effect；`useLayoutEffect` 则保证在 DOM 提交后、重绘前运行。本答案只依赖日志顺序，不依赖“passive 一定在绘制后”。

**3. 在 render 里直接写 `pRef.current.textContent`**

render 必须是纯计算：相同的 props/state 应得到相同的 JSX，不能修改 React 已经渲染出的对象或 DOM。直接写 DOM 的具体问题：

- render 可能被执行多次（StrictMode 开发环境双调用）、被中断、被丢弃后重试；写 DOM 会在这些“不会提交”的渲染中产生真实副作用。
- 你写入的值可能马上被 commit 阶段的真实更新覆盖，或者在 commit 前短暂显示出去，造成闪烁和不可预测的 UI。
- 它绕过 React 对 DOM 的所有权，破坏并发渲染的可预测性，也让 ref 的附加/清理时机失去意义。
- 如果写入依赖 layout 信息，还会在 DOM 尚未更新时读到旧布局。

DOM 写入应放在 commit 阶段触发的代码中：ref 回调、`useLayoutEffect`、`useEffect`，或事件处理函数。render 只返回 JSX。

**4. 一句话分工**

- **render 阶段**：调用组件、计算 JSX、协调（diff）新旧树、构建 work-in-progress；不修改宿主 DOM，可以被中断、暂停、丢弃或重做。
- **commit 阶段**：把已经算好的变更同步应用到 DOM，切换 `root.current`，附加/分离 ref 并运行 layout effect；这部分不可中断（passive effect 不在同步 commit 内）。

### 评分点（共 2 分）

- 0.75 分：首次挂载与点击后的日志顺序、值都正确（`render 0 null / layout 0 0 / passive 0 0`，`render 1 0 / layout 1 1 / passive 1 1`）。
- 0.5 分：解释 render 读到的是上一次 commit 的 DOM，render 阶段不写 DOM；commit 之后才更新。
- 0.5 分：指出 render 必须纯，直接写 DOM 会在被丢弃/重复的渲染中产生副作用、可能被覆盖、破坏 React 的 DOM 所有权。
- 0.25 分：能清楚划分 render 与 commit 的职责。

### 简短解释

render 是“算出应该是什么”，commit 是“把应该是什么写到屏幕上”。ref 指向的是已经提交的 DOM，所以在下一次 render 中读 ref，看到的是上一帧的结果；这正好可以用来观察 render 与 commit 的时间差。

## 第 3 题（3 分｜同层 diff、index key 与 key 变化）

### 参考答案

**1. 在开头插入 X：`[A, B, C] → [X, A, B, C]`**

旧 key 是 0(A)、1(B)、2(C)，新 key 是 0(X)、1(A)、2(B)、3(C)。React 按 key 匹配，复用了 0、1、2 三个 `Row`，只新建 key 3 的 `Row`。

四个输入框从左到右显示：

```text
hello, '', '', ''
```

- 第 1 行（现在名字是 X）：复用了原来 A 的 `Row`，`note` state 仍是 `"hello"`；
- 第 2 行（A）：复用了原来 B 的 `Row`，空备注；
- 第 3 行（B）：复用了原来 C 的 `Row`，空备注；
- 第 4 行（C）：新建的 `Row`，空备注。

控制台只打印：

```text
mount C
```

因为只有 key 3 是新的；前三个 `Row` 被复用，`useEffect` 依赖为空，不会重新执行。`hello` 这份 state 并没有跟着 A 走，而是留在“第 0 个位置”，现在显示在名字 X 旁边。

原因：`key={index}` 把“位置”当成了身份。插入让所有元素的位置后移，React 认为第 0 位的组件还是同一个组件，只是 `name` prop 从 A 变成了 X，于是保留它的 state。

**2. 删除 A：`[A, B, C] → [B, C]`**

旧 key 0(A，备注 hello)、1(B，空)、2(C，空)；新 key 0(B)、1(C)。React 复用 key 0 和 1，删除 key 2。

- 第 1 行名字变成 B，但输入框仍显示 `hello`：A 的 state 被 B 复用；
- 第 2 行名字变成 C，显示空备注：B 的 state 被 C 复用；
- 原来 C 的 `Row`（key 2）被卸载，控制台打印 `unmount C`，C 的备注 state 被销毁。

所以 `hello` 最后显示在 **B** 那一行；被销毁的是 **原来的 C** 的 state。注意 A 的 state 并没有被销毁，而是错误地交给了 B——这正是 index key 最危险的地方。

**3. 改成 `key={item.id}`，以及把 index 再拼进 key**

改成 `key={item.id}` 后：

- 旧 key 是 `a, b, c`，新 key 是 `x, a, b, c`；
- React 按 id 匹配，A、B、C 三个 `Row` 全部复用，只有 X 新建；
- A、B、C 的备注、输入框 DOM 节点都保留；控制台只打印 `mount X`；
- DOM 节点可能被移动（插入到最前面），但因为是同一个 DOM 节点在移动，输入框的焦点通常也能保留。

如果改成：

```tsx
key={`${item.id}-${index}`}
```

插入 X 后：

- 旧 key：`a-0, b-1, c-2`；
- 新 key：`x-0, a-1, b-2, c-3`；
- 没有任何 key 能匹配上，React 会卸载全部旧 `Row`（`unmount A/B/C`），再挂载全部新 `Row`（`mount X/A/B/C`）；
- 所有备注清空，输入框 DOM 被重新创建，焦点丢失，Effect 重新 setup。

原因：key 是组件身份的一部分。即使元素类型仍然是 `Row`，key 变了，React 就认为这是另一个组件实例，必须删除旧 Fiber 及其整个子树、重新挂载。把会变化的 `index`（或 `status` 之类）拼进 key，会让“看起来没换”的行在每次变化时重建。

**4. 同层 diff 的判断条件**

React 在同一个父节点下匹配新旧子节点时，主要看：

1. **key**：是否相同；
2. **元素类型（type / elementType）**：是否相同。

两者都相同，才复用旧 Fiber（保留 state 和 DOM，更新 props）；否则删除旧 Fiber 及其子树，挂载新的。

- **key 相同，但类型从 `Row` 变成 `section`**：类型不同，不能复用。旧的 `Row` 被卸载，state 销毁，DOM 被移除；新的 `section` 重新挂载。
- **类型相同，但 key 变了**：key 不同，同样不能复用，旧组件卸载、新组件挂载，state 和 DOM 都重建。
- **key 只需在兄弟之间唯一**，不需要全局唯一。不同父节点下可以使用相同的 key；没有显式 key 时，React 用位置（索引）作为隐式的 key。
- key 只是给 React 的提示，**不会作为 prop 传给组件**；组件需要这个 id 时要另外传一个 prop，例如 `<Row key={item.id} id={item.id} />`。

另外，单节点与数组的 diff 细节略有不同：单个子节点主要比较 type/key；数组会先按 key 建立映射再匹配。但“key + type 决定复用”这条规则是一致的。

### 评分点（共 3 分）

- 1 分：插入场景的四个输入框值与 `mount C` 正确；能解释 index key 让 state 留在“位置”而不是跟着数据走。
- 0.75 分：删除场景正确（`hello` 出现在 B、控制台 `unmount C`、C 的 state 被销毁），并指出 A 的 state 被错误复用而不是销毁。
- 0.75 分：`key={item.id}` 时 A/B/C 保留 state 与 DOM、只挂载 X；``key={`${id}-${index}`}`` 时全部卸载重建、备注和焦点丢失。能说明 key 变化等于身份变化。
- 0.5 分：diff 规则说清 key + type 两个条件；两个反例（同 key 不同类型、同类型不同 key）都正确；知道 key 只在兄弟间唯一。

### 简短解释

协调不是“按数组下标把新旧节点一一对应”，而是先按 key 建立身份，再比较类型。稳定 key 让 React 能把“同一个数据项”在重排、插入、删除后仍然认出来；index key 把身份绑在位置上，数据一动，state 就错位。key 一旦变化，React 会认为这是一个全新的组件，旧子树连同 DOM 和 state 一起被销毁重建。
