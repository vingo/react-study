## 复习 1（0.5 分｜条件渲染与 state 保留）

### 参考答案

1. **写法 A：草稿保留。** 两个分支都是 `<Editor />`，位置相同、组件类型相同、没有 key 变化。React 协调时只比较“同一位置上的元素类型和 key”，不关心 JSX 写在哪个分支里，因此会复用同一个 `Editor` 实例，`draft` state 保留。
2. **写法 B：草稿丢失。** 外层元素类型从 `div` 变成 `section`，React 认为这是不同类型的元素，会卸载整个旧子树（包括 `Editor`），再挂载新子树。`Editor` 的 state 被销毁，草稿回到 `''`。
3. **两侧都换成 `<Panel>`：草稿保留。** 外层类型相同（都是 `Panel`），React 复用 `Panel`，继续向下协调；`Editor` 仍在相同位置、相同类型，因此也被复用，`draft` 保留。前提是 `Panel` 内部的 children 结构没有让 `Editor` 的位置或 key 发生变化。

一般规则：React 按“树中的位置 + 元素类型 + key”判断是否复用组件实例。同位置同类型（同 key）保留 state；类型变化、key 变化、或位置结构变化会卸载旧实例并重建 state。`key` 是显式覆盖位置身份的手段。

### 评分点（共 0.5 分）

- 0.25 分：正确判断 A 保留、B 丢失，并说明 B 是外层元素类型变化导致整棵子树卸载重建。
- 0.25 分：正确判断两侧都是 `Panel` 时保留，并能概括“位置 + 类型 + key”的复用规则。

### 简短解释

A 中两个 `Editor` 虽然写在两个分支，但协调后是同一位置、同一类型，React 看到的是“同一个组件”；B 中 `div` 与 `section` 是不同类型，React 先卸载再挂载，子树 state 自然清零。

## 复习 2（0.5 分｜reducer 的纯度与不可变更新）

### 参考答案

**两处问题：**

1. `const next = tasks` 只是复制了数组引用，随后 `task.done = !task.done` 直接修改了原数组里的原 task 对象，最后又返回同一个 `tasks` 引用。reducer 必须返回新数组和新对象，不能修改参数。
   - React 用 `Object.is` 比较 reducer 的返回值与上一次 state；返回同一个数组引用时，React 会认为 state 没变，可能直接 bail out，不重新渲染，界面看起来“没更新”。
   - StrictMode 在开发环境会双调用 reducer 以暴露不纯行为：第一次把 `done` 翻转，第二次又在同一个对象上翻转回来，最终可能看起来完全没变。原 state 也已经被污染。
2. `crypto.randomUUID()` 放在 reducer 里，使 reducer 变成非纯函数：同样的 state 和 action 每次调用可能得到不同结果。StrictMode 双调用会生成两个不同 ID；时间旅行调试、重放、测试都不可靠。随机值应该在事件处理函数中生成，然后作为 action 的一部分传入 reducer。

**正确写法：**

```tsx
case 'toggled':
  return tasks.map(task =>
    task.id === action.id
      ? { ...task, done: !task.done }
      : task
  )
```

`added` 的 action 应携带在事件处理函数中生成的 id（同时把 `Action` 的 `added` 分支改为 `{ type: 'added'; id: string; text: string }`）：

```tsx
// 事件处理函数中
dispatch({ type: 'added', id: crypto.randomUUID(), text })

// reducer 中
case 'added':
  return [...tasks, { id: action.id, text: action.text, done: false }]
```

### 评分点（共 0.5 分）

- 0.25 分：指出原地修改 task、返回同一数组引用，并说明 React 可能因引用相同而跳过更新；给出 `map` + 展开对象的正确实现。
- 0.25 分：指出 reducer 中生成随机 ID 破坏纯度，说明 StrictMode 双调用/重放会导致不同结果；说明 ID 应在事件处理函数中生成并通过 action 传入。

### 简短解释

reducer 是“根据旧 state 和 action 算出新 state”的纯函数：不能改参数，不能有随机性。返回同一个引用不仅违反不可变更新，还会让 React 误以为没有变化；随机 ID 则让同一个 action 无法得到可重复的结果。

## 第 1 题（3 分｜Profiler 读图、memo 失效与优化顺序）

### 参考答案

#### 1. `actualDuration`、`baseDuration`、`phase`

- `phase`：这次提交属于 `"mount"`（首次挂载）、`"update"`（因 props/state/Hook 变化而更新）还是 `"nested-update"`。
- `actualDuration`：本次更新中，渲染 `<Profiler>` 及其后代实际花掉的毫秒数。它包含了这次真正渲染的子树；因为 memo 而跳过渲染的后代不计入。理想情况下，挂载后随着 memoization 生效，这个值会明显下降。
- `baseDuration`：对“如果没有做任何优化，整个被包裹子树重新渲染要花多久”的估算。它由树中每个组件最近一次渲染耗时相加得到，代表最坏情况（首次挂载或完全没有 memoization）。把 `actualDuration` 和它比较，可以判断 memoization 是否在起作用。

**结合日志：**

- mount 时 `actualDuration ≈ baseDuration`（142.3 vs 139.8），符合首次挂载要渲染整棵子树的情况。
- update 时 `actualDuration` 仍有 131.1ms，约为 `baseDuration` 的 94%，说明这次更新几乎整棵被包裹子树都重新渲染了，`memo` 并没有让 `Chart` 跳过渲染。如果 `Chart` 真的 bail out，`actualDuration` 应该远小于 `baseDuration`，而不是同一量级。
- 更准确地说：日志显示的是“这次提交里 profiled 子树实际渲染了多少”，要结合代码才能知道是哪个 prop 破坏了 `memo`；单看数字不能直接归因。

**这些数字不能说明的事情（至少两点）：**

- 它们只统计 **render 阶段** 的 profiled 子树，不包含 commit、DOM 变更、layout、paint、Effect、网络请求等时间，也不包含 Profiler 之外的兄弟子树。
- `baseDuration` 是估算值，不是实际跑了一遍“无 memo”的基线；不能把它当成“优化节省了多少”的精确值。
- 开发构建有 Profiling 开销，StrictMode 还可能双调用 render；这些数字不能直接代表生产环境的绝对耗时。要得到更准确的结果，应使用生产 profiling 构建，并在接近用户的设备/CPU 限速下测量。
- 不同机器、不同交互之间的绝对值不可直接比较；`actualDuration` 也不等于“用户感知的延迟”。

#### 2. 点击“切换主题”时 `Chart` 会不会重新渲染

**会。** `Chart` 被 `memo` 包裹，但 `memo` 默认用 `Object.is` 浅比较每个 prop：

- `data`：来自 `useMemo(() => buildSeries(rows), [rows])`，`rows` 是模块级常量，`data` 在主题切换时引用稳定。
- `options={{ animate: true }}`：每次 `Dashboard` 渲染都会创建一个新的对象字面量，引用不同。
- `onSelect={id => console.log('picked', id)}`：每次渲染都会创建一个新的箭头函数，引用不同。

只要有一个 prop 引用不同，`memo` 就不会跳过 `Chart`。所以主题切换仍然触发约 120ms 的绘制。注意：即使 `data` 稳定，另外两个 prop 也足以让 memo 失效；反过来，如果 `data` 写成 `buildSeries(rows)` 直接调用，它也会每次新建，同样会破坏 memo。`memo` 也不能阻止组件自身 state 变化或它使用的 Context 变化。

**修法一：只改 props 身份。**

```tsx
const CHART_OPTIONS = { animate: true } // 模块级常量

const handleSelect = useCallback((id: string) => {
  console.log('picked', id)
}, [])

<Chart data={data} options={CHART_OPTIONS} onSelect={handleSelect} />
```

如果 `handleSelect` 需要读取 `Dashboard` 的 props/state，就把这些值放进依赖数组；如果完全不需要，模块级函数或空依赖的 `useCallback` 都可以。这样三个 prop 在主题切换时都保持同一引用，`memo` 才会 bail out。

**修法二：改组件结构（更彻底）。** 把主题 state 下沉到真正需要它的组件，并用 `children` 组合把 `Chart` 传进去：

```tsx
function ThemeShell({ children }: { children: React.ReactNode }) {
  const [theme, setTheme] = useState<'light' | 'dark'>('light')

  return (
    <div className={theme}>
      <button onClick={() => setTheme(t => t === 'light' ? 'dark' : 'light')}>
        切换主题
      </button>
      {children}
    </div>
  )
}

function Dashboard() {
  const data = useMemo(() => buildSeries(rows), [rows])

  return (
    <ThemeShell>
      <Profiler id="chart" onRender={onRender}>
        <Chart data={data} options={CHART_OPTIONS} onSelect={handleSelect} />
      </Profiler>
    </ThemeShell>
  )
}
```

现在主题 state 在 `ThemeShell` 内部。切换主题时只有 `ThemeShell` 重新渲染，`Dashboard` 不会重新渲染；`children` 是上一次 `Dashboard` 渲染时创建的同一个元素，React 会复用它，`Chart` 子树不会重新渲染。这就是“状态下沉 + 组合（children）”的结构性优化。

**为什么后者更彻底：**

- 它从源头消除了“无关 state 变化导致整棵树重渲染”，而不是靠逐个稳定 prop 来打补丁。
- 它不依赖“每个对象/函数都恰好被 memo 化”；以后新增一个不稳定 prop，也不会让这次主题切换重新变慢。
- `memo` 只是局部的性能优化，一个 prop 不稳定就会整体失效；结构优化则让这次渲染根本不需要发生。

如果 `Chart` 真的需要根据主题改变颜色，那么主题变化时它本来就必须重渲染，这时才考虑 `memo` 或把主题通过 CSS 变量等方式隔离；本例中 `theme` 只影响外层 `div` 的 class。

#### 3. 更合理的优化步骤与 `memo` 的适用条件

**顺序：先测量、再结构、后 memo。**

1. **测量**：用 React DevTools Profiler / `<Profiler>` 确认这次交互是否真的慢、慢在哪个组件、是 render 还是 commit/paint；在生产 profiling 构建和合适的 CPU 限速下复现。不要凭直觉给所有对象套 `useMemo`。
2. **结构优化**：优先做“减少需要渲染的工作”——状态下沉（把 `theme` 放进 `ThemeShell`/`ThemeToggle`）、用 `children` 组合避免父组件 state 变化波及子树、移除不必要的 Effect 和派生 state、保持 render 纯净。很多性能问题在这一步就消失了。
3. **memo 化**：只对“确实频繁重渲染、且渲染昂贵”的组件使用 `memo`；用模块常量、`useMemo`、`useCallback` 稳定它的 props；对确实昂贵且依赖很少变化的计算使用 `useMemo`。加完后重新测量，确认收益。
4. **并发工具**：如果是输入/交互被慢渲染阻塞，再考虑 `useTransition` / `useDeferredValue`（上一课内容）；它们改善优先级，不减少总工作量，也不能替代前面的结构优化。

**`memo` 真正有价值的条件：**

- 组件**经常**因为父组件重渲染而重渲染；
- 每次重渲染时 props **完全相同**（`Object.is` 浅比较都相等）；
- 组件自身的渲染**确实昂贵**（有可感知的卡顿，Profiler 能证明）；
- 并且你已经在测量后确认它是瓶颈。

反例：props 总是新对象/新函数（`memo` 完全无效）；渲染很便宜（没有可感知收益）；组件自身 state/Context 变化（`memo` 不会阻止）；只需要优化首次挂载（`memo` 主要帮助更新，首次仍要渲染）。

### 评分点（共 3 分）

- 1 分：正确解释 `actualDuration`、`baseDuration`、`phase`；根据日志判断 memo 没有让 Chart 跳过渲染（actual 与 base 同量级）；至少说出两点这些数字不能代表的事情（commit/paint/Effect、Profiler 外子树、估算值、开发/Profiling 开销、生产环境差异等）。
- 1 分：判断 Chart 会重渲染；指出 `options` 与 `onSelect` 每次都是新引用（并说明 `data` 为什么稳定）；给出 props 层修法（模块常量 / `useCallback`）和结构层修法（状态下沉 + children 组合），并说明结构修法更彻底的原因。
- 1 分：给出“测量 → 结构 → memo →（必要时）并发”的合理顺序；说明 `memo` 有价值的条件（频繁、相同 props、昂贵），以及 props 总变、渲染便宜、自身 state/Context 等反例。

### 简短解释

`actualDuration` 与 `baseDuration` 同量级，说明“该跳过的没跳过”。`memo` 的浅比较只认引用：一个每次新建的对象或函数就足以让它失效。与其逐个稳定 prop，不如把无关 state 下沉、用 `children` 组合，让这次渲染根本不发生；memo 应该是测量后的最后一步。

## 第 2 题（2.5 分｜useMemo / useCallback 的语义与误用）

### 参考答案

#### A. 报告筛选（1 分）

**结果：** `List` 仍显示上一次 `status` 对应的数据（例如从 `open` 切到 `done` 后仍显示 `open` 的结果），直到 `rows` 引用发生变化才可能重新计算。

**问题一：依赖数组漏了 `status`。** `useMemo` 用 `Object.is` 比较依赖；`status` 不在依赖里，React 会复用上一次的缓存值。`calculateValue` 里读取了 `status`，所以它必须出现在依赖数组中。

**问题二：在 `useMemo` 的计算函数里做副作用。** `useMemo` 的计算发生在 **render 阶段**，render 必须是纯的。可能出现的后果：

- StrictMode 在开发环境会把计算函数调用两次，`analytics.track` 可能重复上报；
- 并发渲染下，这次 render 可能被中断或丢弃，但副作用已经发生，可能上报了从未提交到屏幕的渲染；
- React 可能在特定情况下丢弃 `useMemo` 缓存（例如开发环境热更新、首次挂载时组件挂起），导致计算再次执行；
- `useMemo` 只是性能优化，不是“只执行一次”的语义保证。

**修复：**

```tsx
function Report({ rows, status }: { rows: Row[]; status: string }) {
  const visible = useMemo(
    () => rows.filter(row => row.status === status),
    [rows, status]
  )

  useEffect(() => {
    analytics.track('report-render', { status })
  }, [status])

  return <List rows={visible} />
}
```

分析代码必须保持纯；`analytics` 属于提交后的副作用，放在 `useEffect`（或触发筛选的事件处理函数）里。注意 StrictMode 下 Effect 也会在开发环境额外执行一次 setup/cleanup；统计上报需要幂等或去重。若想记录“每次结果变化”，依赖可以按需求改为 `[rows, status]` 或 `[visible]`，但不要放回 `useMemo`。

#### B. 列表项的回调（1 分）

`handlePick` 确实被 `useCallback` 缓存了，但传给 `Row` 的不是 `handlePick` 本身，而是：

```tsx
onPick={() => handlePick(item.id)}
```

这个箭头函数在**每次 `List` 渲染、每个 item 上**都会重新创建。`Row` 被 `memo` 包裹，浅比较时 `onPick` 每次都是新引用，所以 `Row` 仍然重渲染。`useCallback` 只缓存了 `handlePick`，没有缓存“每个 item 的包装箭头函数”。

**修法：把稳定函数直接传下去，让 `Row` 用它收到的参数调用。**

```tsx
<Row key={item.id} item={item} onPick={handlePick} />
```

```tsx
const Row = memo(function Row({ item, onPick }) {
  return <button onClick={() => onPick(item.id)}>{item.name}</button>
})
```

`Row` 的 props 契约没有变：仍然接收 `item` 和 `onPick`，仍然用 `item.id` 调用 `onPick`。现在 `onPick` 在 `List` 重渲染时保持同一引用（前提是 `onSelect` 稳定），`memo` 才能跳过未变化的行。如果 `onSelect` 本身每次都是新函数，`handlePick` 也会跟着变，需要先在源头稳定 `onSelect`。

**启用 React Compiler 时：** 文档明确用这个模式举例：编译器可以正确优化带或不带内层箭头的写法，按 item 记忆 JSX/函数，使 `Row` 只在真正相关的变化时重渲染。但这属于编译器行为；练习环境未启用编译器，手写代码仍应避免在 memo 子组件的 props 里创建新函数。不能把“编译器会处理”当作不启用编译器时的正确性依据。

#### C. 哪些 memo 化值得（0.5 分）

- **C1 `price * quantity`：不值得。** 这是极便宜的算术；`useMemo` 的依赖比较和缓存维护可能比计算本身还贵，而且结果是原始值，按值比较本来就稳定。直接算即可。
- **C2 给 DOM `<button>` 的 `onClick` 套 `useCallback`：通常不值得。** 宿主元素不会因为 handler 引用变化而“跳过渲染”；这里也没有 memo 子组件。`useCallback` 的价值主要在于传给 `memo` 子组件、作为其他 Hook 的依赖，或避免 Effect 因函数身份变化而重复执行。直接内联函数更简单。
- **C3 复制并排序：可能值得，但应先测量。** `[...items].sort(compare)` 是 O(n log n) 且会复制数组；如果 `items` 很大、排序确实昂贵、且 `items` 引用很少变化，`useMemo` 能避免每次渲染重复排序。稳定引用还能帮助 memo 子组件或 Effect 依赖。如果数组很小或每次渲染 `items` 都变，缓存不会命中，可能不值得。

判断标准不是“能不能 memo”，而是：计算是否真的昂贵、依赖是否真的很少变、结果是否会被用于 memo 子组件/Effect 依赖，以及加完后测量是否真的有收益。

### 评分点（共 2.5 分）

- 1 分：A 中正确指出 `status` 缺失导致结果过期，`analytics` 在 render 阶段执行副作用的问题（StrictMode 双调用、可丢弃 render/缓存），给出 `[rows, status]` 和 Effect/事件处理函数的修复。
- 1 分：B 中正确指出每次渲染新建的内层箭头函数使 `memo` 失效；给出直接传 `handlePick` 并让 Row 调用 `onPick(item.id)` 的修法；说明编译器可自动处理该模式，但不能据此认为不启用编译器时也正确。
- 0.5 分：C 中三处判断合理（C1 不值得、C2 通常不值得、C3 视规模/依赖稳定性而定），并说明理由或“先测量”。

### 简短解释

`useMemo` 缓存的是“计算结果”，`useCallback` 缓存的是“函数本身”；二者都只按依赖的 `Object.is` 比较，且都只是性能优化，不能承担副作用或正确性。内层箭头函数是 memo 的常见杀手：缓存了外层函数，不等于缓存了每次新建的包装函数。

## 第 3 题（2.5 分｜React Compiler 的自动 memo、bailout 与指令）

### 参考答案

#### 1. 哪些函数会被编译；编译器做什么；指令

**`Cart` 和 `PriceTag` 会被自动 memo 化，`formatPrice` 不会。**

React Compiler 1.0 是**构建时**工具（以 Babel/Vite/Metro/Rsbuild 等插件形式接入），在构建阶段分析组件/Hook 并插入自动 memoization；它不是浏览器里的运行时开关，也不会在每次 render 时临时决定是否 memo。它已稳定，可支持 React 17/18/19（17/18 通常需要 `react-compiler-runtime` 包），但本练习环境没有启用。

默认的 `compilationMode: 'infer'` 通过命名和代码形态识别 React 组件/Hook：

- 函数名像组件（PascalCase）或 Hook（`use` 前缀）；
- 并且函数创建 JSX 和/或调用其他 Hook。

`Cart` 和 `PriceTag` 都是 PascalCase 且返回 JSX，所以会被编译并自动 memo 化。`formatPrice` 是小写开头的普通工具函数，不返回 JSX、不调用 Hook，不属于编译器识别的组件/Hook，因此不会被单独编译。即使它在 `PriceTag` 内部被调用，编译器也可能在 `PriceTag` 的编译结果中记忆这次调用的结果，但：

- 编译器只记忆组件和 Hook，不会把每个普通函数都变成全局 memo 函数；
- memo 结果**不会跨组件/Hook 共享**。如果 `formatPrice` 在多个组件里被调用，每个调用点各自计算/记忆；如果它真的非常昂贵且被多处复用，应该考虑在 React 之外实现自己的缓存，并先测量确认值得。

编译器自动 memoization 主要想消除两类开销：

1. **级联重渲染**：父组件 state 变化导致大量子组件跟着重渲染，即使子组件的相关输入没变；
2. **render 期间的昂贵计算**：组件/Hook 内重复执行的高成本计算。

它主要改善**更新性能**，让更新更细粒度（fine-grained reactivity）；首次挂载仍然要完成必要的工作。

**指令：**

- 只想让少数组件先试用：使用 `compilationMode: 'annotation'`，并在每个想编译的组件/Hook 函数体开头加 `"use memo"`（也可以放在模块顶部让整个模块生效）。在 infer 模式下，`"use memo"` 也可用于强制编译某个函数。
- 线上怀疑某个组件被编译坏了、需要临时排除：在函数体开头加 `"use no memo"`（模块级也可以，函数级会覆盖模块级）。无论哪种编译模式，带 `"use no memo"` 的函数都会被跳过。
- 指令是 escape hatch，不应该作为常规写法；`"use no memo"` 应带 TODO/issue，定位并修复根因后移除。

#### 2. `item.seen = true` 与编译器

这行在 render 期间直接修改了 prop 对象，违反 Rules of React 的纯函数/不可变约束。编译器的策略是：

- 它**依赖**代码遵守 Rules of React；遇到可能违反规则的代码时，会**跳过优化（bailout）**，而不是冒险改变应用行为。编译器构建错误很少见，因为“跳过”比“报错”更常见；`panicThreshold: 'none'` 等配置也体现了“跳过有问题的组件、尽量不阻断构建”的取向。
- 它**不会自动把 mutation 改写成不可变更新**，也不应该指望它“修正”这段代码。
- ESLint 的 React Hooks/Compiler 规则（如 purity、immutability 相关规则）会帮助发现这类违规；编译器的日志/DevTools 徽标可以显示哪些组件被编译。具体能否被静态检测到取决于代码形态；无论检测到与否，这段代码本身都是 bug。

如果编译器没有检测到并编译了 `Cart`，自动 memoization 可能让行为更糟或更不可预测：编译器可能认为 `items` 引用没变就跳过重算 `reduce`，于是 `seen` 的修改不会按你期望的每次 render 发生；也可能因为 memo 化的边界让某些更新“看起来丢了”。这类“依赖 memoization 才正确”的代码正是编译器文档警告的主要破坏模式，可能导致 Effect 过度触发、无限循环或更新丢失。

`"use no memo"` 在这里是**诊断/临时隔离手段**：加上它如果问题消失，说明问题很可能与编译结果或 Rules of React 违规有关；但它不是修复。正确做法是消除 mutation，例如：

```tsx
const prepared = items.map(item => ({ ...item, seen: true }))
const total = prepared.reduce(
  (sum, item) => sum + item.price * item.quantity,
  0
)
```

或者如果 `seen` 只是外部副作用，把它移到事件处理函数/Effect 中，不要放在 render 里。

#### 3. “可以删光手动 memo，并依赖 memo 保证正确性”

这个说法不对，至少有三方面问题：

1. **现有 `useMemo` / `useCallback` / `memo` 不应盲目删除。** 文档建议：现有 memoization 可以保留，或者在充分测试后再移除；删除可能改变编译输出。编译器在多数情况下能达到与手写相当或更精细的 memoization，但 `useMemo` / `useCallback` 仍然是 escape hatch，用于精确控制，尤其是**作为 Effect 依赖**的值——需要稳定引用以避免 Effect 反复触发时，手写 memo 仍然有意义。
2. **编译器会 bailout，不等于“所有代码都被优化”。** 它可能跳过无法安全分析的函数；被跳过的组件仍然可能需要手动 memo。`"use no memo"`、`panicThreshold`、logger、ESLint 和 DevTools 都是用来发现/隔离这些情况的，而不是保证“全自动”。
3. **memoization 是性能优化，不是正确性保证。** 如果代码只有在某个值被 memo 时才正确，那它本身就是脆弱的：编译器可能采用不同的 memoization 策略，导致 Effect 过度触发、无限循环或更新丢失。文档明确指出，编译器破坏应用的主要方式之一就是代码“依赖 memoization 来保证正确性”。应该修复根因（不要依赖对象/函数的引用身份、把对象/函数移到 Effect 内部、使用原始值、正确声明依赖），而不是依赖 memo。
4. 补充：编译器不替代 Profiler。仍然要先测量、确认瓶颈，再评估编译前后的实际收益；它也不会让普通工具函数的昂贵计算跨组件共享。

- 1 分：正确判断 `Cart`、`PriceTag` 会被编译而 `formatPrice` 不会，并说明 infer 模式的识别条件；说出两类优化目标（级联重渲染、昂贵计算）；说明 memo 不跨组件共享；正确说出 `"use memo"`（annotation 模式/强制编译）与 `"use no memo"`（临时排除）的用途。

### 简短解释

Compiler 1.0 是构建时的自动 memoization：它让“父组件更新导致整棵子树重渲染”和“render 中的昂贵计算”变得不那么需要手写 `memo`/`useMemo`/`useCallback`。但它建立在 Rules of React 之上：遇到可疑代码就跳过优化，而不是修复代码；指令只是 opt-in/opt-out 的开关。手动 memo 仍然是有用的精确控制手段，尤其对 Effect 依赖；而“正确性依赖 memo”本身就是需要修掉的 bug。
