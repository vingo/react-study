## 复习 1（0.5 分｜React Router 的 Outlet 与 errorElement）

### 参考答案

1. **页面上只有 `<Header />` 和一个空的 `<main />`。** `RootLayout` 没有渲染 `<Outlet />`，所以它的子路由 `ProjectLayout` 根本不会渲染；即使 `RootLayout` 有 Outlet，`ProjectLayout` 自身也没有 Outlet，`Tasks` 仍然不会出现。最小改动是在两处都加出口：

   ```tsx
   function RootLayout() {
     return (
       <div>
         <Header />
         <main><Outlet /></main>
       </div>
     )
   }

   function ProjectLayout() {
     return (
       <section>
         <h2>项目</h2>
         <Outlet />
       </section>
     )
   }
   ```

2. **在补上两个 Outlet 后**，`Overview` 的 loader 抛出 404 时，最近带 `errorElement` 的路由是 `projects/:projectId`，所以渲染 `<ProjectError />`。它替换的是 project 路由的元素（`ProjectLayout` 及其子路由），但根路由 `RootLayout` 仍在它上面，所以 `<Header />` 还在。`useRouteError()` 能拿到 `status: 404` 的 `Response`，`isRouteErrorResponse(error)` 为 `true`。

### 评分点（共 0.5 分）

- 0.25 分：正确指出根布局缺 Outlet 导致子路由不渲染，并指出 ProjectLayout 也缺 Outlet；给出两处修复。
- 0.25 分：正确指出最近的 `ProjectError` 会渲染、Header 仍在（根路由在错误路由之上），并能说明是项目路由的 errorElement。

### 简短解释

React Router 的布局组合靠 `<Outlet />`，不是自动的；错误边界从出错路由向上找最近的 `errorElement`，父级布局仍在。App Router 的 `children`/`error.tsx` 是同一思想的文件系统版本，但边界范围由特殊文件的组件层级决定。

## 复习 2（0.5 分｜useDeferredValue 与 Suspense）

### 参考答案

1. **用户看到旧结果，不会看到 `Spinner`。** `deferredQuery` 的后台更新属于 transition；React 在已经显示过内容的 Suspense 边界上遇到挂起时，会保留旧内容，等新内容就绪后切换。只有首次挂载、边界刚出现、`key` 变化导致边界重建，或没有旧内容可保留时，fallback 才会立即出现。
2. `stale === true` 表示当前列表仍对应旧的 `deferredQuery`，即 UI 落后于输入，**不等于**“网络请求正在进行”。请求可能在 `stale` 为 true 之前就完成，也可能在完成后仍然因为渲染而未切换；它只是一个渲染层的滞后信号。
3. **不一定。** 在 App Router 中，导航到没有可用预取/缓存内容的目标段时，`loading.tsx` 的 Suspense fallback 可以立即显示；如果导航被 transition 包裹、旧页面仍在展示，或目标内容已缓存，则可能继续显示旧 UI。区别在于：`useDeferredValue` 是同一棵树内的低优先级渲染，已有 Suspense 内容默认保留；路由导航可能切换到新 segment 的 loading 边界。

### 评分点（共 0.5 分）

- 0.25 分：正确判断旧结果保留、不显示 Spinner，并说明 transition/已显示 Suspense 边界的旧内容保留机制；能说出 fallback 出现的条件。
- 0.25 分：正确解释 `stale` 是渲染滞后而非网络状态；说明 App Router 导航的 loading 行为取决于目标段缓存/预取/transition，不能一概而论。

### 简短解释

`useDeferredValue` 只延迟渲染，不发起或取消请求；Suspense 在后台 render 挂起时保留已提交内容。App Router 的 `loading.tsx` 是另一套导航级 Suspense 边界，是否出现取决于目标段是否有可复用的 UI。

## 第 1 题（3 分｜文件约定、布局链与 route group）

### 参考答案

#### 1. 命中结果（1 分）

| URL | page | layout 链（根 → 叶） | params | groups |
|---|---|---|---|---|
| `/cart` | `app/(shop)/cart/page.tsx` | `app/layout.tsx` → `app/(shop)/layout.tsx` | `{}` | `['shop']` |
| `/products/42` | `app/(shop)/products/[id]/page.tsx` | `app/layout.tsx` → `app/(shop)/layout.tsx` | `{ id: '42' }` | `['shop']` |
| `/about` | `app/(marketing)/about/page.tsx` | `app/layout.tsx` | `{}` | `['marketing']` |
| `/docs/a/b` | `app/docs/[...slug]/page.tsx` | `app/layout.tsx` → `app/docs/layout.tsx` | `{ slug: ['a', 'b'] }` | `[]` |

- `(marketing)` 下没有 `layout.tsx`，所以 `/about` 的布局链只有根布局；分组本身不进入 URL。
- `/marketing/about` **不会命中**：`(marketing)` 是 route group，URL 中不应出现 `marketing`。
- `/docs` **不会命中** `[...slug]`：catch-all 至少要消费一段。要匹配 `/docs` 需要 `[[...slug]]`，或在 `app/docs/` 放一个 `page.tsx`。

#### 2. 布局保留、page 替换、root layout（1 分）

从 `/cart` 到 `/products/42`：

- `app/layout.tsx`（根布局）和 `app/(shop)/layout.tsx` 都复用，state、滚动位置、输入内容保留，保持交互；
- 只有 page 被替换：cart page 换成 products/[id] page；
- `(shop)` 不出现在 URL 中；两个 URL 分别是 `/cart` 和 `/products/42`。

如果删除顶层 `app/layout.tsx`，让 `(shop)` 和 `(marketing)` 各自拥有根布局（各自包含 `<html>`/`<body>`），那么跨这两个区域导航会触发**整页刷新（full page load）**，而不是客户端导航；同一根布局内部仍然保留布局状态。多个根布局适合完全不同的应用外壳，不要为了“多一个布局”滥用。

#### 3. loading 位置、layout 挂起、params（1 分）

- 只让 `/cart` 有自己的 skeleton：把 `loading.tsx` 放进 `app/(shop)/cart/`（与 cart page 同目录），它只包住 cart page；`(shop)/loading.tsx` 会作用于整个 shop 段。
- `(shop)/loading.tsx` **接不住** `(shop)/layout.tsx` 的慢数据：组件层级是 `layout > loading > page`，loading 在 layout 内部，layout 在它上面。layout 读取未缓存数据或 `cookies()/headers()` 时：
  - 未开启 Cache Components：导航会阻塞到 layout 渲染完，loading fallback 不显示；
  - 开启 Cache Components：layout 里的运行时读取必须自己用 `<Suspense>` 包住，否则构建期会报 blocking-route；应把慢取数下沉到 page，或在 layout 内手写 Suspense。
- Next.js 16 的 `params` 是 Promise：Server Component 用 `async` + `await params`；Client Component 用 `use(params)`。不能像 Next.js 14 那样同步读取。

### 评分点（共 3 分）

- 1 分：四个 URL 的 page/layout 链/params/groups 正确；`/about` 的布局链没有不存在的 marketing layout；`/marketing/about` 与 `/docs` 不匹配的原因正确。
- 1 分：说明导航时根布局与 shop 布局保留、page 替换；route group 不影响 URL；多个根布局之间导航整页刷新。
- 1 分：cart 专属 loading 放对位置；解释 loading 不包同段 layout；说明 layout 运行时数据的两种行为；说明 params 是 Promise 及读取方式。

### 简短解释

文件系统就是路由树：route group 只加布局、不加 URL；layout 是导航时保留的骨架；loading 是 layout 内部的 Suspense 边界。把这三层关系画出来，大部分“为什么 fallback 不出现/为什么 state 丢了”的问题都能直接定位。

## 第 2 题（2.5 分｜loading / error / not-found 边界选择）

### 参考答案

#### 1. 错误边界（1 分）

- **`dashboard/settings/page.tsx` 抛错**：由 `app/dashboard/settings/error.tsx` 接住。settings page 被错误 UI 替换，`dashboard/layout.tsx` 和根布局仍然存在（例如看板侧边栏还在）。如果错误发生在 settings 的 layout（本题没有），则同段 error 接不住，会冒泡到 `dashboard/error.tsx`。
- **`dashboard/layout.tsx` 抛错**：由 `app/error.tsx` 接住。`dashboard/error.tsx` 与 `dashboard/layout.tsx` 同段，且在 layout 内部，不能捕获 layout 自身；dashboard layout 的 UI（侧边栏）随错误 UI 一起被替换，根布局仍在。
- **`app/layout.tsx` 抛错**：普通 `error.tsx` 都接不住，必须由根目录的 `app/global-error.tsx` 处理（它必须自带 `<html>`/`<body>`，也是 Client Component）。没有 global-error 时由 Next.js 默认错误页处理。

根因：组件层级是 `layout > template > error > loading > not-found > page/子 layout`。error 只包住它下面的内容，不包同段 layout，也不包父 layout。

#### 2. not-found（0.75 分）

- `dashboard/settings/page.tsx` 调用 `notFound()`：由最近的 `app/dashboard/settings/not-found.tsx` 渲染；settings 的 error/loading 边界仍然生效。
- `dashboard/reports/page.tsx` 调用 `notFound()`：reports 目录没有 `not-found.tsx`，向上找到 `app/dashboard/not-found.tsx`；再没有才到根 `app/not-found.tsx`。
- 访问完全未匹配的 `/nope`：由根 `app/not-found.tsx` 渲染（Next.js 13.3+）。未匹配 URL 没有“当前 segment”，所以不会去找某个子目录的 not-found。`global-not-found.js` 可以绕过根布局直接返回全局 404，但截至 Next.js 16 仍是 experimental。

`notFound()` 会抛出 `NEXT_HTTP_ERROR_FALLBACK;404` 并终止当前 segment 渲染；不要用 `try/catch` 吞掉它。需要局部捕获时，先让框架的中断错误透传。

#### 3. error.tsx 的客户端要求、retry/reset、事件错误、流式 404（0.75 分）

- **必须是 Client Component**：React Error Boundary 依赖客户端 class 生命周期（`getDerivedStateFromError`/`componentDidCatch`），并且错误 UI 需要按钮等交互来重试；Next.js 要求 `error.tsx` 加 `'use client'`。
- **`retry()` vs `reset()`**：`retry()` 重新取数并重渲染边界子树，适合临时性失败；`reset()` 只清除错误状态、不重新取数，适合你有特定理由只重渲染。多数场景优先 `retry()`（Next.js 16.3 起稳定）。
- **Event Handler 的错误不会被捕获**：Error Boundary 只处理渲染期错误；点击回调、`setTimeout`、已捕获的 Promise 错误要自己 `try/catch` 并存入 state。`startTransition` 内未处理的错误会冒泡到最近边界。
- **流式响应后的 404**：如果流式响应已经开始，HTTP 状态码已经固定为 200；Next.js 会渲染 not-found UI 并注入 `<meta name="robots" content="noindex">`，避免被索引。要在响应头返回真正的 404，必须在流开始前完成检查（例如 page 顶层或 Proxy）。

### 评分点（共 2.5 分）

- 1 分：三个错误场景分别对应 settings error、root error（app/error）、global-error；说明同段 layout 不被同段 error 捕获，根 layout 需要 global-error；能说明哪些 UI 被替换/保留。
- 0.75 分：三个 not-found 场景分别对应 settings、dashboard、根；解释最近边界与未匹配 URL 的根兜底；提到 `notFound()` 抛错/不要吞掉。
- 0.75 分：`error.tsx` 必须 Client 的原因；`retry` 重新取数 vs `reset` 只清状态；Event Handler 不被捕获；流式开始后 200 + noindex、流开始前才能真 404。

### 简短解释

边界选择不是“谁离得近”，而是看组件层级：layout 永远在 error/loading 外面，not-found 在 loading 里面。把 `layout > error > loading > not-found > page` 背下来，再记住未匹配 URL 归根 not-found，就能推出所有场景。

## 第 3 题（2.5 分｜流式渲染与 Next.js 16 缓存）

### 参考答案

#### 1. static shell 与流式补全（0.75 分）

- 首次请求时，static shell 包含根布局/导航、`<h1>博客</h1>`、`Posts` 的缓存结果（如果该 `use cache` 条目在预渲染时已生成并进入 shell），以及 `UserPreferences` 外层的 Suspense fallback `<p>加载偏好…</p>`。
- `UserPreferences` 依赖 `cookies()`，是运行时数据，在请求时流式补全，原地替换 fallback。`Posts` 被 `use cache` 缓存，通常进入静态 shell，而不是每次请求流式。
- 如果慢数据在 `app/blog/layout.tsx` 里，`app/blog/loading.tsx` **不能**为它显示 fallback：loading 在 layout 内部（`layout > loading`），layout 在它上面。开启 Cache Components 时，layout 里的未缓存/运行时读取必须自己用 `<Suspense>` 包住，否则构建期会报 blocking-route；也可以把慢取数下沉到 page。
- 每个 Suspense 边界是独立流式点：一个慢不会阻塞另一个；兄弟边界按完成顺序补发。`loading.tsx` 是整段 page 的粗粒度 Suspense，手写 Suspense 可以把 fallback 下沉，让更多真实内容进入 shell。

#### 2. fetch 缓存与 Cache Components（1 分）

**未开启 `cacheComponents`（上一代模型）：**

- `fetch` 默认 **不跨请求持久缓存**（`auto no cache`）：构建期可静态预渲染时可能执行一次并进入静态输出；路由在请求期渲染时每次请求都执行。想缓存必须显式声明。
- `cache: 'no-store'`：每次请求都从远端取，即使路由没有 Request-time API；不读也不写持久缓存。
- `cache: 'force-cache'`：在服务端缓存中按 URL/method/headers/body 匹配；命中且新鲜则返回，否则重新取并写入；只有 200 响应会被存储。它是 opt-in 的，连 POST、带 authorization/cookie 的请求也可以显式缓存。
- `next: { revalidate: n }`：缓存 n 秒；`false` 表示 indefinite，`0` 表示不缓存；与 `no-store` 冲突时两者都被忽略。`next.tags` 用于给缓存项打标签，供 `revalidateTag` 失效。
- 同一 render pass 内相同 GET URL + options 会自动 memoize（请求去重），只持续一次渲染，和跨请求 Data Cache 不同。

**Next.js 16 的 `use cache` / `cacheComponents`：**

- **稳定特性**：Next.js 16.0.0 起 Cache Components 从 experimental 移到顶层 `cacheComponents`，`use cache`、`cacheLife`、`cacheTag` 稳定（无 `unstable_` 前缀）。但它仍是显式开启的模型；16 的 `create-next-app` 默认开启，旧项目需迁移。开启后 `dynamic`/`revalidate`/`fetchCache` 路由段配置会报错，要求改用 `use cache` + `cacheLife`，并把未缓存/运行时读取放进 Suspense。
- **缓存键**：build ID、函数 ID、可序列化参数，以及从外层闭包捕获的变量；不同参数/闭包值生成不同条目。
- **序列化**：参数和返回值必须可序列化；class 实例、函数、Symbol、WeakMap 等不支持；`children`/Server Action 只能透传，不能在缓存作用域里读取或修改。
- **运行时 API**：缓存作用域内不能读 `cookies()`、`headers()`、`searchParams` 等请求期 API；应在作用域外读取，把值作为参数传入，参数自然进入缓存键。默认存储是进程内存，serverless 多实例不保证共享；持久共享用 `'use cache: remote'`，按用户隔离/读取运行时数据用 `'use cache: private'`。新部署会因 build ID 变化清空缓存。

#### 3. 失效方式选择（0.75 分）

- **`revalidateTag('posts', 'max')`**：把带 `posts` 标签的缓存标记为 stale，采用 stale-while-revalidate；下一次访问先返回旧内容，同时后台刷新。适合博客、商品目录等“短暂旧数据可接受”的内容。Next.js 16 起第二个 profile 参数必填，单参数形式已废弃。可在 Server Action 或 Route Handler 调用。
- **`updateTag('posts')`**：立即过期缓存并刷新当前 UI/客户端缓存，提供 read-your-own-writes；只能在 Server Action 中使用。适合用户刚发帖/改设置，必须立刻看到自己的修改。
- **`revalidatePath('/blog')`**：按路由路径失效，不需要知道 tag；`type: 'page'` 只影响该路径，`type: 'layout'` 影响该布局及其下所有页面。适合只知道路径、或数据来源没有打 tag 的场景；但可能过度失效，tag 更精确。rewrite 场景要传目标路径（destination）。
- 三者在 Server Action/Route Handler 中调用后只是标记/过期，真正重新取数发生在后续访问（`updateTag` 会配合客户端刷新）。可以组合使用：例如 `updateTag('posts')` + `revalidatePath('/blog')` 保证页面与所有用 tag 的数据一致。
- **为什么 `use cache` 里不能读 `cookies()`/`searchParams`**：缓存条目必须对相同输入返回相同输出，且键要可序列化、可确定；请求期 API 使结果依赖当前用户/请求，无法安全共享缓存。正确做法是在缓存作用域外读取，把值作为参数传入，让值成为缓存键的一部分。

### 评分点（共 2.5 分）

- 0.75 分：正确描述 static shell 的内容与流式补全；说明 layout 慢数据不能被同段 loading 捕获及 Cache Components 下的要求；说明 Suspense 边界独立。
- 1 分：正确说明 fetch 默认不持久缓存、`no-store`、`force-cache`、`revalidate`、tags 的语义；明确 `use cache`/`cacheComponents` 在 16 稳定但需显式开启；说明缓存键、序列化限制、运行时 API 限制、默认内存存储。
- 0.75 分：三种失效方式的语义/调用位置/适用场景正确；Next.js 16 `revalidateTag` 第二参数要求正确；解释 `use cache` 不能读运行时 API 及“值作为参数进入缓存键”的替代方案。

### 简短解释

流式渲染解决“先看到什么”，缓存解决“是否需要重新算”。`use cache` 把可缓存的计算显式标记出来，参数就是缓存键；运行时数据必须在缓存作用域外读取并作为参数传入。写后一致性则按“可接受短暂旧数据 → revalidateTag；必须立刻看到 → updateTag；只知道路径 → revalidatePath”选择。
