## 复习 1（0.5 分｜Transition 与输入响应性）

### 参考答案

1. **紧急更新**是 `setQuery(next)`：它直接决定受控输入框的值，必须立即提交。**Transition** 是 `startTransition` 里的搜索更新（以及由 `useDeferredValue` 派生出的结果列表更新）。输入框不会被慢搜索卡住，是因为搜索被放进较低优先级的 Transition/延迟渲染：React 可以先提交输入框的紧急更新并让浏览器绘制，再在空闲时处理搜索与结果；Transition 的 render 可中断、可重做。
2. `deferredQuery` 是 `query` 的延迟版本：它先保留旧值，等紧急更新提交后再在低优先级 render 中追上最新值，因此结果列表可以“稍后更新”。`isPending` 表示 Transition 仍在进行（还有未提交的 Transition 工作），适合显示“搜索中…”。如果 `Results` 直接读 `query`，每次输入都会让结果列表参与紧急 render；列表很贵时输入仍可能卡顿，`deferredQuery` 也就失去意义。
3. `useDeferredValue` 不是 debounce：它没有固定等待时间，也不丢弃输入；它只是让派生渲染以较低优先级追赶最新值，React 仍可能在每次输入后渲染，只是可以被打断/延后。debounce 是“等用户停止输入 N 毫秒再发请求”。本题如果只是本地渲染，deferred 足够；如果是网络请求，仍应 debounce + AbortController/请求竞态保护，二者解决不同问题。

### 评分点（共 0.5 分）

- 0.25 分：正确区分紧急的输入更新与低优先级的搜索/结果更新，说明输入不被阻塞的原因（可中断、紧急优先）。
- 0.25 分：正确解释 `deferredQuery`/`isPending`，并说明 deferred 与 debounce 的区别（无固定延迟、不丢弃输入；网络请求仍需 debounce/取消）。

### 简短解释

Transition 调的是“优先级”，不是“减少工作量”。它让输入先提交，慢列表稍后追赶；`useDeferredValue` 是渲染层的延迟，不是网络层的防抖。

## 复习 2（0.5 分｜Profiler 数字与 memo 边界）

### 参考答案

1. `actualDuration` 是本次提交中 `<Profiler>` 子树实际花在 render 上的毫秒数；`baseDuration` 是把子树中每个组件最近一次 render 的耗时相加、假设没有任何 memoization 的估算值。这里 `actualDuration`（118.4ms）与 `baseDuration`（121.0ms）几乎相同，说明这次更新几乎整棵子树都重新渲染了，**`memo` 没有让 `Chart` 跳过**。如果 `Chart` 真的 bail out，实际渲染的子树应显著小于 base，actual 会明显更低。
2. 击穿 memo 的 prop 至少有两个：`options={{ animate: true }}` 每次父组件 render 都创建新对象；`onSelect={id => ...}` 每次都是新函数。`data` 若来自 `useMemo` 或模块常量则引用稳定，不是问题。
   - **props 层修法：** 把 `options` 提成模块常量或用 `useMemo`；把 `onSelect` 用 `useCallback` 稳定（依赖写全）。这样三个 prop 浅比较相等，`memo` 才能跳过。
   - **结构层修法：** 把触发备注输入的状态下沉到独立组件，或用 `children` 组合把 `Chart` 作为稳定的 children 传入，让父组件的无关 state 变化根本不导致 `Chart` 所在子树重新 render。结构修法更彻底，因为不依赖每个 prop 恰好稳定。

### 评分点（共 0.5 分）

- 0.25 分：正确解释 actual/base，并根据数字判断 memo 未生效（actual 与 base 同量级）。
- 0.25 分：指出至少一个不稳定 prop（options 或 onSelect），给出 props 层（常量/useMemo/useCallback）与结构层（状态下沉/children）两类修法。

### 简短解释

`memo` 只做 props 浅比较；一个每次新建的对象或函数就足以让整块优化失效。actual 接近 base 是“该跳过的没跳过”的信号。

## 第 1 题（3 分｜ViewTransition 的触发、语义与降级）

### 参考答案

#### A. 为什么没有动画

1. **“切换内容”** 只改变 `<ViewTransition>` 内部 `article` 的文本，边界本身没有挂载/卸载，因此它是 **update**（如果内容变化被 React 视为边界内 DOM 变化）。“切换显示”让整个边界从无到有/从有到无，分别是 **enter / exit**。
   真实浏览器里可能一个动画都看不到，原因至少包括：
   - `setTab`、`setShow` 都是**普通同步 setState**，不是 Transition；紧急更新不会启动 View Transition。
   - 条件分支里 `<ViewTransition>` 外面还套了 `<div>`。enter/exit 只在边界位于被切换子树的最前面时触发；`<div><ViewTransition>` 会让 enter/exit 失效。
   - `default="none"` 且只给了 `enter` / `exit`。“切换内容”是 update，没有 `update` class，等于关闭了 update 动画；即使加上 `startTransition`，update 也不会用 enter/exit 的 class。
   - 补充：如果浏览器没有 `document.startViewTransition`，React 会降级为普通提交，也不会出现动画。测试环境 jsdom 就属于这种情况。
2. 修复要点：
   - 两个更新都包进 `startTransition`；
   - 条件分支直接返回 `<ViewTransition>`，不要在外面套 `<div>`；
   - 显式提供 `update` class，并保留 `enter` / `exit`；
   - 需要方向时用 `addTransitionType`。

```tsx
import { addTransitionType, startTransition, ViewTransition, useState } from 'react'

function Panel() {
  const [tab, setTab] = useState<'a' | 'b'>('a')
  const [show, setShow] = useState(true)

  function switchTab() {
    startTransition(() => {
      addTransitionType('forward')
      setTab((current) => (current === 'a' ? 'b' : 'a'))
    })
  }

  function toggle() {
    startTransition(() => {
      addTransitionType(show ? 'hide' : 'show')
      setShow((current) => !current)
    })
  }

  return (
    <section>
      <button onClick={switchTab}>切换内容</button>
      <button onClick={toggle}>切换显示</button>

      {show && (
        <ViewTransition
          name="panel"
          default="none"
          enter="panel-in"
          exit="panel-out"
          update="panel-update"
        >
          <article>{tab === 'a' ? 'A 面板' : 'B 面板'}</article>
        </ViewTransition>
      )}
    </section>
  )
}
```

`name="panel"` 只在需要共享元素时保留；如果这里只是普通 enter/exit/update，可以删掉 name，让 React 自动生成唯一 name。

#### B. 类型、name 与 class

1. **enter**：边界在 Transition 中被插入；**exit**：边界在 Transition 中被删除；**update**：边界内部 DOM 变化，或边界自身因相邻兄弟变化而改变尺寸/位置；**share**：同一 Transition 中，一个带 name 的边界在卸载子树里、另一个同 name 边界在挂载子树里，两者形成共享元素过渡。share **优先于** enter/exit。
2. 普通场景不应该随手写 `name`：React 会自动生成唯一 name，避免不同位置的边界意外匹配成 share；手写 name 增加冲突和意外动画风险。只有**共享元素过渡**才需要显式 name，并且要在整个应用同时挂载的范围内唯一（例如 `item-${id}`）。同一个 name 同时挂载两份会报 “There are two `<ViewTransition name=%s>` components with the same name mounted at the same time”，View Transition 会出错。
3. class prop 的值可以是：`"auto"`（浏览器默认）、`"none"`（关闭）、class 字符串，或对象 `{ [transitionType]: value, default: value }`。`default="none"` 会关闭未显式列出的类型。示例：

```tsx
<ViewTransition
  default="none"
  enter={{ next: 'from-right', previous: 'from-left', default: 'fade' }}
  exit={{ next: 'to-left', previous: 'to-right', default: 'fade' }}
  update="cross-fade"
>
  <Page />
</ViewTransition>
```

`addTransitionType('next')` 必须在 `startTransition` 的作用域内、state 更新之前调用：

```tsx
startTransition(() => {
  addTransitionType('next')
  setIndex((i) => i + 1)
})
```

#### C. 生命周期、Suspense / Activity 与浏览器降级

1. React 在提交阶段准备 `view-transition-name`，调用 `document.startViewTransition({ update, types })`；在 `update` 回调里执行 DOM mutation、`useInsertionEffect`、等待字体、执行 layout effect/ref、等待导航、测量布局。`ready` 之后恢复 `view-transition-name`，再调用 `onEnter` / `onExit` / `onUpdate` / `onShare`；`finished` 之后才执行普通 `useEffect`。业务代码不应该自己调用 `document.startViewTransition`：React 会自己协调多个过渡、合并排队更新、与 Suspense/Activity/导航配合；手写会打断 React 正在进行的过渡。
2. `<ViewTransition>` 包在 `<Suspense>` **外面**时，fallback → 内容通常算 **update**（同一个边界内从 A 换到 B）；包在 fallback 或内容内部时，边界的挂载/卸载更可能算 **enter/exit**。React 会在 Suspense reveal 时最多等待约 **500ms** 的字体和可见图片，避免内容在动画中途闪现。
3. `<Activity mode="hidden">` 在 Transition 中变 visible → 内部 `<ViewTransition>` 触发 **enter**；visible → hidden 触发 **exit**。隐藏期间通过 FragmentInstance 添加的事件监听器不会生效；恢复可见时 React 会自动补上。隐藏期间 Activity 的状态保留，Effect 被销毁。
4. 浏览器没有 `document.startViewTransition` 时，React 19.3.1 会捕获调用异常并继续提交 DOM，更新照常发生，只是没有动画（本机运行时验证）。`prefers-reduced-motion` 不会被 React 自动处理，需要作者用 `@media (prefers-reduced-motion: reduce)` 关闭或弱化动画。

#### D. 测试

jsdom 没有 `document.startViewTransition`，也不做布局和真实的 View Transition 渲染；动画时长、伪元素样式、像素结果都不稳定或根本不存在。可以稳定断言：切换后的 DOM 内容；React 是否调用 `document.startViewTransition`、调用的 `types`；过渡期间元素内联样式上的 `view-transition-name` / `view-transition-class`；在受控 mock 下 `onEnter` 等事件是否被调用（如果模拟了 ready/finished）。

mock 至少需要：一个接收 `{ update, types }` 的函数；记录参数并执行 `update()` 让 React 提交 DOM；返回带 `updateCallbackDone`、`ready`、`finished`、`skipTransition` 的对象（promise 可立即 resolve）；另外补上 React 会访问的 `document.fonts` 和 `document.documentElement.getAnimations`。测试不要依赖动画完成回调的时序或实际 CSS。

### 评分点（共 3 分）

- 1.25 分：A 中正确区分 update 与 enter/exit；指出同步更新、包裹 div、`default="none"` 无 update class 三个原因（浏览器无 API 作为补充亦可）；给出可工作的修复代码（startTransition + 显式 update + 去掉包裹 div）。
- 0.75 分：B 中正确定义四种触发类型、share 优先级、name 唯一性与使用场景；正确列出 class prop 的值并写出按 transition type 映射的代码；说明 `addTransitionType` 的位置。
- 0.75 分：C 中描述 React 内部调用/lifecycle、不手写 `startViewTransition` 的理由；说明 Suspense 内外差异与 500ms 等待；说明 Activity 的 enter/exit 与监听器行为；说明浏览器降级与 reduced-motion。
- 0.25 分：D 中说清 jsdom 限制、可断言内容与 mock 最小结构。

### 简短解释

ViewTransition 不是“包上就动”：它要 Transition 语义、正确的位置和匹配的 class。enter/exit 看边界生命周期，update 看边界内部变化；浏览器不支持时 React 只保证提交，不保证动画。

## 第 2 题（2.5 分｜Fragment ref 与 FragmentInstance）

### 参考答案

#### A. 去掉包裹节点

1. 关键改法：

```tsx
import { Fragment, useRef } from 'react'
import type { FragmentInstance } from 'react'

function Toolbar() {
  const ref = useRef<FragmentInstance | null>(null)

  return (
    <Fragment ref={ref}>
      <button>保存</button>
      <div className="primary">
        <button>发布</button>
      </div>
      <button>取消</button>
    </Fragment>
  )
}
```

`ref.current` 的类型是 `FragmentInstance`（由 react-dom 增强）。不能用 `<>...</>` 简写，因为简写不支持 `ref`；必须显式 `import { Fragment }`。

2. `focus()` 从 Fragment 的所有嵌套子节点里深度优先找第一个可聚焦元素，本例是“保存”；`focusLast()` 反向深度优先，本例是“取消”；`blur()` 只在当前 `document.activeElement` 位于 Fragment 内时清除焦点，否则什么也不做。它们搜索的是**所有嵌套节点**，不是第一级。
3. `addEventListener('click', handler)` 会加到**第一级 DOM 子节点**：button 保存、div.primary、button 取消。点击“发布”时，事件从按钮冒泡到 div.primary 上的原生监听器，因此 handler 会触发（`event.target` 是发布按钮，`currentTarget` 是 div.primary）。`getClientRects()` 返回这些第一级子节点的矩形数组；jsdom 没有布局，通常返回空数组，不能断言长度或尺寸。
4. Effect 骨架：

```tsx
useEffect(() => {
  const instance = ref.current
  if (!instance) return

  const observer = new IntersectionObserver((entries) => {
    // ...
  })
  instance.observeUsing(observer)
  return () => {
    instance.unobserveUsing(observer)
    observer.disconnect()
  }
}, [])
```

`observeUsing` / `unobserveUsing` 只观察第一级 DOM 子节点；不会递归观察嵌套元素。

#### B. 能力与边界

1. 真实方法/能力包括：`focus`、`focusLast`、`blur`（深度优先）；`addEventListener`、`removeEventListener`、`dispatchEvent`（第一级 DOM 子节点）；`observeUsing`、`unobserveUsing`（第一级）；`getClientRects`、`getRootNode`、`scrollIntoView`（第一级/父根）；运行时还存在 `compareDocumentPosition`。`getRootNode` 返回 Document/ShadowRoot，或在无父 DOM 时返回 FragmentInstance 自身。
2. 判断：
   - **错误。** `FragmentInstance` 不是 Element，没有 `style`、`className` 或完整的 DOM 查询能力；它是受限制的组句柄。
   - **错误。** `focusLast()` 找的是最后一个**可聚焦**节点，会跳过不可聚焦的普通 DOM 节点。
   - **错误。** FragmentInstance 的 `scrollIntoView` 只接受布尔 `alignToTop`；传 options 对象会抛错，这一点与 Element.scrollIntoView 不同。
   - **错误。** 隐藏的 `<Activity>` 中监听器不会立即生效；Activity 恢复 visible 时 React 才会补上。
   - **错误。** react-dom 19.3.1 运行时确实有 `compareDocumentPosition`，但本机 `@types/react-dom@19.3.0` 的 `FragmentInstance` 接口尚未声明它；说“类型和运行时都完整可用”不准确。
3. 适合场景：没有共同父 DOM 的兄弟组需要统一聚焦/失焦、统一原生事件、统一 observer、统一测量/滚动；或者第三方组件不转发 ref、不能改内部结构。若只是需要一个稳定的 DOM 容器且布局允许，普通 wrapper 更简单；`display: contents` 的 wrapper 仍是 DOM 节点，可能影响可访问性树、表单布局或第三方 CSS，不能无脑替代。Fragment ref 不能替代 `style`、`className`、`querySelector`、完整 Element 事件/属性操作；需要这些时仍要真实 DOM 或重构组件。

### 评分点（共 2.5 分）

- 1.25 分：A 中正确用 `<Fragment ref>` 替换包裹 div，写出 `FragmentInstance` 类型；正确说明 focus/focusLast/blur 的深度优先与目标；正确说明 addEventListener/getClientRects 的第一级范围及冒泡；给出 observeUsing/unobserveUsing 的 Effect + cleanup。
- 1.25 分：B 中列出至少六个真实方法并区分范围；正确判断五个说法（FragmentInstance 非 Element、focusLast 只找可聚焦、scrollIntoView 布尔参数、Activity 隐藏监听器、compareDocumentPosition 类型缺口）；说明适用场景与不能替代的 DOM 能力。

### 简短解释

Fragment ref 的价值是“不改变 DOM 结构也能对一组兄弟节点施加行为”。记住两条范围规则：事件/observer/几何看第一级宿主子节点，焦点看整棵嵌套树。

## 第 3 题（2.5 分｜Hydration mismatch 的定位与修复）

### 参考答案

#### A. 读 diff

1. `+` 是客户端首次 render 的内容，`-` 是服务端 HTML 的内容；最可能出问题的是 `TicketBadge`，不一致的是 `<span data-testid="ticket">` 的文本。
2. 最可能的错误实现是：

```tsx
function TicketBadge() {
  const [ticket] = useState(() => Math.random().toString(36).slice(2, 8))
  return <span data-testid="ticket">{ticket}</span>
}
```

`renderToString` 在服务端执行一次 `Math.random()`，`hydrateRoot` 在客户端又执行一次初始化，两次结果不同；所以 `+` 与 `-` 必然不同。
3. 用 `useId()`：

```tsx
import { useId } from 'react'

function TicketBadge() {
  const ticket = useId()
  return <span data-testid="ticket">{ticket}</span>
}
```

`useId` 保证同一次服务端渲染与 hydration 生成一致的值，适合 DOM id、`htmlFor` 关联等。它**不适合**生成业务订单号/数据库 id：它的值不保证跨请求稳定、不是随机安全的，也不应该作为列表 key 或持久标识。业务 id 应由服务端生成并作为 prop/数据快照传给客户端。
4. 生产环境只有 minified #418，需要从 `onRecoverableError` 收集 `error`、`errorInfo.componentStack` 和可能的 `error.cause`：

```tsx
hydrateRoot(container, <App />, {
  onRecoverableError(error, errorInfo) {
    reportToMonitoring({
      type: 'hydration-recoverable',
      error,
      componentStack: errorInfo.componentStack,
      cause: (error as Error & { cause?: unknown }).cause,
    })
  },
})
```

同时应配置 `onCaughtError` / `onUncaughtError`，覆盖 Error Boundary 捕获和未捕获错误。

#### B. 原因与修法

1. 原因：
   - **B1**：`<p>` 里不能放 `<div>`。`renderToString` 可能原样输出 `<p><div>...</div></p>`，但浏览器解析时会把 `div` 移出 `p`，hydrate 时服务端字符串对应的真实 DOM 与客户端树不一致。`renderToString` 不报错不代表浏览器解析后结构仍合法。
   - **B2**：`new Date().toLocaleTimeString()` 在服务端和客户端各自的时刻/时区/locale 执行，首次 render 文本可能不同。
   - **B3**：`window.innerWidth` 在服务端不存在（可能直接抛错）；如果有分支回退，服务端和客户端首屏宽度也可能不同。`useState` 初始化器在服务端和客户端都会执行。
   - **B4**：`Math.random()` 同上，两次初始化不同。
2. 修法：
   - **B1**：外层改成 `<div>`，或把内层 `<div>` 改成 `<span>`，保证浏览器解析后的结构稳定：

```tsx
<div>
  <strong>限时优惠</strong>
  <div>立减 20 元</div>
</div>
```

   - **B2**：有三种层级：
     - 把服务端时间作为 prop/快照传下来，客户端首屏用同一个值；挂载后再更新。

#### C. 工具与取舍

1. `onCaughtError` 在 Error Boundary 捕获错误时调用；`onUncaughtError` 在错误没有被 Boundary 捕获时调用；`onRecoverableError` 在 React 自动恢复（例如 hydration mismatch 后客户端重新渲染）时调用。hydration mismatch 通常走 `onRecoverableError`。恢复后页面可能被整棵子树客户端重渲染：用户可能看到内容闪一下、表单光标/滚动位置丢失、动画起点重置；控制台/监控仍应记录并修复。
2. `browser()` 用法：

```tsx
import { Suspense, use } from 'react'
import { browser } from 'react-dom'

function TimeZone() {
  use(browser())
  return <p>{Intl.DateTimeFormat().resolvedOptions().timeZone}</p>
}

<Suspense fallback={<p>时区加载中…</p>}>
  <TimeZone />
</Suspense>
```

服务端渲染时 `use(browser())` 会在最近的 Suspense 边界挂起，HTML 里是 fallback；客户端 hydration 时不挂起，直接渲染真实内容。与“Effect 后显示”的区别：Effect 方案服务端和客户端首屏都渲染占位，hydration 后再更新，多一次客户端 render；`browser()` 把组件完全排除出服务端渲染，语义更明确，但必须有 Suspense 边界，并且 SSR 输出只有 fallback。
3. 不能只看字符串：浏览器解析 HTML 时会修正非法嵌套（如 `<p><div>`、表格结构），所以“字符串看起来合法”或“renderToString 没报错”不等于 hydration 时的 DOM 结构一致。排查顺序：开发构建读完整 `+/-` diff 与组件栈 → 定位最近组件 → 对照服务端 HTML 和客户端首次 render → 检查非法嵌套/浏览器 API/时间随机/数据快照/扩展注入 → 修复根因 → 用真实 `renderToString` + `hydrateRoot` + `onRecoverableError` 回归。生产环境用错误回调 + componentStack 监控，不要靠 `suppressHydrationWarning` 掩盖。

### 简短解释

Hydration 的第一原则是“服务端 HTML 与客户端首次 render 一致”。React 19 的 `+/-` diff 只是把这个不一致指给你看；真正的修复在数据快照、HTML 结构、浏览器 API 的使用时机，以及稳定的 `useId`。`suppressHydrationWarning` 是创可贴，不是结构修复。
