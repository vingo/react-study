## 复习 1（0.5 分｜Effect 的职责边界）

### 参考答案

三个 Effect 都不该原样保留：前两个是“把 render 能算出的值搬进 state”，第三个把用户事件误当成了外部同步。逐条看：

1. **标题不该用 state + Effect。** `title` 完全由 `roomId` 派生，在 render 中直接计算即可：
   ```tsx
   const title = `房间：${roomId}`
   ```
   用 Effect 再 `setTitle` 会多一轮渲染，还可能让界面短暂显示旧标题或空字符串。

2. **总价也不该用 state + Effect。** `total` 完全由 `items` 派生，在 render 中计算：
   ```tsx
   const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0)
   ```
   只有计算确实昂贵时才考虑 `useMemo`。把派生值存进 state 会产生“两套真相”，并且首帧可能显示 0。

3. **下单 POST 不属于 Effect。** 这个 Effect 会在组件首次挂载时执行，也会在 `roomId` 每次变化时执行，而不是在用户点击“下单”时执行。也就是说，打开页面或切换房间就会悄悄创建订单；开发环境 StrictMode 还会额外执行一次 setup，可能重复提交。下单是明确的用户事件，应放在按钮的 `onClick` / 表单 action / mutation 中。补上 `onClick` 后，这个 Effect 应删除。

4. **真正适合 Effect 的是“与外部系统同步”。** 例如 `roomId` 变化时建立 WebSocket、组件卸载或房间切换时关闭旧连接：
   ```tsx
   useEffect(() => {
     const ws = new WebSocket(`/ws/${roomId}`)
     return () => ws.close()
   }, [roomId])
   ```
   其他例子：订阅 DOM 事件、同步第三方地图/编辑器实例、连接/断开浏览器 API。判断标准是“这个副作用是否随某个响应式值同步外部系统”，而不是“有事情发生就写 Effect”。

### 评分点（共 0.5 分）

- 0.2 分：指出 `title` 和 `total` 是派生值，应在 render 中计算，不需要 state + Effect；能说出多一轮渲染或短暂错误值。
- 0.15 分：指出 POST 会在挂载和 `roomId` 变化时触发，而不是点击时；应放到事件处理函数/action；能提到 StrictMode 可能重复执行。
- 0.15 分：给出一个真正需要 Effect 的外部系统同步例子，并包含 cleanup。

### 简短解释

Effect 的职责是“让外部系统和当前 props/state 保持同步”，不是“把 render 能算出来的值搬进 state”，也不是“承接用户事件”。TanStack Query 之所以能替代大量取数 Effect，正是因为它把缓存、重取、取消和错误状态这些外部同步工作集中管理了。

## 复习 2（0.5 分｜Error Boundary 与请求竞态）

### 参考答案

1. 最终显示 **alice**。从 alice 切到 bob 后，两个请求都还在进行；bob 先返回，`setUser(bob)`；alice 后返回，又执行 `setUser(alice)`，把新数据覆盖成旧数据。没有 cleanup 或请求身份校验，后到的旧响应总会赢。
   如果 alice 后到的是失败，而 bob 已经成功：`.catch` 会 `setError(aliceError)`，下一次 render 执行 `if (error) throw error`，Error Boundary 显示“加载失败”，把 bob 已经成功的内容也替换掉。旧请求的错误同样会污染新请求的状态。

2. 能捕获的是 **render 期间抛出的错误**。所以 `if (error) throw error` 会被 Error Boundary 捕获。
   直接在 `.catch(err => { throw err })` 回调里抛不行：这是异步回调，不在 React 的 render/lifecycle 调用栈里，Error Boundary 捕不到，通常变成未处理的 Promise rejection。fetch 的 rejection 本身也不会被 Error Boundary 捕获；必须把它转成 state 后在 render 中抛出，或者通过 `use()` 在 render 中读取（由 Suspense/Error Boundary 接管），或者在 UI 中直接处理错误。
   Error Boundary 能捕获子组件在渲染、生命周期、构造函数中抛出的错误；不能捕获事件处理函数、`setTimeout` / Promise 回调、服务端渲染，以及边界自身抛出的错误。

3. cleanup 修复：
   ```tsx
   useEffect(() => {
     let ignore = false

     fetch(`/api/users/${id}`)
       .then(r => r.json())
       .then(data => {
         if (!ignore) setUser(data)
       })
       .catch(err => {
         if (!ignore) setError(err)
       })

     return () => {
       ignore = true
     }
   }, [id])
   ```
   或者用 `AbortController` 把 `signal` 传给 fetch，并在 cleanup 中 `abort()`；catch 时忽略 `AbortError`。`id` 变化时还要清掉旧的 `error` / `user`，避免把上一位用户的错误带过来。

   TanStack Query 的对应机制：
   - **不同 id 使用不同 queryKey**，缓存条目天然隔离，alice 和 bob 不会写进同一个槽位，从根上避免“旧用户覆盖新用户”。
   - 同一 key 的并发/在途请求由 Query 的取消与重取机制协调；`queryFn` 会收到 `AbortSignal`，可以真正中止 fetch。mutation 场景则用 `cancelQueries` 防止在途 refetch 覆盖乐观更新。
   - 错误是 query 的状态（`isError` / `error`），不会从异步回调里直接抛给 React；重试策略（默认 3 次、指数退避）和错误 UI 都由查询状态驱动。

### 评分点（共 0.5 分）

- 0.2 分：正确预测 alice 覆盖 bob；指出旧请求后到的错误也会让边界显示失败、盖掉 bob 的成功内容。
- 0.15 分：说明 Error Boundary 捕获 render 抛错，但捕获不到 `.catch` 等异步回调；fetch rejection 需要先转成 state 或用 `use()`。
- 0.15 分：给出 ignore 标记或 AbortController 的 cleanup；能说出 Query 用不同 queryKey 隔离、AbortSignal/取消机制、错误状态化。

### 简短解释

Error Boundary 是“渲染期错误”的边界，不是“所有异步错误”的边界；请求竞态也不是靠“最后 setState 的人赢”来解决，而是要让旧请求的结果失效，或者让不同请求拥有不同的缓存身份。

## 第 1 题（2.5 分｜queryKey 的身份与缺失参数）

### 参考答案

1. **`open` 和 `done` 是两个不同的 queryKey。**
   `['todos', { status: 'open' }]` 与 `['todos', { status: 'done' }]` 哈希结果不同，所以切换筛选会创建/使用另一个缓存条目。`done` 没有缓存时会执行 `fetchTodos('done')`：此时 `data` 为 `undefined`，`status` 为 `pending`，`isPending` 为 `true`，`isFetching` 为 `true`；拿到数据后 `isPending` 变 `false`、`isFetching` 变 `false`。
   如果两种筛选都已经访问过且仍在 `staleTime` 内，来回切换会直接命中各自的新鲜缓存，不发请求；如果其中一份已经过期，会先显示该份缓存数据，同时在后台重取；如果已经被 `gcTime` 回收，则会回到首次加载状态。

2. 逐对判断：
   - `['todos', { status, page }]` 与 `['todos', { page, status }]`：**相同**。query key 的哈希会稳定排序普通对象的键，对象键顺序不影响身份。
   - `['todos', status, page]` 与 `['todos', page, status]`：**不同**。数组元素顺序有意义，`['todos', 'open', 1]` 和 `['todos', 1, 'open']` 不是同一个 key。
   - `['todos', { status: undefined }]` 与 `['todos', {}]`：**相同**。对象里的 `undefined` 属性在哈希/JSON 序列化时被丢弃，`{ status: undefined }` 等价于 `{}`。
   - `['todos', undefined]` 与 `['todos']`：**不同**。数组里的 `undefined` 在 JSON 序列化时变成 `null`，而且数组长度也不同，因此哈希不同。
   结论：对象键顺序不重要，数组顺序和数组长度重要；对象里的 `undefined` 会被忽略，数组里的 `undefined` 不会。

3. **`Profile` 从 alice 切到 bob 后仍显示 alice 的数据。**
   两个用户共用 `['profile']` 这一个 key。alice 的数据在 60 秒内是 fresh 的；`userId` prop 变成 bob 时，queryKey 没变，Query 认为这是同一个缓存条目，且数据新鲜，于是直接返回 alice 的缓存，不会因为 `queryFn` 闭包换了就自动重取。界面显示 alice。若此时另一个组件同时渲染 bob 的 Profile，两者会争用同一个缓存槽。
   60 秒后查询变 stale；此后的窗口聚焦、网络重连、重新挂载或手动失效会触发重取，才会用当前 `queryFn` 重新请求；结果仍写回 `['profile']`，于是 bob 的数据覆盖 alice。再切回 alice 时，可能又先看到 bob 的缓存。只靠 `staleTime` 只能决定“什么时候重取”，不能把两个用户的数据分开。
   正确写法是把 `queryFn` 依赖的所有变量都放进 key：
   ```tsx
   useQuery({
     queryKey: ['profile', userId],
     queryFn: () => fetchProfile(userId),
     staleTime: 60_000,
   })
   ```
   这样 alice 和 bob 各有一个缓存条目，切换时会命中各自的数据或各自加载。
   只把 `staleTime` 改成 `0` 不能真正修复：queryKey 仍然是同一个共享槽位，`userId` 变化本身不会创建新缓存条目，也不会仅因为 `queryFn` 闭包换了就立刻重取（要等挂载、聚焦、重连或手动失效等 stale 触发）。切换瞬间仍会显示上一位用户的缓存；等某次重取发生时，bob 的结果又写回 alice 用过的槽位，之后切回 alice 可能看到 bob 的数据。两个用户同时挂载时还会互相覆盖。
   若希望在切换用户或翻页时先保留上一份数据、同时提示“正在更新”，使用：
   ```tsx
   import { keepPreviousData } from '@tanstack/react-query'

   placeholderData: keepPreviousData
   ```
   新 key 还没有数据时，会先用上一个 query 的数据作为 placeholder，并令 `isPlaceholderData` 为 `true`；此时 `status` 是 `success`（不是 `pending`），`isPending` 为 `false`，真正的请求仍在后台进行（`isFetching` 为 `true`）。真实数据到达后 `isPlaceholderData` 变回 `false`。它只是过渡显示，不能替代正确的 key；展示上一位用户的隐私数据可能不合适，这种场景更适合明确的加载 UI，而不是 `keepPreviousData`。

4. 会失效。`invalidateQueries` 的 `queryKey` 是**前缀匹配**：`['todos']` 会匹配 `['todos', { status: 'done' }]`、`['todos', todo.id]` 等所有以 `todos` 开头的 key。匹配到的查询被标记为 stale；其中正在被渲染（active）的查询会后台重取，inactive 的会留在缓存里，等下次挂载时再取。失效会把 stale 状态凌驾于 `staleTime` 之上（`staleTime: 'static'` 是例外）。
   加 `exact: true` 后只匹配完全等于 `['todos']` 的 key，不会命中 `['todos', { status: 'done' }]`。

### 评分点（共 2.5 分）

- 0.5 分：指出 open/done 是不同 key，会发请求；说清首次加载的 `data` / `isPending` / `isFetching`，以及两份缓存来回切换的行为。
- 0.5 分：四组身份判断全部正确，并说明对象键顺序、数组顺序、对象/数组中的 `undefined` 的差异。
- 0.75 分：正确预测 Profile 显示 alice；解释同 key + fresh 缓存导致不重取；给出 `['profile', userId]`；说明 `staleTime: 0` 不能隔离缓存、仍会共用槽位。
- 0.25 分：提到 `placeholderData: keepPreviousData` 与 `isPlaceholderData`，并说清“先显示上一份数据、后台继续取新数据”的行为。
- 0.5 分：说明 `invalidateQueries({ queryKey: ['todos'] })` 是前缀匹配、会失效过滤列表和详情；`exact: true` 只匹配精确 key。

### 简短解释

queryKey 是缓存的身份，不是“给请求起的名字”。queryFn 里用到的每个会变化的变量都必须进入 key；漏掉一个变量，就等于让不同数据共享同一个缓存槽。`staleTime` 管“数据新不新鲜”，`gcTime` 管“没用的数据还留多久”，两者都不能替代正确的 key。

## 第 2 题（3 分｜staleTime、gcTime 与加载标志）

### 参考答案

1. **`t = 12s`：直接命中缓存，不发请求。**
   数据在 `t = 1s` 写入，到 `t = 12s` 才 11 秒，小于 `staleTime: 30_000`，所以是 fresh。`gcTime` 的 5 秒是从 `t = 10s` 卸载、查询变为 inactive 时开始计时的，本应在 `t = 15s` 回收；`t = 12s` 重新挂载会取消这次回收。屏幕立即显示列表，`fetchTodos` 不执行，`isPending = false`，`isFetching = false`。这里 `staleTime` 决定“不用重取”，`gcTime` 决定“缓存还在”。

2. **`t = 26s`：缓存已经被回收，重新加载。**
   组件在 `t = 20s` 卸载，查询再次 inactive，`gcTime` 5 秒后在 `t = 25s` 把缓存删除。因此 `t = 26s` 挂载时没有缓存：`data` 为 `undefined`，`isPending = true`，`isFetching = true`，显示“首次加载…”，`fetchTodos` 会执行，并在 `t = 27s` 成功。
   关键点：`t = 26s` 距离上次成功（`t = 1s`）只有 25 秒，数据按 `staleTime: 30_000` 本来还算是 fresh；但 fresh 只表示“不需要因过期而重取”，并不阻止 `gcTime` 删除长期无人使用的缓存。`gcTime` 只看查询 inactive 了多久，与数据是否 stale 无关。

3. **改成 `staleTime: 5_000`、`gcTime: 30_000`：**
   - `t = 12s`：缓存还在（只 inactive 了 2 秒，远小于 30 秒），但数据已经 11 秒，超过 5 秒，所以是 stale。Query 会**立即返回缓存数据**，同时后台重取。屏幕显示列表，`isPending = false`，`isFetching = true`；不会出现“首次加载…”。重取成功后列表更新，`isFetching` 变 `false`。
   - `t = 26s`：`t = 20s` 卸载后只过了 6 秒，仍小于 `gcTime: 30_000`，缓存还在；数据已 stale，所以同样立即显示旧数据并在后台重取，`isPending = false`，`isFetching = true`。也不会出现“首次加载…”。
   结论：有缓存但 stale 时，界面是“旧数据 + 后台刷新”；没有缓存时才是“首次加载”。

4. **`staleTime: Infinity`、`gcTime: 5_000` 时，`t = 26s` 仍会发请求。**
   `t = 12s` 时数据是 fresh（Infinity），不会重取；但 `t = 20s` 卸载后，`gcTime` 仍在 `t = 25s` 把缓存删掉。`t = 26s` 没有缓存，Query 必须重新请求，`staleTime: Infinity` 也救不回来。
   这说明：`staleTime` 控制“已有数据在多久内算新鲜、哪些时机会因过期而重取”；`gcTime` 控制“inactive 的查询在缓存里保留多久”。`staleTime` 再长也不能阻止 `gcTime` 回收；`gcTime` 再长也不会让 stale 数据自动变 fresh。默认值是 `staleTime: 0`（一拿到数据就 stale）和 `gcTime: 5 * 60 * 1000`（5 分钟）。

5. **`t = 60s` 切回标签页：触发后台重取。**
   最后一次成功是 `t = 27s`，`staleTime: 30_000` 到 `t = 57s` 变 stale。窗口聚焦时，stale 查询默认会 `refetchOnWindowFocus`，于是后台重取；新数据到达前，列表仍显示旧数据。此时 `isPending = false`（有 `data`，`status` 是 `success`），`isFetching = true`（有请求在进行），界面显示“后台刷新中…”。
   首次骨架屏应使用 `isPending`（没有数据，`status === 'pending'`）或 `isLoading`（`isPending && isFetching`，只在第一次请求进行时为 true）。“后台刷新中”应使用 `isFetching`（任何请求进行中都为 true，包括后台重取、轮询、翻页）。
   如果组件在 `isFetching` 时直接 `return <p>首次加载…</p>`，那么每次后台刷新都会把已经显示的列表整个替换成加载页，造成闪烁、丢失滚动位置和输入焦点。`isFetching` 适合做顶部进度条、半透明遮罩或“正在更新”小提示，不适合做硬加载分支。
   注意：`isPending` 在查询被 `enabled: false` 禁用时也可能为 true（此时并没有在请求），所以带条件的查询更稳妥的是用 `isLoading` 判断“第一次请求正在进行”。

   补充：stale 查询会在新观察者挂载、窗口重新聚焦、网络重连时自动后台重取；fresh 查询不会因为这些时机重取。`invalidateQueries` 会无视 `staleTime` 把匹配查询标记为 stale 并重取 active 查询（`staleTime: 'static'` 除外）。

### 评分点（共 3 分）

- 0.5 分：`t = 12s` 命中 fresh 缓存，不发请求，`isPending` / `isFetching` 均为 false；说明 `gcTime` 计时从卸载开始且重挂载会取消回收。
- 0.75 分：`t = 26s` 缓存已在 `t = 25s` 被 GC，显示首次加载，两个标志为 true，会请求；明确指出“数据本来还 fresh，但 fresh 不阻止 GC”。
- 1 分：换成 `staleTime: 5_000` / `gcTime: 30_000` 后，`t = 12s` 和 `t = 26s` 都是“立即显示旧数据 + 后台重取”，`isPending = false`、`isFetching = true`，不会出现首次加载；能说明有缓存但 stale 与无缓存的区别。
- 0.5 分：`staleTime: Infinity` + `gcTime: 5_000` 在 `t = 26s` 仍请求，说明两者独立、GC 不受 freshness 阻止。
- 0.25 分：聚焦时因 stale 触发后台重取；`isPending` / `isFetching` / `isLoading` 的语义与使用场景正确。

### 简短解释

`staleTime` 是“数据保鲜期”，`gcTime` 是“缓存保质期”。数据可以一边“还没过期”一边因为没人用而被回收；也可以“已经过期”但仍在缓存里，先展示旧值再后台刷新。加载 UI 要区分“没有数据”和“有数据但正在更新”，这就是 `isPending` 与 `isFetching` 的分工。

## 第 3 题（2.5 分｜mutation 的失效与乐观更新）

### 参考答案

1. **缺少 `await queryClient.cancelQueries({ queryKey: ['todos'] })`，并且它必须放在读取快照之前。**
   正确顺序：
   ```tsx
   onMutate: async (updated) => {
     await queryClient.cancelQueries({ queryKey: ['todos'] })

     const previous = queryClient.getQueryData<Todo[]>(['todos'])
     queryClient.setQueryData<Todo[]>(['todos'], old =>
       old?.map(todo => (todo.id === updated.id ? updated : todo)),
     )

     return { previous }
   }
   ```
   原因：如果后台 refetch 已经在途，它可能在乐观更新写入之后才返回，并把服务端的旧结果写回缓存，用户的乐观更新就会“闪一下又被打回原形”。`cancelQueries` 会取消匹配查询的在途取数；默认 `revert: true` 会把查询数据恢复到这次在途 fetch 开始之前的状态。因此要先 `await` 它完成，再读取 `previous` 快照，最后写入乐观值：这样快照和乐观写入都发生在取消/revert 之后，不会被在途结果插入的竞态窗口弄脏。它返回的 Promise 会在所有取消操作完成后 resolve；`queryFn` 若消费了 `AbortSignal`，网络请求也会真正中止，否则只是不再采用其结果。
   注意 `invalidateQueries` / `cancelQueries` 的 queryKey 是前缀匹配，`['todos']` 会覆盖列表和详情等所有以 `todos` 开头的查询。

2. 服务端返回 500 时的顺序：
   - `onMutate`（在 `mutationFn` 之前；补上第 1 问的 `cancelQueries` 后）：取消在途取数、拍快照、写入乐观更新。界面先显示“已完成/未完成”的乐观结果，mutation 的 `isPending` 为 `true`，按钮显示“保存中…”。
   - `mutationFn`：发出请求，最终 reject。
   - `onError(error, updated, onMutateResult)`：用 `onMutateResult.previous` 把 `['todos']` 写回旧值，界面回滚到点击前。
   - `onSettled(data, error, variables, onMutateResult)`：无论成功失败都会执行；这里调用 `invalidateQueries`，把匹配查询标记 stale 并对 active 查询重新取数，用服务端真实状态做最终对账。如果这个 Promise 被返回，mutation 会等它完成才 settle。
   回滚数据来自 `onMutate` 的返回值（`onMutateResult.previous`）。如果 `onSettled` 触发的重新请求也失败，缓存会停留在刚刚回滚的旧数据上，同时查询带上错误状态（`isError`，通常还有 `isRefetchError`，`error` 可用）；界面应显示“保存失败/刷新失败”的提示，而不是乐观结果。如果服务端实际上已经成功、只是响应丢失，之后某次重取成功会纠正本地状态。

3. **必须用 `onSettled`，因为它成功和失败都会执行。**
   只在 `onSuccess` 失效会漏掉失败路径：请求失败不代表服务端一定没改动（例如服务端已提交但响应超时/网络中断），而回滚只是客户端的猜测。失败后也需要重新取一次服务端状态来对账，否则可能长期停留在错误的回滚值。`onSettled` 还能统一处理成功或失败后的列表/详情刷新，避免成功和失败写两套失效逻辑。
   `onSuccess` 仍适合做“只在成功时发生”的副作用，例如跳转、清空表单、显示成功 toast；缓存失效应放在 `onSettled`。

4. 如果不 `return`，`isPending` 会在 `mutationFn` settle 后很快变 `false`，即使 `invalidateQueries` 的重新取数还在进行。“保存中…”提前消失，按钮重新可用，用户可以再次点击，可能造成重复提交；同时界面仍显示乐观值，尚未得到服务端确认。
   `return queryClient.invalidateQueries(...)` 后，`onSettled` 返回的 Promise 会被等待，mutation 会保持 `pending` 直到失效重取完成，`isPending` 在此期间一直为 `true`，按钮保持禁用，服务端结果回来后才算真正完成。官方乐观更新示例的注释就是：返回失效的 Promise，让 mutation 在 refetch 结束前保持 pending。

5. 会匹配。`invalidateQueries({ queryKey: ['todos'] })` 前缀匹配 `['todos', todo.id]`、`['todos', { status }]` 等所有以 `todos` 开头的查询；如果只想匹配某个具体的列表 key、不碰详情，给那个完整 key 加 `exact: true`：
   ```tsx
   queryClient.invalidateQueries({ queryKey: ['todos'], exact: true })
   // 或对筛选列表：queryKey: ['todos', { status: 'done' }], exact: true
   ```
   如果 mutation 改的是单条 todo，乐观更新应同时改：
   - 详情缓存 `['todos', todo.id]`；
   - 所有包含这条 todo 的列表缓存，例如 `['todos']`、`['todos', { status: 'done' }]`。
   可以用 `queryClient.setQueriesData({ queryKey: ['todos'] }, updater)` 批量更新匹配的列表/详情，但同一个 `updater` 必须能处理列表和详情两种数据形状；否则分别对 `['todos', todo.id]` 和各列表 key 调用 `setQueryData`。
   只改列表：详情页仍显示旧 todo；只改详情：列表仍显示旧内容。只更新其中一个缓存，另一个就会在切换页面时露馅。`onSettled` 里用前缀失效可以同时覆盖两者；`invalidateQueries` 默认只重取 active 查询，inactive 查询会被标记 stale，下次挂载时再取。

### 评分点（共 2.5 分）

- 0.75 分：指出缺少 `cancelQueries`，放在读取快照之前并 `await`；解释在途 refetch 会覆盖乐观更新，以及默认 `revert: true` / 快照顺序的原因。
- 0.5 分：正确描述 `onMutate` → `mutationFn` → `onError` → `onSettled` 的顺序、回滚来源 `onMutateResult.previous`，以及重取失败时缓存停留在回滚值并进入错误状态。
- 0.5 分：说明 `onSettled` 成功失败都执行，失败路径也需要对账；只写 `onSuccess` 会漏掉失败后服务端可能已变更/需要重新同步的情况。
- 0.5 分：说明不返回 invalidation Promise 会让 `isPending` 提前结束、按钮提前可用；返回后 mutation 保持 pending 直到 refetch 完成。
- 0.25 分：说明前缀匹配会命中详情/列表，`exact: true` 只匹配精确 key；单条 mutation 应同时更新/失效详情与所有相关列表缓存。

### 简短解释

乐观更新的完整闭环是：先取消可能覆盖它的在途取数，再拍快照、写乐观值；失败时用快照回滚，最后由 `onSettled` 失效并重新取服务端真相。`cancelQueries` 防“旧刷新覆盖新乐观值”，`onError` 防“失败后界面撒谎”，`onSettled` 防“成功或失败后缓存与服务器脱节”，返回失效 Promise 则让 `isPending` 如实覆盖整个对账过程。
