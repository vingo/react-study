## 复习 1（1 分｜render / commit 时序与读取 DOM）

### 参考答案

未开启 StrictMode 时，控制台顺序是：

```text
render: undefined
effect: A
render: A
effect: B
```

- 首次 render 发生在任何 DOM 提交之前，此时页面里还没有 `h1`，所以读到 `undefined`。
- 首次 commit 把 `<h1>A</h1>` 写进 DOM 后，Effect 才运行，所以读到 `A`。
- 父组件把 `text` 改成 `B` 后，第二次 render 仍发生在新的 commit 之前，DOM 还是上一次提交的 `<h1>A</h1>`，所以读到 `A`。
- 第二次 commit 写入 `B` 后，Effect 读到 `B`。

要点：render 只是调用组件函数、计算 JSX，不修改 DOM；commit 才把差异写入 DOM；Effect 在 commit 之后运行。开发环境的 StrictMode 会额外重复调用 render 和 Effect 的 setup/cleanup，但题目已说明未开启。

### 评分点（共 1 分）

- 0.5 分：四行日志的内容与顺序正确。
- 0.5 分：能说明 render 在 commit 之前、Effect 在 commit 之后；首次 render 读不到 DOM，更新 render 读到的是上一次 commit 的 DOM。

### 简短解释

“render 中读 DOM”读到的永远是上一次提交的结果，而不是本次即将渲染的内容。

## 复习 2（1 分｜Effect cleanup 与 setup 的时序）

### 参考答案

日志顺序：

```text
connect general
disconnect general
connect react
disconnect react
```

- `roomId` 从 `general` 变为 `react` 时，React 先用**旧依赖**执行 cleanup（`disconnect general`），再用**新依赖**执行 setup（`connect react`）。

- 未开启 StrictMode；若开启，首次挂载后会额外执行一轮 setup → cleanup → setup。

### 评分点（共 1 分）

- 0.6 分：四行日志顺序正确。
- 0.4 分：说明依赖变化时先 cleanup 旧值、再 setup 新值；卸载时执行最后一次 cleanup。

### 简短解释

cleanup 闭包捕获的是建立该 Effect 时的 `roomId`，所以断开的是旧连接。这个“清理旧请求”的机制也是后面处理请求竞态的基础。

## 第 1 题（2.5 分｜`use` 的调用位置与 Promise 稳定性）

### 参考答案

1. **不违反 Hooks 规则。** `use` 不是 Hook：它必须放在组件或自定义 Hook 内，但可以出现在 `if`、循环等条件结构中。`useContext` 则必须写在顶层。
   但是，`const albumsPromise = fetchAlbums(query)` 写在 `if` 外面，所以即使 `enabled` 为 `false`，它仍然会执行并发起请求。在 render 中调用 fetch、创建 Promise 属于副作用，违反组件纯度：每次 render 都可能发请求，StrictMode 或并发重试会放大这个问题。`use` 可以条件调用，不代表 Promise 的创建也可以随意放在 render 里。

2. `use` 在挂起时是通过**抛出一个特殊 thenable** 与 Suspense 集成的，try/catch 会把这个内部信号当成普通异常捕获。
   - Promise 仍 pending 时，catch 会立刻捕获 Suspense 信号，组件可能直接渲染“加载失败”，而不是让最近的 Suspense 边界显示 fallback；Suspense 无法正常等待。
   - Promise reject 时，拒绝原因也会被 catch 捕获，显示“加载失败”。
   - 开发环境可能报错：`Suspense Exception: This is not a real error!`。React 文档明确要求 `use` 不能放在 try/catch 里；等待由 Suspense 边界负责，错误由 Error Boundary 负责。

3. 两种写法都会在**每次 render 新建 Promise**：
   - `use(fetchAlbums(query))`：首次 render 挂起；Promise resolve 后 React 重试。由于这次渲染在首次挂载前就挂起了，React **不保留它的状态，会从零重新渲染**；重试时又调用 `fetchAlbums(query)`，得到一个新的 pending Promise，于是再次挂起并继续显示 fallback。这个循环可能让内容一直出不来，同时每次重试都可能发起新请求。
   - `use(fetchAlbums(query).then(r => r.json()))`：即使 `fetchAlbums` 内部做了缓存，`.then()` 也会在每次 render 返回**新的 Promise**，问题相同。
   - 开发环境常见警告：`A component was suspended by an uncached promise`。

   正确的心智模型：`use` 读取的 Promise 必须是**跨 render 稳定的同一个实例**；React 依靠这个实例判断“数据是否已经好了”。在 render 中新建 Promise，等于每次都换一个等待对象。

4. 正确做法：
   - Promise 在**渲染之外**创建：事件处理函数、路由 loader、Server Component、父组件，或模块级缓存。
   - 用按 `query` 索引的缓存复用同一个实例，例如：

```tsx
const cache = new Map<string, Promise<Album[]>>()

function fetchAlbums(query: string) {
  if (!cache.has(query)) {
    cache.set(query, getAlbums(query))
  }
  return cache.get(query)!
}

function Albums({ albumsPromise }: { albumsPromise: Promise<Album[]> }) {
  const albums = use(albumsPromise)
  // ...
}
```

   - `query` 变化时，为目标 query 取得（或重新发起）Promise，并存到 state / 作为 prop 传入；若希望旧内容继续显示，把更新 Promise 的 state 更新放进 `startTransition`（或对 query 使用 `useDeferredValue`）。需要刷新同一 query 时，先让缓存失效，再在 `startTransition` 中换入新 Promise。
   - 不要在 render 中 `.then()` 包一层；也不要直接读 `promise.status` / `promise.value` 绕过 `use`。

### 评分点（共 2.5 分）

- 0.5 分：指出 `use` 可以条件调用；同时指出 `fetchAlbums` 在 `if` 外无条件执行、请求属于 render 副作用。
- 0.5 分：说明 try/catch 会捕获 Suspense 内部信号，pending 时错误地显示“加载失败”，reject 时也被捕获；应使用 Suspense + Error Boundary，并能提到 `Suspense Exception: This is not a real error!`。
- 1 分：说明 render 中新建 Promise 会导致每次 retry 都换新 Promise、反复挂起、内容可能永远不出现；能提到挂起前未挂载的渲染状态不保留、React 从零重试；能提到 `A component was suspended by an uncached promise`；指出 `.then()` 也会返回新 Promise。只指出“会重复请求”但没解释重试循环，最多 0.5。
- 0.5 分：给出按 key 缓存的稳定 Promise、在渲染外创建/传入；query 变化时换新 Promise 并用 transition/`useDeferredValue` 保持输入和旧内容。

### 简短解释

`use` 不是“在组件里发请求”的 API，而是“读取一个已经存在、且身份稳定的异步资源”。Promise 的身份就是 Suspense 的等待键；每次 render 换键，Suspense 就只能反复重来。

## 第 2 题（2 分｜Suspense fallback 与 transition 下的更新）

### 参考答案

1. 首次挂载时 `Albums` 挂起，最近的边界是内层 `<Suspense>`，所以显示 **“专辑加载中…”**；`Header` 仍可见，外层边界不会被激活。如果 `Header` 也挂起，内层边界无法覆盖它，才会由外层显示“页面加载中…”。
   在首次挂载时用 `startTransition` **不能避免** fallback。此时还没有任何“已经显示的内容”需要保护；transition 只避免在更新时隐藏已经展示的内容。初次挂载仍然显示 fallback（新建的 Suspense 边界也会立即显示 fallback）。

2. 点击 Pink Floyd 是普通 `setState`（紧急更新）。`Albums` 因 floyd 的 Promise pending 而挂起，内层边界立即用 **“专辑加载中…”** 替换旧专辑；`Header` 保留；`isPending` 为 `false`，不会显示“切换中…”。

3. 点击 Led Zeppelin 的更新在 `startTransition` 中。该边界已经显示过内容，所以 React **保留旧 beatles 专辑**，不显示 fallback；`isPending` 为 `true`，显示“切换中…”。zeppelin 数据就绪后再切换到新专辑。原因：transition 更新挂起时，React 会等待足够数据，避免隐藏已经展示的内容。
   注意：如果 transition 中新增了一个之前从未显示过的 Suspense 边界，那个新边界仍会立即显示自己的 fallback。

4. 应把 `key` 加在 **包住 Albums 的 Suspense 边界本身**（或该边界上方的组件），例如：
   ```tsx
   <Suspense key={artistId} fallback={<p>专辑加载中…</p>}>
     <Albums artistId={artistId} />
   </Suspense>
   ```
   加在内层只会重置专辑区域；加在外层会连 Header 一起重置。不加 key：从 A 导航到 B 仍被视作同一个边界，transition 期间会继续显示 A 的旧内容，直到 B 就绪。加 key：key 变化让 React 把 B 当成不同内容，重置边界，于是显示加载 fallback，而不是继续展示 A 的旧数据。前者适合“刷新同一条目”，后者适合“切换到另一个实体/页面，旧内容会误导用户”。

### 评分点（共 2 分）

- 0.5 分：首次显示内层“专辑加载中…”，Header 保留；首次挂载的 fallback 不会因 transition 被避免。
- 0.5 分：普通更新显示 fallback，`isPending` 为 false。
- 0.5 分：transition 更新保留旧内容、`isPending` 为 true、不显示 fallback，并能解释原因。
- 0.5 分：key 放在 Suspense 边界（或上方组件）；说清加 key 会重置边界、显示 fallback，不加则保留旧内容。

### 简短解释

transition 的承诺是“不要为了新内容而把用户正在看的内容藏起来”；它不承诺初次加载不显示 fallback，也不会自动把“另一个实体”当成不同内容。后者要用 key 表达。

## 第 3 题（2.5 分｜rejected Promise、Error Boundary 与请求竞态）

### 参考答案

#### A 部分：错误边界与重试

1. 首次渲染时 `Profile` 因 `use(userPromise)` 挂起，最近的 Suspense 边界显示 **“加载中…”**。500ms 后 Promise reject，`use` 在渲染期间抛出拒绝原因，最近的 Error Boundary 捕获，显示 **“加载失败”**；Suspense fallback 被替换。
   如果没有 `Boundary`：错误会向上传播到根，React 移除出错的 UI / 交给根错误处理；开发环境显示错误覆盖层。Suspense 只负责等待，不负责捕获拒绝。

2. 点击“重试”**不会重新请求**，屏幕也不会回到“加载中…”：
   - `Boundary` 的 `hasError` 已经是 `true`，它继续渲染 fallback，不会重新渲染子组件。
   - 即使边界被重置，`userPromise` 仍是 state 中那个**已经 reject 的同一个 Promise**，`use` 会立刻再次抛出，重新进入错误状态。

   正确的重试要同时做两件事：
   - **重置边界状态**：改变 boundary 的 key、使用 `react-error-boundary` 的 `resetKeys`，或在边界内提供把 `hasError` 设回 `false` 的方法。
   - **换一个新的 Promise**：让缓存失效并重新请求（例如 `refetchUser('alice')`），把新 Promise 存入 state；若希望旧内容保留，可在 `startTransition` 中更新。新 Promise 变化也应触发边界重置。

3. `Boundary` 放在 `App` 外层时，fallback 会替换整个 App 的 UI（包括按钮等）；只包住 `Profile` 时，只有 Profile 被替换，页面其余部分保留。错误边界的粒度应按“哪里出错时适合显示什么错误 UI”来设计，不需要每个组件都包一层。
   它能捕获子组件在**渲染、生命周期、构造函数**中抛出的错误。它**不能**捕获：事件处理函数、`setTimeout` / `requestAnimationFrame` 等异步回调、服务端渲染、边界自身抛出的错误。一个例外是：由 `useTransition` 返回的 `startTransition` 内抛出的错误会被错误边界捕获。所以事件里的异步错误要在事件/action 中自行 try/catch 或转成错误 state。

#### B 部分：请求竞态与加载状态

4. 最终显示 **alice**（错误结果）。原因是没有取消或忽略旧请求：
   - 从 alice 切到 bob 后，两个请求都在继续。
   - bob 的响应先到，`setUser(bob)`。
   - alice 的响应后到，又执行 `setUser(alice)`，把新数据覆盖成旧数据。

   用 cleanup 修复（ignore 标记）：

```tsx
useEffect(() => {
  let ignore = false

  fetch(`/api/users/${id}`)
    .then(r => r.json())
    .then(data => {
      if (!ignore) setUser(data)
    })
    .catch(error => {
      if (!ignore) setError(error)
    })

  return () => {
    ignore = true
  }
}, [id])
```

   或者使用 `AbortController`：

```tsx
useEffect(() => {
  const controller = new AbortController()

  fetch(`/api/users/${id}`, { signal: controller.signal })
    .then(r => r.json())
    .then(setUser)
    .catch(error => {
      if (error.name !== 'AbortError') setError(error)
    })

  return () => controller.abort()
}, [id])
```

   cleanup 会在 `id` 变化时、下一次 setup 之前执行，也会在卸载时执行；它只负责“让旧请求的结果失效”，并不自动取消网络请求，除非使用 `AbortController`。

   加载状态设计：
   - 不要在 `id` 变化时立刻 `setUser(null)`，这会造成“旧内容 → 空白/加载 → 新内容”的闪烁。
   - 初次加载显示骨架屏/Suspense fallback；切换或刷新时保留旧数据，用 `isPending`、半透明、顶部进度条等内联指示表示“正在更新”。
   - 也可以使用 Suspense + 按 id 缓存的 Promise，并把切换放进 `startTransition`，让旧内容保留到新 Promise 就绪；初次加载仍由 fallback 负责。
   - 用 `use` 时，等待哪份数据由当前渲染传入的 Promise 决定，不需要手写 `setUser` 的竞态保护；但缓存键必须与 `id` 对齐，切换 id 要拿到新的 Promise。缓存键写错仍会取错数据。
   - 错误状态与加载状态分开：初次加载失败和后台刷新失败可以使用不同 UI，并提供可真正重置边界和重新请求的“重试”。

### 评分点（共 2.5 分）

- 0.5 分：pending 时显示 Suspense fallback，reject 后 Error Boundary 显示错误；没有边界时错误传播到根、UI 被移除。
- 0.5 分：指出重试按钮只改 `attempt` 无效（边界仍处于错误状态，且 Promise 仍是同一个 rejected 实例）；说明必须同时重置边界 + 换新 Promise。
- 0.5 分：说清边界放置范围/粒度；指出不能捕获事件处理函数和普通异步回调错误，能提到 `startTransition` 例外。
- 1 分：正确预测 alice 覆盖 bob 的竞态，说明旧请求后到会 `setUser` 覆盖；给出 ignore 标记或 AbortController 的 cleanup；加载状态设计合理（不 `setUser(null)`、保留旧内容 + `isPending`，或 Suspense + transition）。竞态解释与修复占 0.75，加载状态设计占 0.25；只写“用 cleanup”但没让旧响应失效，不给修复分。

### 简短解释

Suspense/`use` 负责“等待”，Error Boundary 负责“渲染期错误”，Effect cleanup 负责“让上一次异步工作的结果失效”。三者职责不同：`use` 的 rejected Promise 会走渲染期错误通道，所以必须用 Error Boundary；Effect 里的 fetch 不会自动激活 Suspense，也不会自动取消，竞态要自己清理。
